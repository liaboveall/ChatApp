## 产品与范围

**D-001 重写，不修补**
旧版的问题是结构性的：迁移链断裂、数据模型导致越权、前端 JS 需要全部重写、技术栈落后两个大版本。在旧代码上修补，成本会高于重写。

**D-002 技术选型只看"最新、最好"（用户）**
不考虑用户是否熟悉，也不参考其他项目的技术栈。版本以 registry 上的最新稳定版为准，不用 beta 或 RC，例外会单独注明。

**D-010 邀请制注册（用户）**
- 注册必须持有邀请码。站点管理员可以无限邀请；普通成员有 5 个"成功邀请"名额，可以调整。
- 群邀请链接只对已注册用户有效，因此不能被当作注册的后门。
- 既然只有受邀者能注册，就不需要人机验证。

**D-016 桌面优先（用户）**
- 以 ≥ 1280px 为主，最低支持 1024px；手机和平板布局放到 v1.1。
- 桌面端的 PWA 仍然要做：可以安装成独立窗口，并使用 Window Controls Overlay。

**D-017 Apple Liquid Glass 风格（用户）**
- 以 2026 年 WWDC 修正后的版本为准，即可读性优先。
- 玻璃效果只用于导航层，内容层保持实底；提供四档透明度。
- 不打包 SF 字体，不使用 SF Symbols，也不使用任何 Apple 商标。原因是授权只允许在 Apple 平台上使用。

**D-018 本地优先，上线放在最后（用户）**
- M1 到 M7 都在本地开发和验收；M7 在本地用生产配置做一次 HTTPS 彩排，降低最后上线的风险。

**D-020 消息规则**
- 撤回：2 分钟内，与微信的习惯一致。
- 编辑：24 小时内，不保留历史版本。
- 超出撤回时限后，只能"仅对自己删除"。
- 群主或会话管理员、站点管理员可以删除任何消息，并写入审计日志。

**D-021 附件**
> 2026-10-01补充：单位与基础设施硬限以D-078为准（MiB/GiB）；后台只能在硬限内收紧，隔离实施见D-081。下列保留历史表述。
- 单个文件 100 MB，图片 20 MB，每人总空间 5 GB，均可在后台调整。
- 视频不做转码，因为服务器只有 2 个 CPU 核心。
- HEIC 格式、视频封面放到 v1.1。
- ↪ **D-041** 补充：视频重新封装以去除位置等元数据（仍然不转码）。

**D-022 AI 预算默认值**
> 2026-10-01修正：D-087保留预算初值，取代“足够日常使用”的容量判断；D-062管预占，06第8.1节管任务容量和实验预留。
- 每人每天 50 万 token；全站每月 20 美元，用到 80% 时提醒，100% 时暂停。
- 按 DeepSeek 的价格，这些额度足够日常使用；均可在后台调整。
- ↪ **D-034**、**D-049** 补充：额度和预算只针对站点 key 的运行；"每天"和"每月"按 `Asia/Shanghai` 计算。

**D-026 频道里成员加入、离开不产生系统消息**
频道人多，这类消息会刷屏；成员变化只体现在成员列表里。群组和私信里照常产生。

**D-027 站点管理员不能读取私有会话的内容**
- 站点管理员可以对会话做管理操作，但读不到自己不在其中的群组、私信、Agent 会话的消息。
- 唯一的例外是处理举报时，可以看到被举报的消息及前后各 5 条，并且要写入审计日志。
- ↪ 已被 **D-034** 补充：使用站点 key 的 Agent 运行内容，站点管理员也可以查看（同样写审计日志）。例外从一个变为两个。

## 架构与技术

**D-003 全栈 TypeScript；后端用 Bun 1.4 + Hono 4**
- 选择理由：
  - 前后端共享 zod 契约，类型和运行时校验都统一；
  - Bun 自带高性能的 WebSocket 发布订阅、S3 客户端和测试工具；
  - Hono 基于 Web 标准，万一需要，可以换回 Node 24 LTS 运行。
- 放弃的方案：
  - Django 6 + Channels 4：两种语言，实时能力偏弱；
  - Elixir/Phoenix：实时能力最强，但生态小，也无法和前端共享类型；
  - Go、Rust：性能不是这个项目的瓶颈；
  - Elysia：只能跑在 Bun 上。
- ↪ "可以换回 Node"只在一定范围内成立，Bun 专有 API 的边界见 **D-055**。

**D-004 前端用 React 19.3 单页应用 + Vite 8**
- 选择理由：
  - 应用需要登录才能使用，用不到服务端渲染；
  - React 的组件生态最全（Base UI、virtua（原定 react-virtuoso，V-09 实测后改，D-144）、Streamdown 等）；
  - React Compiler 1.0 可以自动处理大部分性能优化。
- 放弃的方案：
  - Next.js 16：对 WebSocket 支持不好，服务端渲染用不上；
  - TanStack Start：用不上服务端渲染；
  - Vue 3.6、Solid 2：还在 RC 阶段；
  - Svelte 5：可以用，但生态不如 React。

**D-005 实时模型：写操作走 HTTP，WebSocket 只推送；用 seq / change_seq 补发；自己实现 WebSocket 层**
- 放弃的方案：
  - Socket.IO：协议较重；
  - Centrifugo：为超大规模设计，对我们来说只是多维护一个服务；
  - Zero 1.9、Electric 这类同步引擎：聊天消息基本只追加，"序号 + 事件"已经够用；而"正在输入"、AI 流式输出这类瞬时事件，照样需要另开通道。

**D-006 PostgreSQL 18.6 + pgvector 0.8.6**
- PostgreSQL 19 目前还是 beta4，不用。
- 18 版原生支持 `uuidv7()`；pgvector 提供语义搜索和 Agent 记忆需要的向量能力。

**D-007 Valkey 9.1 + BullMQ 6**
- 用途：事件总线、在线状态、限流、任务队列。
- 放弃的方案：
  - Redis 8：Valkey 是 BSD 许可的社区版本，功能相当；
  - pg-boss：既然已经有 Valkey，BullMQ 更成熟，功能也更全。

**D-008 对象存储用 Garage 2.4（自托管 S3）**
- 选择理由：占用资源很小，支持 arm64；对外是 S3 接口，以后可以换成 R2 或 S3；下载统一经过应用鉴权。
- 放弃的方案：
  - 直接存本地磁盘：以后不方便迁移；
  - MinIO 社区版：已进入维护模式；
  - RustFS：9 月中旬才发布 1.0，还太新。

**D-009 认证用 Better Auth 1.7**
- 支持邮箱密码（必须验证邮箱）和 Passkey。
- 不做第三方登录：在邀请制下意义不大。
- 两步验证放到 v1.1。

**D-012 ORM 用 Drizzle**
- 选择理由：贴近 SQL，适合序号分配、未读数、部分索引、pgvector 这类场景。
- 放弃的方案：Prisma 7，可以用，但对 SQL 的控制力不如 Drizzle。
- 版本：Drizzle 1.0 目前是 RC4。M1 开工时如果 1.0 已经正式发布，就用 1.0；否则先用 0.45.x，并计划在 1.0 正式发布后升级。

**D-024 组件底层用 Base UI 1.8（Radix 作为备选）**
Base UI 提供无障碍的交互原语（菜单、弹窗、焦点管理等）；视觉部分按 02 整体重做。组件的组织方式参考 shadcn/ui。

**D-025 不使用 outbox 表**
> 2026-10-01：以下为历史记录；相关实现条款由 D-056 取代或补充。
事件在事务提交之后发布；万一发布失败，客户端会通过 `change_seq` 补发兜底，因此不会丢数据。
- ↪ **D-043** 补充：客户端按会话检测 `changeSeq` 跳号。否则发布失败而连接没断时，客户端没有理由去补发，上面的兜底并不成立。

**D-030 Garage 的访问密钥由 setup 生成，再导入 Garage（开发准备）**

**D-032 清理 git 历史中的用户上传文件（用户确认，2026-09-30；执行了 D-019 中待确认的那一步）**
- **删除范围**：所有历史中的 `media/chat_files/`、`media/room_icons/`，以及 `media/profile_pics/` 下除 `default.jpg` 以外的文件，共 96 个路径、约 41 MB。
- **保留**：3 个应用素材（`media/default.jpg`、`media/profile_pics/default.jpg`、`media/ai_avatar/ai_avatar.png`），这样 `v1-legacy` 仍然是完整的旧版代码。`.env` 只含默认配置，也不删。
- **做法**：在 `--no-local` 的镜像克隆里执行 `git filter-repo --invert-paths`（通过 `uvx` 运行）。推送前逐项核对：
  - 提交数量不变；
  - v2 最新提交的内容与改写前逐字节相同；
  - main 只少了 `media/` 下的文件；
  - 标签正确指向改写后的 main；
  - 仓库打包大小从约 35 MB 降到 264 KB。
- **推送**：以原子方式推送，main 使用 `--force-with-lease`（仅当远程仍是旧提交时才覆盖）。之后本地仓库也同步到了改写后的历史。
- **残留风险**：
  - GitHub 上已经没有任何分支或标签引用旧提交，但在 GitHub 做垃圾回收之前，知道旧提交号的人仍可能直接访问到它。如需彻底清除，要联系 GitHub Support。
  - 本地的 reflog 中还保留着旧提交，大约 30 天后会自动清掉，也可以手动执行 `git reflog expire --expire=now --all && git gc --prune=now` 立即清除。

## 规划审查修订（2026-09-30，会话 2）

> 来自对 00–13 的全面审查。标"用户"的四条由用户拍板；其余由 Claude 按用户授权决定（原话："其他的要优化完善的地方你自己决定"）。

**D-033 内存预算放宽（用户）**
- 只要求不超过服务器的总内存。ChatApp 合计上限约 6 GB：api 1 GB、worker 2 GB、postgres 2 GB、valkey 512 MB、garage 512 MB（见 10 第 3 节），其余留给已有站点和系统。
- 取代 10 中"合计 ≤ 1.5 GB"的约束。本地向量模型的标准相应放宽：内存 2 GB，模型文件 1.5 GB，允许选用比 int8 精度更高的版本（06 第 10 节）。

**D-034 站点 key 的 Agent 运行内容可以由站点管理员查看；鼓励用户自带 key（用户）**
- 区分两种 key：
  - **站点 key**：站点提供的 DeepSeek key；
  - **自带 key**：用户在设置里填写的自己的 DeepSeek key（M5a）。
- 使用站点 key 的运行：完整内容保留 30 天（后台可调），站点管理员可以在后台查看，每次查看都写审计日志。完整内容包括请求、读取到的消息、工具参数和结果、模型输出。
- 使用自带 key 的运行：管理员只能看到用量、状态、耗时等元数据。
- 界面鼓励使用自带 key，但文案只讲好处：不占每日额度，全站预算用完时照常可用。文案里不提管理员能看到内容（用户要求）。
- 隐私说明（01 第 4.11 节）如实写明管理员能看到什么。这是 Claude 的补充：原规格对用户承诺"管理员不能读取私有内容"，如果不更新说明，就与实际行为不符。
- 补充 D-027：管理员能看到私有内容的例外从一个变为两个。

**D-035 新成员看不到加入前的历史（用户）**
> 2026-10-01：以下为历史记录；相关实现条款由 D-057、D-060（保留用户的历史不可见目标，替换实现） 取代或补充。
- **适用范围**：频道和群组。退出或被移出后再加入，按新成员处理。
- **实现**：`conversation_members.visible_from_seq` 记下加入时会话的 `last_seq`，成员只能看到 `seq` 比它大的消息。已读位置也从这里开始，未读数不会一加入就显示 99+。
- **所有读取路径用同一个可见性判断**：消息列表、补发、搜索、Agent 工具、语义搜索、附件下载、引用摘要。
- **广播不能泄露**：如果被更新的消息早于最近一次有人加入（`seq ≤ conversations.last_join_seq`），只广播不含内容的 `message.changed`，客户端再按自己的权限补拉。Agent 的流式输出同理。

**D-036 "重新生成"替换原回复（用户）**
> 2026-10-01：以下为历史记录；相关实现条款由 D-068（保留原位替换目标） 取代或补充。
- 在原位置替换同一条消息，旧内容不保留；只有发起这次运行的人可以操作。
- Agent 会话和面板里，只能重新生成最近一条回复；群组和频道里，24 小时内可以重新生成。执行过需要审批的工具的运行，不能重新生成。
- 取代 05 中"基于同样的输入重新运行一次"的模糊描述。

**D-037 副作用工具恰好执行一次（取代 INV-10 的原做法）**
- **原做法的问题**：原做法是"先写入步骤，重试时发现步骤已存在就跳过"。如果 worker 在"写完步骤、还没执行"时崩溃，已经批准的操作就永远不会执行，而且会补写一个虚构的结果。
- **新做法**：副作用操作和一条 `agent_effects (run_id, step_index)` 记录在同一个事务里提交。重试时先查这张表：有记录就直接返回之前的结果，没有才执行。
- **状态存放**：续跑需要的完整模型消息存进 `agent_run_states`；`agent_steps.payload` 只存供展示的截断版本（≤ 32 KB），避免截断破坏续跑时重建的历史。

**D-038 WebSocket 连接与登录会话绑定**
> 2026-10-01：以下为历史记录；相关实现条款由 D-057、D-070 取代或补充。
- 每个连接记下自己的 sessionId。退出登录、注销其他设备、账号被封禁或修改密码时，发一条内部事件，让对应的连接在几秒内以 4401 关闭。另外每 5 分钟复核一次会话。
- 推送订阅也和登录会话绑定，会话失效时一并删除。
- 修改密码时注销其他所有会话，通过邮件重置密码时注销全部会话。不开启 Better Auth 的 `cookieCache`，否则已注销的会话在缓存期内仍能调用 HTTP 接口。

**D-039 收紧 Better Auth 的原生接口**

**D-040 邀请名额原子占用；未验证的账号怎么处理**
> 2026-10-01：以下为历史记录；相关实现条款由 D-059 取代或补充。
- **注册时的占用**：先原子地占用名额——邀请码的 `use_count` 条件加 1，邀请人的 `users.invites_used` 也条件加 1，并写入一条 `pending` 使用记录（10 分钟内没有确认就自动释放）。账号创建成功后，这条记录改为 `confirmed`。
- **未验证的账号**：7 天内没有验证邮箱的账号会被自动删除，邀请名额、用户名和邮箱随之释放。邀请人也可以立即撤销还没验证的注册，比如对方把邮箱填错了的情况。
- **邮件送不到时的兜底**：用 `bun run admin:verify-email`（M1a），或者在管理后台（M7）手动标记邮箱已验证。

**D-041 附件按用途授权；视频去除位置信息**
- **读权限**：消息里的附件，谁能看到这条消息谁就能读；用户头像，所有登录成员都能看；会话头像的可见范围和会话本身一样（频道全站可见）。这修正了原 INV-09 与头像的矛盾。
- **图片**：先按拍摄方向旋转，再重新编码去除 EXIF。
- **视频**：用 `ffmpeg -map_metadata -1 -c copy` 重新封装，去掉位置等元数据。这不是转码，所以和 D-021 不冲突。处理失败的视频改为只能下载。
- **服务端镜像**：改用 Debian 系的 `oven/bun:1.4-slim`，因为 ffmpeg 和 onnxruntime 需要 glibc。

**D-042 会话级封禁；邀请链接随创建者一起失效**
- **封禁**：被"移出并封禁"的人，不能通过频道发现、群邀请链接或被别人拉入的方式重新加入，直到被解除封禁。
- **邀请链接失效**：群邀请链接的创建者退出或被移出群组时，他创建的链接自动作废；如果群组设置为 `admins_only`，创建者被取消管理员时也一样。

**D-043 补强实时一致性（补充 D-005、D-025）**
> 2026-10-01：以下为历史记录；相关实现条款由 D-056 取代或补充。
- **跳号检测**：客户端按会话检测 `changeSeq` 是否跳号，缺号 1 秒后仍未补上，就调用 `/changes`。这样"事件发布失败、连接却没断"的情况也能自愈。
- **`/changes` 的补充**：接口同时返回这段时间里我隐藏的消息。如果缺口超过 1000 条变更，接口返回 `resetRequired`，客户端丢弃这个会话的缓存，重新加载。
- **焦点上报**：客户端新增 `focus` 消息，上报当前在看的会话以及页面是否在前台。正在看的会话不推送。
- **在线状态**：按连接分别记录活跃状态再汇总；worker 每 30 秒清理一次过期的连接，并发布离线状态；客户端发出 `presence.watch` 后，服务端立即回一份当前状态；用户的最后一个连接断开时，写入 `users.last_seen_at`。
- **客户端的连带更新**：收到某条消息的更新时，同时更新引用它的回复和会话列表里的预览。

**D-044 数据库是唯一的事实来源；Valkey 的使用规范**
> 2026-10-01：以下为历史记录；相关实现条款由 D-056、D-061、D-071 取代或补充。
- **频道名**：Valkey 的 pub/sub 不区分 db 编号，所以事件频道名要带上环境：`events:{APP_ENV}`。
- **任务保留与告警**：BullMQ 统一设置任务保留期限：已完成的保留 1 天或 1000 条，失败的保留 7 天。Valkey 内存用到上限的 80% 时告警。
- **对账任务**：定时消息、提醒、审批过期、卡住的 run，都以数据库为准。`reconcile` 任务每分钟把到期的项重新放入队列，并用实体 id 作为任务 id 去重。因此 Valkey 不需要备份。
- **登录会话**：以 Postgres 为准，Valkey 丢了数据不会让用户掉线。
- **客户端库**：应用里所有 Valkey 访问统一用 ioredis（BullMQ 本来就依赖它）。

**D-045 网关、安全响应头与健康检查**
- **安全响应头的分工**：静态文件（index.html、assets）的 CSP 等安全头写在 Nginx 站点配置里；API 和附件的响应头由应用设置；两边不重复。HSTS 由 Nginx 添加。

- **健康检查**：路径改为 `/api/healthz`、`/api/readyz`，避免被前端的回退规则拦走。
- **客户端 IP**：只信任本机反向代理（`TRUSTED_PROXIES`）写入的客户端 IP 头，限流按真实 IP 计算。
- **邀请码不进日志**：不出现在服务器会记录的地方。检查接口改为 POST；注册链接和群邀请链接把码放在 URL 的 `#` 后面。

**D-051 补强 Agent 的安全与行为**
> 2026-10-01：以下为历史记录；相关实现条款由 D-060、D-061、D-068 取代或补充。
- **面板和 ⌘K 的读取范围**：默认只读当前会话，用户在界面上明确切换到"我的全部会话"后才放宽。原因是面板既读不可信的群聊内容，又能接触私密数据；一旦被注入，可能把私信写进草稿或链接。
- **记忆的写入**：只有本轮用户原话里有明确的记忆意图（"记住""别忘了"等）时，才向模型提供 `remember` 工具；否则写入记忆需要审批。这是为了防止记忆被投毒。
- **等待审批时的消息**：当前消息先收尾，标为"等待某某批准"；继续运行时再新建一条消息。这样群里不会挂着一个长达 24 小时的"输出中"气泡。
- **机器人的身份**：机器人不是任何会话的成员，不出现在成员列表里。Agent 的回复由专门的 domain 函数写入，前提是调用者此刻仍能在该会话发言。Agent 消息中的 @提及不产生通知。
- **流式输出**：每 50–100 毫秒合并发送一次增量。每秒写库时，同时记下已写入部分对应的增量序号（`streamIndex`），中途打开会话的客户端可以接着往下拼。
- **评测**：
  - 安全类用例检查结果：没有泄露数据，也没有未经审批的副作用。必须 100% 通过。
  - "模型是否尝试了越权操作"单独统计。
  - 每周定时跑一次评测，及时发现 `deepseek-flash` 升级带来的变化。

## 独立复审后的实施规划（2026-10-01）

以下决定落实审查 F01–F24；表示设计已修订，不表示实现或故障测试已通过。

**D-056 持久工作意图与完整同步水位（取代 D-025、D-043 的可靠性交付方案，补充 D-044）**
- 业务变更、同步日志和需要可靠执行的工作意图在一个 Postgres 事务提交；增加 `work_items`，承担小型 outbox 和任务台账职责。dispatcher 至少一次派发，消费者依靠业务唯一键和条件更新去重。
- Valkey Pub/Sub 只是实时提示，BullMQ 只是执行运输层。独立的 Postgres 扫描循环恢复未完成任务，不能把恢复循环本身只放在可能丢失的队列中。
- 用只含实体标识的 `conversation_changes` / `user_changes` 日志和有固定上界的游标补齐；客户端区分 observed 与 synced 水位。前台每 30 秒对账，尾事件丢失也能发现。正常依赖下目标 35 秒内收敛；依赖故障时显示未同步，不能宣称已送达。
- 放弃只靠跳号和 after-commit 入队：它们不能恢复最后一个丢失事件或根本没创建的任务。协议见 03、05。

**D-057 内容按接收者投影，撤权以数据库为准（取代 D-035 的广播技巧、D-038 的五分钟兜底）**
> 后续D-079区分session与持久委托；D-082补实体版本与关系墓碑，其他权限原则仍有效。
- 消息创建、编辑和删除统一广播不含正文的变更提示，再按 HTTP 当前权限读取；引用、预览、附件列表也逐个做可见性投影。移除 `last_join_seq` 作为授权依据。
- 写入与成员变化按 03 的锁顺序串行化；WS 的个人内容和 Agent 增量在每次实际派发批次重新查会话、成员和运行版本，不靠缓存中的订阅名单授权。
- 注销事件可靠投递，并每 5 秒复核连接；授权查询失败即停止敏感派发。撤权提交后开始的授权读取必须失败；提交前已授权的在途响应或已下载内容无法收回，不承诺消除网络在途窗口。

**D-058 认证端点默认拒绝，管理员不具备代登能力（补充 D-027、D-034，取代 D-039 的黑名单收口）**
- `/api/auth/*` 不是无条件透传：仅放行 05 列明的登录、验证、本人会话和 Passkey 能力；其余默认 404。插件升级后的新路由默认关闭。
- 不启用 admin 插件的 HTTP 管理能力；禁止代登、替他人设置密码或邮箱、原生硬删除与无邀请创建账号。后台和 CLI 经应用 domain 执行，扩展字段一律禁止客户端赋值。
- 管理员限制是应用角色边界，不是对掌握主机、数据库和加密密钥的运维者提供端到端隔离。[Better Auth 管理插件](https://better-auth.com/docs/plugins/admin)能力不能直接等同于本站角色权限。

**D-059 注册是可恢复的激活状态机（取代 D-040 的 pending 超时直接释放）**
- 注册占用带稳定 `registration_id`，账号在第一次插入时原子写入同一标识并保持未激活。优先使用共享事务；adapter 不支持时使用 04 的可恢复流程，不能只在 after hook 关联账号。
- 邮箱验证与邀请确认都完成后才能激活；清理、人工验证、邀请撤销使用同一把注册锁。超时必须先查明账号是否存在，禁止仅按 pending 时间退名额。
- V-13 必须证明“账号创建时关联标识”可实现；若做不到，M1a 先实现定制 adapter/注册服务，注册入口不得以已完成交付。

**D-060 Agent 上下文有来源与范围世代（补充 D-014、D-035、D-051）**
- 面板切换读取范围即开启新上下文世代，不沿用另一范围的模型历史、摘要或工具结果。恢复与每次模型调用前检查全部来源；来源被撤权、编辑或撤回时终止旧 run，重新发起时重建。
- 共享输出只读所有当前接收者共同可见的当前会话消息，水位为成员 `visible_from_seq` 的最大值。成员世代变化时停止旧 run 的后续生成和发布，必要时从新水位重新请求。用户主动粘贴转述的内容属于新消息，不声称系统能防止人工转述。
- 无来源标记的旧摘要不允许直接恢复。个人长期记忆也不得注入共享输出。

**D-061 Agent 持久状态、执行租约和续跑编号（补充 D-037、D-044、D-051）**
- 审批回应、状态转为 queued、`resume_seq` 增加及工作意图必须同事务提交；每段输出以 `(run_id, resume_seq)` 唯一。BullMQ jobId 使用 work id 和投递序号，不复用已保留的 runId job。[BullMQ 任务标识规则](https://docs.bullmq.io/guide/jobs/job-ids)是运输层限制，不是业务去重依据。
- `lease_epoch` 防止旧 worker 提交；取消先写 Postgres，Valkey 仅用于唤醒。工具执行事务复核 epoch、取消、权限和审批参数哈希。
- “恰好一次”仅指同库事务内的业务效果；邮件、Web Push、模型供应商调用不能承诺外部恰好一次，未知结果按各自重试策略处理。

**D-062 调用前原子预占预算（补充 D-022、D-049）**
- 每次模型调用按保守输入估算、最大输出和思考 token、当前价格版本预占用户日额度与站点月费用；不足则不发起调用。统计缓存不能用于授权花费。
- 唯一 attempt id 记录 reserve → started → settled/unknown/released；usage 只结算一次。网络结果未知或收费后崩溃不得自动退占用或盲重试；保守记满上限并人工/供应商对账。
- 周期归属在预占时冻结，审批续跑新调用按新周期。该控制保证应用按配置计价的准入上限，不保证供应商账单绝无价格变动或外部重复计费。

**D-063 完整副本清单与删除时限（取代 D-048 的立即物理删除表述，补充 D-052）**
> 后续D-084补成功确认前的异地删除意图；下面的立即清空指最终在线删除事务完成，待异地确认时返回202而非成功。
- 撤回事务立即清空在线正文、提及与向量，并使附件不可访问；对象物理删除目标 1 小时、最长 24 小时，失败告警重试。备份最多 28 天，逾期备份未清理必须告警，不能继续宣传已物理清除。
- Agent 状态、步骤、审批参数、效果结果、派生摘要均进入 04 的保留清单。效果账本只留去重所需 id、哈希和结果码。删除私有 Agent 会话同时清除其运行内容；注销时取消未完成运行和未来任务。
- 普通消息撤回可能仍在既有 Agent 运行副本中保留到创建后 30 天；这些副本不能再作模型上下文。外部已送达通知、供应商副本、用户另存文件不可远程召回，隐私说明如实区分。

**D-064 上传预占、对象账本与媒体资源上限（补充 D-021、D-041）**
- 先持久化上传身份、临时对象 key 和配额预占，再接收流；无 Content-Length 时预占该类型上限。对象写入、处理、绑定、删除都有可恢复状态及代次。
- 用户配额按处理后的主文件计费，衍生文件计入全站容量；输出变大必须再原子预占，失败则删除且不公开。墓碑和删除任务防止旧处理任务复活对象。
- 图片像素、动画帧、时长、解码内存和超时有硬限；媒体子进程无网络，默认并发 1，和向量工作共享内存闸门。具体默认值见 01、03。

**D-065 Web Push 从 M6 起执行 SSRF 与接收权限检查（取代 SEC-23 的延期假设）**
- 注册和发送时均校验端点：HTTPS、受支持服务商域名清单、公共 DNS 地址、连接目标固定、无重定向、超时和出口防火墙；服务商清单由 V-10 的真实订阅证据确定，不能先允许任意 URL。
- endpoint 与用户、session、安装实例绑定，禁止无证明跨账号换绑。发送前重查成员、可见性、session、消息状态和通知偏好；通知正文临发送再生成。
- 中国网络可达性是实测事项，不承诺某浏览器必定可达。Sentry 转发只使用服务端固定目的地与项目 id。

**D-066 幂等键绑定操作与请求（补充 D-005）**
- Postgres 的 `idempotency_records` 唯一键包含 actor、operation、target、key，存规范化请求哈希与资源 id；相同键不同请求返回 409，重放前重新鉴权。
- 一般创建键保留 24 小时；消息 `(sender_id, client_id)` 在消息生命周期内唯一，跨会话复用也返回冲突；离线队列 24 小时后不自动重发。编辑用 expectedChangeSeq，已完成的撤回/取消可幂等返回。

**D-067 向量和摘要有内容版本（补充 D-015）**
- 任务携带 content_version、模型版本和维度，写回时确认消息仍有效且版本匹配；检索联表重查授权、删除状态及版本。模型迁移在新索引构建、评测完成后切换，不混用维度。
- 旧任务不能重建已撤回内容，摘要也需来源版本；本地向量性能按真实 ARM 测量，不由桌面耗时折算。

**D-068 重新生成不重做效果（补充 D-036）**
- 仅允许终态且未执行任何业务效果、无待审批的 run；包括提醒、记忆等无需审批的效果。重新校验当前权限和上下文后原位替换，保留稳定的目标消息 id。
- 原回复不作为消息历史保留；旧 run 副本仍按 30 天规则处理。输出达到 20000 Unicode 字符时停止并记录 length 截断，不因 token 预算大于字符上限而写库失败。

**D-069 跨表约束及生产 bootstrap（补充 D-052）**
- 群主与成员 owner 必须一致；转让、最后成员退出、归档恢复有明确事务与约束。附件有效绑定、Agent 内容清理和外键策略见 04。
- `db:bootstrap` 只创建机器人、系统保留名、配置默认值，可在生产幂等执行；`db:seed` 仅创建开发演示数据。不以开发 seed 代替生产初始化。

**D-070 离线数据按账号与会话世代隔离（补充 D-038）**
- Query、IndexedDB、草稿、队列、推送与 SW 消息均带 userId 和登录世代；注销先本地封锁并通知全部标签页，SW 只缓存公共外壳，敏感 HTTP 响应 no-store。
- 重连先验证当前身份、成员世代和幂等键，才发送 24 小时内纯文本队列。首次离线冷启动只显示外壳；已验证的活动标签页可以继续看已载入内容。不能宣称能立即清掉失联设备已下载的数据。

**D-071 一致备份、恢复隔离与目标（取代 D-044 的恢复后直接外发，补充 D-048）**
> 后续D-076/079/084补凭证与委托失效、独立删除journal。缺删除证据不能仅经人工确认解锁；RPO不放宽已确认删除重放要求。
- 不可变对象 key；备份先建立物理删除屏障，再取得数据库一致快照和附件清单，按清单校验对象，全部成功并异地落盘才算成功。失败备份不能替代上一份有效备份。
- 目标 RPO ≤ 24 小时、RTO ≤ 4 小时，以实际演练为准；每 12 小时执行，上一份异地备份快照年龄不能超过 24 小时，否则告警并记目标违约。
- 恢复先禁止模型、邮件、推送和定时外发，清会话/验证令牌、增加恢复世代，核对可能重复执行的任务后人工解锁。物理备份无法判断灾难前已发出的外部效果。

**D-072 健康、网关和旧前端升级（修正 D-045）**
- Docker restart 策略只处理退出，不会因 unhealthy 自动重启。应用内部死锁由独立 watchdog 有限重启；共享依赖故障只告警，不循环重启全部服务。
- HSTS 独立片段加 always，显式覆盖所有 HTTPS location 及错误响应；静态 CSP 与 API 头仍按职责划分。Nginx 1.28 不依赖新版本继承选项。
- 哈希资源保留至少 7 天且至少最近 3 版；API/WS 与上一版客户端兼容，过期客户端提示刷新，不能静默丢草稿。

**D-073 全站容量和背压（补充 D-033、D-052）**
> 后续D-078统一附件单位，D-081将原后台2GiB分为1536MiB worker与512MiB独立media，D-087补AI容量估算；不沿用同worker内解码的实现假设。
- 5 GB 是个人上限，不是给 1000 人预留 5 TB。上线前填写实际可用存储预算，设置预占闸门和磁盘水位；共享宿主机其他站点也计入余量。
- 目标数据集与混合负载、慢连接、重连风暴见 08。媒体、向量、Agent 的并发受同一 worker 2 GB 总预算约束；超限优先暂停向量和新 AI/上传，保留聊天和删除。

**D-074 可访问性是桌面版要求（补充 D-016、D-017）**

## 第二次独立复审后的规划完善（2026-10-01）

用户授权“全面优化完善项目规划”。以下 D-076–D-092 落实 [15 的 R01–R12 和五项一致性问题](15-planning-rereview-2026-10-01.md)，优先于它们明确补充或取代的旧条款。这里只完成设计；AT-25–AT-37、V-18–V-21 仍待实现验证。

**D-076 认证凭证绑定注册实例，服务端一次性消费（补充 D-058、D-059、D-071）**
- 邮箱验证和密码重置使用应用控制的随机 256-bit opaque token，数据库只存哈希及受限邮件投递密文；绑定 user_id、registration_id（普通注册必填）、用途、邮箱摘要、auth_epoch、restore_epoch、有效期和 consumed_at。不得用邮箱查找后来重建的替代账号。
- 默认有效期均为 1 小时；重发使同用户同用途的旧凭证失效。消费、验证事实、邀请确认检查及激活在同一事务中完成；密码重置的密码更新、消费、撤销也必须原子，禁止原生 JWT 回调旁路。
- 链接使用 /verify-email#token=… 或 /reset-password#token=…；页面读取后立即清 fragment，只在内存保留，用户确认后 POST 受控端点。GET 不消费、不激活、不登录，避免邮件预取扫描消费链接。人工验证仍受注册锁及审计约束。
- V-13 必须证明锁定版适配可行；不支持就做受控认证适配，不把默认库行为当作一次性、注册绑定或恢复失效的证据。AT-25 覆盖同邮箱重建、重发、重复、撤销竞态和旧快照。

**D-077 日志只记录白名单字段和规范化路由（补充 D-046、D-072）**
- 应用、Nginx、错误收集统一禁止原始 URL/query/Referer、Cookie、请求体和认证头；路径里的凭证同样不能记录。访问日志只记 route 类别、method、状态、耗时、服务端 requestId 和经信任链验证的 IP。
- 网关未知路由只写 unknown；不能回退到 $request/$request_uri/$uri。错误日志无法安全剥离请求行时，该站点使用丢弃原文错误输出的配置，以脱敏状态指标、上游健康和 requestId 诊断；不得影响其他站点日志。
- Sentry 在事件及 breadcrumb 发送前执行允许字段重建，拒绝 envelope 指定目的地；认证页使用 no-referrer。AT-26 用假哨兵同时验证成功、4xx、413、超时、上游失败、重定向和监控转发。

**D-078 请求按用途预算，先限流读取再解析（补充 D-064、D-072）**
- 普通 JSON 原始 UTF-8 请求体最多 128 KiB；monitoring envelope 最多 256 KiB；单文件流最多 100 MiB 且不能超过 reservation。全版附件大小统一按 MiB/GiB 计算，界面明确单位。
- 网关和应用均在解析前执行字节限额；不信任 Content-Length，无长度流也累计，异常 framing 拒绝。拒绝请求 Content-Encoding 压缩，避免解压放大。普通请求总读取 15 秒、空闲 5 秒；上传总 120 秒、空闲 15 秒。端点可以更严，不能全局放宽。
- 未读完的大请求不反射输入；默认 413、415 或 408，关闭/取消上游读取。M1a 校准最大合法中文正文、Passkey 和审批参数；不够时只调整经证据批准的端点。AT-27 覆盖直连 API 与代理两条路径。

**D-079 请求身份与持久委托分离（补充 D-057、D-061）**
- domain 接受服务端构造的 SessionPrincipal、DelegatedPrincipal 或限定维护动作的 SystemPrincipal，拒绝裸 userId 作为执行凭证。后台 run/未来任务使用持久 delegation，记录来源设备 origin、账号 auth_epoch、restore_epoch、目的、目标、参数哈希、到期和撤销状态；执行时仍检查当前成员/禁言/归档/来源。
- 普通退出、自然 session 过期不撤销已授权任务；明确撤销设备则撤销该 origin 的全部未完成委托。注销其他设备只影响其他 origin；安全性“注销全部设备”、改密、重置、封禁、注销和恢复撤销全部委托。改密可以保留当前登录会话，但也撤销全部旧委托；解封不复活任务。
- run 委托最长 25 小时，审批不延长；批准的定时消息/个人提醒有独立子委托，最长预约 365 天，到点超过 24 小时未执行即 failed。取消父 run 不撤销已提交的未来任务，用户可在任务列表单独取消；删除相关 Agent 会话/注销则全部取消。
- 权限检查在事务锁内；撤销先提交则旧 worker 不得提交新效果，已经发出的模型请求仍结算 usage。完整真值表见 03，AT-28。

**D-080 私有 BYOK 内容的来源限制随派生数据传递（补充 D-034、D-060）**
- 私有 Agent 会话/面板中的 BYOK 请求、输出、附件与派生记忆/摘要标记 byok_private；站点 key 的自动上下文和全部工具查询均排除该类别。复制、摘要、向量命中和恢复不能丢失标签；旧数据缺标签时拒绝作为站点输入。
- key_source 在创建 run 时固定，来源或 scope 切换都新建 context_epoch。改用站点额度是新建空白请求，不重放 BYOK prompt、图片、工具结果或摘要；用户可以主动重新输入。私有记忆默认保留原类别，设置页手动新增默认 byok_private，可逐条明确允许站点助手使用。
- 此保护不改变共享消息的权限：群里主动 @Agent 的消息及群内回复、完整预览并批准的代发内容，是用户明确发布的普通消息；有权用户后续可用站点助手读取，可能进入站点运行审计。只释放发布的内容，不释放原 run、私有推理/工具结果；隐私页说明此边界，鼓励 BYOK 的文案仍只讲好处。
- AT-29 同时验证私有内容不随 key 切换泄露、工具全范围检索不绕过，以及明确发布内容按普通权限可用。

**D-081 固定媒体执行容器，隔离网络和业务凭据（落实 D-064，修正 D-041 的共进程假设）**
- M3 创建独立 media 镜像/容器：network_mode=none、非 root、read_only、cap_drop=ALL、no-new-privileges、默认 seccomp、pids_limit=64、memory/swap 总上限 512 MiB；可写 tmpfs 总 256 MiB，临时文件计入内存上限。不挂载 Docker socket、应用 env、数据库或对象存储卷。
- worker 负责授权、S3 与账本；通过仅两者可访问的 Unix socket 传受限文件字节和固定操作枚举，禁止任意命令、URL、宿主机路径。media 不持有 S3/DB/模型凭据。单并发、单任务 60 秒，终止整个子进程组并清理；协议和输出限额由 worker 独立检查。
- worker 限 1536 MiB，media 限 512 MiB，合计保持原后台 2 GiB 预算；向量 ≤1 GiB 且受余量闸门约束。V-18/AT-30 在真实 Linux/ARM 上验证 IPC、隔离、超时、OOM、资源占用；失败时阻止媒体上线，不退回有凭据的 worker 解码。

**D-082 实体版本与同步游标各司其职（补充 D-056、D-066）**

## M1a 实施决定与实验结论（2026-10-01）

> 以下是 M1a 实施中的决定，均有可重复运行的测试或命令作证据（见 PROGRESS 的 M1a 交接记录）。它们补充或修正对应的旧条款，不改变用户已定的产品方向。

**D-094 认证入口由受控处理器实现，SDK 只转发 Passkey（补充 D-058、D-076，V-13 结论）**
- `/api/auth/*` 前面是精确的 method + path 允许清单（`packages/contracts/src/auth-endpoints.ts`）。注册、登录、退出、改密、邮箱验证与密码重置共 8 个入口由应用自己的处理器实现：先做请求预算、Origin、限流和 zod strict 校验，再经 domain 事务写入；登录用 `auth.api.signInEmail` 完成口令校验与建会话，响应体去掉令牌。只有 7 个 Passkey 路由在严格校验后转发给 SDK。SDK 注册的其余 28 个 (方法, 路径)，包括 `get-session`、`list-sessions`、`revoke-*`、`update-user`、GET 的 `verify-email` 和 `reset-password/:token`，一律 404。
- 原因：① 原生 `get-session`/`list-sessions` 的响应带 `session.token`，等于把 HttpOnly 令牌（以及其他设备的令牌）交给脚本；② SDK 的 `after` 钩子在事务提交之后才执行、拿不到事务句柄，无法在首次 INSERT 关联注册，也无法原子消费凭证；③ 原生验证/重置是 GET 链接加 JWT，预取就会消费，也不能绑定注册实例和 restore_epoch。
- 证据：`test/security/auth-matrix.test.ts` 用匿名、成员、管理员三种身份请求 SDK 注册的全部 39 个 (方法, 路径)，除允许清单外全是 404 且数据库无变化；`test/contract/auth-sdk-endpoints.snapshot.json` 固定 SDK 端点清单，升级后出现新路由会让测试失败；路由变体（大小写、尾斜杠、`%` 编码、双斜杠、`;`、错误方法）全部 404。
- 设备管理改为 `/api/me/devices` 一组接口（列表、撤销单台、注销其他、安全注销全部），以 origin 作设备，不暴露令牌。
- 放弃：透传 SDK 加 after hook 关联注册；启用 admin 插件。

**D-095 不启用 username 插件（补充 D-039）**
- username 由受控注册写入并带 CHECK（`^[a-z0-9_]{3,20}$`），保留名走 contracts 的保留名单和 `username_reservations`；在 SDK 里只声明为 `required: true, input: false` 的用户附加字段。声明还有一个作用：Better Auth 1.7.7 带运行时 Drizzle schema 检查，会拒绝“存在 SDK 从不写入的 NOT NULL 列”，这个检查在升级时也是保险。`display_username` 列不建。
- 原因：插件的增量只有用户名登录（05 已禁止）和 `is-username-available`；它的校验钩子与受控创建重复。

**D-096 注册在一个事务里完成，中间状态保留为可恢复行（落实 D-059，V-13 结论）**
- `registerAccount` 在单个事务中按“邀请人 → 邀请码”的锁序占位（条件更新 `use_count` 与 `invites_used`），写入 registration，账号第一次 INSERT 就带 `registration_id` 并保持 pending，随后建立双向关联、转 confirmed，创建验证凭证和 email work_item，写幂等记录和审计。口令哈希在取锁前计算，并且总会计算，已有邮箱与新邮箱耗时一致。已有邮箱返回与成功相同的通用响应，不占名额；用户名冲突返回 409。`reserved`/`account_created` 状态与对账器（`reconcileRegistrations`）仍保留，用来恢复多步创建。
- 证据（AT-05）：在 registration / accounts / auth_challenges / work_items / audit_logs 各自的 INSERT 上用触发器注入失败，整体回滚、名额不变，同一请求在故障消除后仍可成功；同一单次码 6 个并发恰好 1 人成功；额度 2 的成员 5 个并发恰好 2 人；两个码抢同一邮箱只建 1 个账号、只占 1 个名额；对账器的释放与退额度只发生一次。
- 放弃：延迟外键的多步流程（共享事务做得到时不需要）；after hook。

**D-097 数据库拥有者账号与应用账号分离（落实 04 约定）**
- 新增 `DATABASE_OWNER_URL(_TEST)`；`DATABASE_URL(_TEST)` 是无特权的 `chatapp_app`。迁移、bootstrap、CLI、测试清表用拥有者；`db:migrate` 迁移后幂等创建并授权应用账号（默认权限覆盖以后新增的表）。API 与 worker 启动自检：未 bootstrap 就拒绝启动，生产里账号有特权也拒绝。`bun run setup` 会把旧布局一次性转成新布局并补齐模板新增的键。
- 证据：集成测试用应用账号连接，并断言它不能建表、改表、truncate、建角色、读迁移记录。

**D-098 限流用自有 Valkey 限流器，失败即关闭（落实 SEC-11；修正 03/07 里“Better Auth 限流计数存 Valkey”的说法）**
- 固定窗口，INCR 与 PEXPIRE 在同一个 Lua 脚本里；键含环境；主体是 IPv6 按 /64 分组后的 IP，或账号邮箱的 HMAC 摘要。Valkey 不可用时返回 503 + Retry-After，不放行。不使用 Better Auth 内置限流，也不使用 `secondaryStorage`（它会让会话读取走缓存，违背“每次请求查当前会话”）。
- 匿名“请求”类端点（验证重发、找回）至少耗时 300 ms，已有账号与未知邮箱的响应时间相同。

**D-099 `users.account_source` 与 INV-18 的 CHECK**
- `account_source ∈ {registration, cli, bootstrap}`。CHECK：active 必须 email_verified；只有 registration 来源的账号带 registration_id，并且从第一次 INSERT 起就带。CLI/bootstrap 是 INV-18 里“受审计的例外”，创建时写审计行。

**D-100 会话与 Cookie 的实现结论（V-04、V-05、V-13）**
- UUID（V-04）：`advanced.database.generateId` 注入 UUIDv7 后，SDK 创建的行（会话、passkey 挑战）用 uuid 主键工作正常；Drizzle 适配器要求 `usePlural`，并可用 `transaction: true` 让整个原生流程共享一个事务。
- Cookie（V-05）：SDK 默认会生成 `__Secure-` 前缀。要得到 `__Host-`，必须 `useSecureCookies: false`，自己给出名字 `__Host-chatapp.session_token` 并显式设置 `secure`、`path=/`、不设 Domain。https 下实测通过；http 开发环境使用无前缀名。M7 在真实 Nginx 下再复核。
- 会话令牌在库里是明文，Cookie 值是 `令牌.签名`；因此备份加密与数据库访问限制是硬性要求（04 已写）。
- 会话带 `auth_epoch` 与 `authorization_origin_id`（SDK 的 additionalFields，`input: false`）：`session.create.before` 钩子在建会话时同时做账号状态闸门并创建 origin；每次请求再由 `resolveSessionPrincipal` 复核账号状态、epoch、origin 与 restore_epoch，写入路径在事务里用 `lockAndRevalidate`（先锁用户行）再次复核。

**D-101 请求预算、路径规范化与日志的实现（落实 D-077、D-078）**
- 请求预算中间件在任何解析之前读取并计数：不信 Content-Length，总时限 15 s、空闲 5 s，超限 413，压缩 415，Content-Type 只认 UTF-8 JSON，Content-Length 与 Transfer-Encoding 同时出现 400，非法 UTF-8 或 JSON 422。读完后把文本预填进 Hono 的 `bodyCache`，校验器与处理器不再碰原始流（有测试固定这一行为）。Bun 的 `maxRequestBodySize` 暂设 1 MiB；M3 上传需要为该路由放宽，并保持流式计数。
- 路径守卫：路径含 `%`、`//` 或反斜杠一律 404；点段在 URL 解析时已被规范化，所有层看到同一个 URL，不存在解析差异。
- 日志：pino 只接受白名单字段；路由记匹配到的模式，通配则记 `unknown`；Drizzle 包装的错误消息里带 SQL 和参数值，所以错误只记类名、SQLSTATE、约束名和栈帧。AT-26 的哨兵测试覆盖成功、4xx、413、415、422、429 与 500。

**D-102 WebSocket 网关：先接受升级再按码关闭，持久撤权加 5 秒复核（落实 05 第 4 节）**
- Origin、限流和会话在升级前判定，随后接受升级并以 4403/4401/4429/1013 关闭（浏览器看不到被拒升级的 HTTP 状态）。连接绑定 sessionId、originId 与 authEpoch。撤销（退出、设备、改密、重置）在同一事务里写 `realtime` work_item，worker 的 dispatcher 发布到 `events:{env}`，网关立即复核（真实进程走查中退出后 58 ms 关闭，集成测试要求 < 2 s）；hint 丢失时每 5 秒批量复核（实测 ≤ 6 s），复核查询失败即 1013 关闭。帧 64 KiB、每 10 秒 200 条、每用户 10 连接、25 秒心跳、60 秒无响应 4408、256 KiB 发送缓冲。
- 未做：topic 订阅与 Hub（M2），presence/typing（M2b）。

**D-103 隔离故障环境的实现（落实 D-085，AT-34）**
- `compose.test.yml` 每次运行一个独立 compose 项目（`chatapp-test-<runId>`），随机密码，每次运行选定后固定的随机回环端口（必须固定：容器重启后 Docker 会重新分配随机端口）；清单 `.test-runs/<runId>/manifest.json` 权限 600、不入库。注入前逐项验证：`APP_ENV=test`、project 与 run-id 标签、完整容器 id、卷与网络标签、只绑 127.0.0.1 且不含开发端口、库名 `chatapp_test`、在三个服务里读回的随机实例标记；动作只经 `act()`，每次重新核对标签；清理只对该项目执行 `compose down -v`，核验失败就什么也不删，也不使用 prune。

**D-107 jsonb 列统一用 `jsonbValue`，不用 Drizzle 自带的 `jsonb()`（2026-10-02）**
- 发现：给你创建管理员账号后，我用 SQL 查审计行的 `metadata->>'role'` 得到空值。原因是 drizzle-orm 0.45.3 的 `jsonb()` 先把值 `JSON.stringify`，Bun 的 SQL 驱动按参数类型再编码一次，于是**所有**经 Drizzle 写入的 jsonb 值（对象、数组、数字都一样）在库里是“内容为 JSON 文本的 jsonb 字符串”。经 Drizzle 读回来时它会再解析一次，所以应用里一直看不出问题，集成测试也没发现；`->>`、`@>`、索引和 SQL 层的审计检索都会读不到。涉及 4 列：`audit_logs.metadata`、`work_items.payload`、`app_settings.value`、`users.settings`。应用代码里没有用 SQL 读 JSON 字段的地方，所以没有功能受损。
- 实验（测试库的临时表）：直接把原始值交给驱动不行（数字会被当成整数参数，Postgres 拒绝写入 jsonb 列）；先序列化成文本，再在 SQL 里写 `${text}::text::jsonb`，对象、数组、字符串、数字、布尔、嵌套值和更新路径都按真实类型存储，读取时 Bun 返回已解析的 JSON。
- 处理：`packages/db/src/schema/json.ts` 的 `jsonbValue<T>()` 是 customType（SQL 类型仍是 `jsonb`，drizzle-kit 报告无 schema 变更）；四列都改用它；guard 拒绝任何非测试文件从 `drizzle-orm/pg-core` 导入 `jsonb`；迁移 `0002_normalize_jsonb` 把已有的“字符串形态”值改写成其中的 JSON（只处理内容确实是合法 JSON 的行，其余保持原样）；回归测试 `jsonb-storage.test.ts` 用 SQL 直接读存储类型，并核对数据库里的每个 jsonb 列都被覆盖（新增 jsonb 列会让它失败，提醒补测试）。我把测试改回旧编码验证过：6 项里 5 项变红。
- 影响：拉取后需要 `bun run db:migrate`（测试库 `db:migrate:test`）。迁移在空库上什么也不做；你的开发库里 6 行被规范化。Drizzle 1.0 稳定后若修了这个问题，再评估是否改回原生 `jsonb()`（届时仍须先用同样的 SQL 级测试验证）。

## D 设计阶段（2026-10-02）

**D-108 强调色文字与状态色使用单独的可读令牌（补充 D-074、D-092；D4 确认，2026-10-02）**
- 02 第 4.1 节的强调色实底配气泡文字是对的，但把实底色直接当文字色（链接、tinted 按钮、焦点环）不行：深色下蓝 3.11:1、红 4.27:1，tinted 按钮文字浅色下蓝 3.79:1。新增 `--accent-text`（8 色 × 深浅，在所有表面含输入框底色和 16% 强调色调叠加后的表面上不低于 4.7:1）。
- 状态色（红橙绿蓝）原来只有装饰色，红 #FF3B30 作文字只有 3.55:1。新增 `text` 和 `solid` 两组可读值。
- 装饰色只用于渐变、色块和光晕，不用于文字；"颜色不作为状态的唯一标记"落实为：在线用实心点、离开缺一角、离线空心圈，选中会话有色条，开关打开有勾，密码规则用图标加文字。

**D-109 玻璃分三种材质，承载文字的玻璃有不透明度下限（补充 D-017、D-074，改变 02 第 2 节档位的适用范围；D4 确认，2026-10-02）**
- 问题：规格的四档透明度（45% / 62% / 80% / 100%）放在会被任意内容垫在背后的层上（工具栏、输入栏、菜单、弹层）时，文字对比度无法保证。背后是纯黑图片时，浅色清透玻璃上主文字 4.06:1、次要文字 1.50:1、占位文字 1.27:1；标准和着色档的次要文字也不够。
- 决定：`.glass`（只浮在壁纸上，目前只有侧栏，随档位）、`.glass-text`（承载文字，不低于 90%（浅）/ 88%（深），不带强调色调）、`.glass-lite`（放在实底上，不开模糊）。下限由脚本按黑白两个极端反推，留 4.6:1 的余量。清透、标准、着色三档因此只影响侧栏；"不透明"和系统的"减少透明度"对所有玻璃有效。壁纸色块每层不超过 30%（浅）/ 34%（深），这是侧栏玻璃对比度检查的前提。
- 代价和替代：如果你更想要通透感，可以放宽下限，代价是个别背景下文字不达标；也可以让三个档位真正影响工具栏和输入栏，但文字下方要加实底衬层（02 第 4.1 节允许这种做法），观感是"玻璃里有一块不透明的字"。**D4：用户回答"接受"，下限不放宽。**

**D-110 同屏至多 4 个模糊层，模态下让背景去模糊（补充 02 第 2 节的性能规则；D4 确认，2026-10-02）**
- 实测：每条消息的悬停工具条都带模糊时一屏有 19 层；设置面板打开时是 5 层。决定：悬停工具条、审批卡、回到最新按钮用 `glass-lite`；模态层（命令面板、设置、对话框）打开时，被遮住的工具栏和输入栏去掉模糊（它们已不低于 88% 不透明，几乎看不出区别）。控制条和"设计说明"页有实时计数。

**D-111 令牌只有一份数据源，对比度脚本是门槛（Claude）**
- `design/prototype/tools/tokens.mjs` 生成 CSS、驱动 `contrast.mjs`（3000 多组检查，退出码非零即失败）并供"设计说明"页现算表格，文档里的数值由它导出，不手抄。M1b 把令牌移进 `apps/web/src/design` 时保留这个脚本，改令牌必须先过它。
- 检查脚本的三处假设是我在实测中修正的，原因写在脚本注释里：引用块的色调方向要让它离文字色更远；带色调的玻璃只用于侧栏；侧栏占位符放在不低于 72% 的内容色衬底上。
- 像素级审计（`run.sh audit`）补静态检查看不到的东西：它第一次运行就抓到面板被自己的遮罩压暗（静态检查不可能发现），修复后中位对比度全部达标。

**D-112 原型的位置、发布方式、浏览器检查方法与字体内嵌（Claude）**
- 位置 `design/prototype/`（评审用的参考实现，不是产品代码）；以 Artifact 发布，使用普通 HTML 页面，不用 Design 画布类型（它是静态画板，装不下带完整交互的原型）。`biome.json` 只对 `design/**` 关闭四条风格规则。

**D-115 前端栈的版本与兼容结论（M1b 任务 1）**
- **版本**：`apps/web` 的 36 个依赖都是精确版本，没有 beta 或 RC；2026-10-03 逐个对照 npm 的 `latest` 标签，全部相同。`@rolldown/plugin-babel` 0.2.4 的版本号在 1.0 之前，但它是 `@vitejs/plugin-react` 6 文档里接入 React Compiler 的方式，也是 npm 的 latest，不算 beta/RC。版本表见 03 第 2.2 节。
- **一起工作的组合与注意点**（都有运行证据：构建、单元测试、Storybook 构建、E2E）：
  1. Vite 8.3.2 加 `@vitejs/plugin-react` 6.1.1：React Compiler 通过 `@rolldown/plugin-babel` 的 `reactCompilerPreset()` 接入（plugin-react 6 不再内置 Babel）。`vite.config.ts` 和 `vitest.config.ts` 写法相同，Storybook 沿用 `vite.config.ts`，只去掉 TanStack Router 的代码生成插件。

**D-116 CSP 下前端的做法（落实 07 SEC-06）**
- 策略与 SEC-06 逐字相同，定义在 `apps/web/tools/csp.ts`，连同 `Referrer-Policy: no-referrer`、`X-Content-Type-Options: nosniff`、`Cross-Origin-Opener-Policy: same-origin` 和 `Permissions-Policy`；`vite preview` 在 E2E 里发送这些头，生产的 Nginx（M2b）用同样的值。
- 页面没有内联脚本和内联样式：`index.html` 里的 `theme-init.js` 是同源外部脚本，在第一次绘制之前按本机保存的外观给 `<html>` 加属性，并与 `applyToRoot` 保持一致（单元测试比对两者）；Base UI 用 `CSPProvider disableStyleElements`；样式属性只通过 CSSOM 设置（React 的 `style` 和 Motion），不受 `style-src 'self'` 限制。
- **Zod 4 的 JIT 探测违反 CSP**：Zod 会用 `new Function('')` 探测是否能即时编译，没有 `unsafe-eval` 时 Chromium 会发出 `securitypolicyviolation`，Firefox 在控制台报错。处理：`lib/zod-config.ts` 调用 `z.config({ jitless: true })`，并在 `main.tsx`（与 Storybook 的 preview）里最先导入；Rolldown 还要 `output.strictExecutionOrder: true`，否则按 chunk 拆分后配置模块可能晚于创建 schema 的模块执行（我真实遇到过）。
- **验证方式**：每个 E2E 测试都自动断言页面没有记录到任何 `securitypolicyviolation`，也没有意外的控制台错误和页面异常（Firefox、WebKit 的 CSP 拦截会进控制台）。**WebSocket 在 `connect-src 'self'` 下在 Chromium、WebKit、Firefox 都能连接并保持**（`realtime.spec.ts`），所以 SEC-06 里「不能的话显式加上 `wss://`」的备选不需要。Trusted Types 仍留给 M2b（V-08）。

**D-117 外观偏好是设备级的（修改 04 对 `users.settings` 的设想）**
- 主题、强调色、透明度档位、字号、减少动态效果和紧凑侧栏，存在本机 `localStorage`（键 `chatapp.appearance`），**不上传服务器**，退出登录后保留。账号相关的本地数据都放在 `chatapp.u.<userId>.<authEpoch>.*` 之下，退出或会话丢失时整体清掉（D-121）。
- 理由：登录页也要有主题，而且必须在第一次绘制之前生效，不能等接口；一台设备上的外观选择通常就是这台设备的；不增加接口和同步冲突。
- 04 原写 `users.settings` 放「外观、Agent 默认模式、timezoneAuto」，现已改成：该列现在只有 `timezoneAuto`，外观不在其中。将来要跨设备同步，就在 `settings` 里加 `appearance` 键并另开决策，本机值作为未登录时的回退；现在没有这个键，不需要迁移。01 第 4.11 节「范围切换与本地数据」一行补了一句。

**D-118 `PATCH /api/me`（时区与「跟随浏览器」）**
- 请求体是 strict 的 `{expectedMeVersion, timezone?, settings?: {timezoneAuto?}}`，至少改一项，时区用 IANA 名校验。`settings` 按键合并（jsonb 的 `||`，序列化后用 `::text::jsonb`，遵守 D-107），`meVersion` 加 1，条件是当前版本等于 `expectedMeVersion`；版本过期返回 409 `VERSION_CONFLICT`，同一版本上的两个并发写入只有一个成功；响应是新的 Me。逻辑在 `domain/me.ts` 的 `updateMe`，路由很薄；OpenAPI 快照已更新。
- 条件写入本身防止重复生效，所以这个端点不带 `Idempotency-Key`（05 的规则：已有版本号的实体用 `expectedVersion`）。显示名、用户名和简介在 M2 加入。
- 客户端：设置页的时区、「跟随浏览器」开关和 `use-auto-timezone.ts`。`timezoneAuto` 为 true 时，浏览器的时区变化会提交；一旦固定，任何设备都不覆盖（沿用 12 里已有的规则）。E2E 的 `shell.spec.ts` 覆盖默认跟随和固定后不被覆盖，`me-settings.test.ts`（真实 Postgres）覆盖合并、版本冲突、并发和非法输入。

**D-119 密码规则的结构部分移进 `packages/contracts`**
- 长度、过于简单（字符种类少、重复或连续序列）、含账号标识（邮箱前缀、用户名、显示名、产品名，各 4 个字符以上）这几条是纯函数，前后端共用一份（`packages/contracts/src/password-policy.ts`），注册和重置页据此实时列出规则（图标加文字，不只靠颜色）。常见密码表体积大，只留在服务端，由 `domain/password-policy.ts` 传入；表单看不到它，所以「常见密码」只在提交后由服务端拒绝，并显示在字段上。
- 登录从不套用密码策略（沿用 SEC-10）。

**D-120 认证页的一次性令牌、重定向和路由**
- **令牌只在 URL 片段里**：验证邮箱、重置密码和邀请码（`#invite=`）都从 `window.location.hash` 读进内存，随即用 `history.replaceState` 抹掉（不经过路由的 `replace`，那会换掉历史项的 key 并重新挂载页面）。同一个标签页里再粘贴新链接（只触发 `hashchange`）也能读到。
- **路由分组**：`_guest`（未登录者的页面：登录、注册、找回密码、`/check-email`；已登录的人会被送进应用）、`_public`（从邮件链接打开的页面：`/verify-email`、`/reset-password`，登录与否都能用，因为把已登录的人重定向走会丢掉地址里的一次性凭据）、`_app`（需要登录）。路由守卫以 `/api/me` 的回答为准，不看浏览器里存了什么。`/check-email` 是「验证邮件已发出，可以重发」的页面，独立成路由，因为它不带令牌，也不应在片段变化时重新挂载；05 的接口没有变化。设置是应用页面上的一层面板，用 `?settings=<分区>` 表示打开了哪一页。
- **`?redirect=`** 只接受本站内的路径（`/` 开头、不含 `//`、反斜杠、空白）；`https://…`、`//host` 一律丢弃，登录页不会变成开放重定向。

**D-121 客户端会话结束的处理（落实 D-070、SEC-34）**
- 任何「会话没了」的信号（退出登录、API 的 401、WebSocket 的 4401、别的标签页的退出）都走同一条路：取消并清空查询缓存、停止实时连接、清掉账号范围的本地存储、通知其他标签页（BroadcastChannel，外加 localStorage 墓碑，覆盖没有 BroadcastChannel 的情况），然后回到登录页并说明原因。设备级的外观设置保留。
- 同一次丢失可能被多个信号同时报告，只有第一个起作用：用显式的 `active` 标记，而不是查询缓存（探测登录状态时缓存里已经写进了 `null`）。每次重置 `generation` 加 1（`currentGeneration()` 有单元测试，但 M1b 还没有使用者：查询的取消和清空由 TanStack Query 完成；M2 的消息缓存按 03 第 11 节「旧响应直接丢弃」的要求接上它）。
- **4401 要先探测**：在自己这台设备上改密码，服务端也会关掉这台设备的连接（4401）；客户端直接请求一次 `/api/me`（探测的答案不写进查询缓存）：仍是已登录就刷新身份并重新连接；返回 401 才算会话结束、回到登录页；API 不可达时保留会话，让连接退避重试。
- 另一个标签页登录时，本标签页的路由守卫要重新判断（先用 staleTime 0 重新取一次 `/api/me`，再让路由失效）。

**D-124 Passkey 请求体大小（落实 D-078 留给 M1b 的校准，部分）**
- Chromium 的虚拟认证器（CDP `WebAuthn.addVirtualAuthenticator`，平台型、支持常驻凭据与用户验证）下实测：`verify-registration` 请求体 1169 字节，`verify-authentication` 649 字节，只占 128 KiB 解析前限额的 1% 以内，**不需要放宽任何端点**。服务端（`@better-auth/passkey` 1.7.7 默认 `attestationType: "none"`）不要求证明材料，所以真实设备的响应也不会带上厂商证书链。E2E 把这两个数字写进报告，并断言各自小于 16 KiB（限额的八分之一）。
- **没有验证**：真实硬件（Windows Hello、Touch ID、手机跨设备）的实际大小；虚拟认证器只存在于 Chromium，WebKit 与 Firefox 的 Passkey 仪式没有自动化（相应用例按设计跳过）。留给 V-22。

## M2a 实施决定与实验结论（2026-10-03）

以下出自 M2a 的实现和实测，命令、结果和限制见 [PROGRESS](PROGRESS.md) 的 M2a 交接记录。它们是「开始M2a」授权内的工程做法与规格细化，属于我的决定，已于 2026-10-03 你验收 M2a 后生效；改了规格文字的，已同步到 01、04、05、07、08、09。要改动其中任何一条，告诉我，我会新增取代它的记录。

**D-125 个人日志只记个人状态，共享资料走会话主题（细化 04 的 conversation_changes / user_changes，D-082）**
- `user_changes` 只有三种实体：`conversation`（我与这个会话的关系：加入、移出、重入、角色、禁言、通知、免打扰、置顶、隐藏、已读位置）、`message_hidden`（我「仅自己删除」的消息）、`me`（我的资料）。操作是 `upsert` 或 `remove`。
- 名称、简介、设置、人数、归档是**会话的共享资料**：只推进 `conversations.metadata_version`，用会话主题上的 `conversation.changed{conversationId, metadataVersion}` 通知，并出现在 `GET /api/sync/heads` 的 `metadataVersion` 里；成员列表变化推进 `membership_version`，对应 `member.changed`。**不会**为每个成员写一条日志：改一次五百人频道的名字不应该写五百行、推进五百个人的序号。客户端收到提示或在对账里发现版本落后，就重取 `GET /api/conversations/:id`。
- 归档同理：由 `conversations.archived_at` 派生，对每个成员都是归档；`user_conversation_states.state` 的 `archived` 值保留不用（04 原写「active/hidden/archived/removed」，现在只会写 active、hidden、removed）。
- `conversation_changes` 的 `kind` 是 `message_created`、`message_edited`、`message_recalled`、`message_deleted`，只放 id，不放正文。

**D-126 同步游标、日志保留与重置（落实 05 第 4.5 节、D-056）**
- **游标**是 `base64url(载荷).HMAC-SHA256`：密钥是用固定标签从 `BETTER_AUTH_SECRET` 派生的 32 字节（`config.auth.cursorKey`，不增加新密钥）；载荷绑定 actor、authEpoch、restoreEpoch、会话、membershipId、`after`、固定的 `through` 和 10 分钟过期。客户端能原样交回，不能改写。
- **重置**（`resetRequired: true` 加 `baseline`）的条件：`after` 低于日志下限 `change_log_floor`；`after` 大于当前头（客户端比服务器还新，例如恢复过备份）；缺口超过 1000 条；游标无效、过期、不属于本人或本会话、或绑定的 membership 已不是当前这一个（退出重入）。`baseline` 是同一个事务快照里的会话、最新一页消息、`users` 字典、`hasMoreBefore`、`baselineChangeSeq`、`baselineUserSeq`，不会混入两个时间点。个人日志的重置基线是 `me`、全部会话和 `baselineUserSeq`。
- **保留**：两类日志保留 7 天。清理（worker 每 10 分钟）在**同一条语句**里删除过期条目并把下限列推进到被删掉的最大序号：`conversations.change_log_floor`、`users.change_log_floor`（04 原写「记录 earliest_available_seq」，现在记的是已删的最大序号，下限只增不减）。`user_conversation_states` 里 `removed` 的墓碑保留 7 天，覆盖所有仍可能引用它的游标，之后与已过期的会话邀请一起清掉。
- `limit` 限制的是**扫描的日志条数**（最大 100），不是过滤后的消息数，所以全被过滤掉的一页也能推进 `scannedThrough`；`synced` 只能由最后一页的 `through` 推进，响应里的实体版本不是日志位置。响应带 `users` 字典。

**D-127 实时事件、主题和订阅（落实 05 第 4.4 节）**
- 业务事务把提示写进 `work_items(kind='realtime')`，去重键 `mc:{会话}:{changeSeq}`、`cm:{会话}:{metadataVersion}`、`mm:{会话}:{membershipVersion}`、`uc:{用户}:{序号}`；worker 的分发器认领后发布到 Valkey 总线 `events:{环境}`，每个 API 进程的网关据此在进程内扇出；API 在写操作之后发一个 `work.wake`，分发器立即扫描，周期扫描（1 秒）保证最终送达。提示只含 id 和版本（SEC-27），客户端用 HTTP 读内容。
- **事件与主题**：会话主题 `conv:*` 上有 `message.changed`、`conversation.changed`、`member.changed`、`typing`；个人主题 `user:*` 上有 `user.changed` 和 `conversation.removed`；`presence:*` 上有 `presence`。05 原把 `conversation.changed` 放在个人主题，现改到会话主题（见 D-125）。
- **订阅由服务端按当前关系决定**：连接建立时先加载本人的会话订阅，**再**发 `hello`（所以收到 `hello` 之后发生的事都不会漏）；成员关系变化（`user.changed`、`conversation.removed`）让网关立即重算订阅，所以被移出的人在被通知之后不再收到该会话的任何提示（冒烟脚本第 21 步实测）；另有 5 秒的兜底复核：对比 Postgres 里的 `users.user_change_seq` 与连接持有的值，不同就刷新订阅，所以丢了一条提示最多 5 秒内自愈。
- **实测延迟**：本机上，从 `POST` 发出到另一个成员的 WebSocket 收到 `message.changed`，中位约 40 毫秒、最差约 42 毫秒（api、worker 是两个真实进程，经 Postgres 与 Valkey）。这是本机的参考数字，M2b 的验收（p95 < 200 毫秒，含界面）仍要在界面上量。

**D-128 对 05 接口细节的修订**
- **消息列表**返回 `{messages, users, hasMoreBefore, hasMoreAfter}`，取代 `hasMore`：往前翻、往后翻、围绕某条（`aroundSeq`）三种取法都需要分别知道两端还有没有。
- **`changes` 响应**增加 `users` 字典，重置时带 `baseline`（D-126）；`GET /api/sync/heads` 是 `{userChangeSeq, conversations: [{id, membershipId, lastChangeSeq, metadataVersion, membershipVersion, viewerVersion}]}`。
- **`expectedMembershipVersion` 是可选的**：拉人、改成员、封禁、转让都可以带；带了而版本不符返回 409 `VERSION_CONFLICT`，不带就按当前状态执行（这些操作各自在事务里重新校验，条件写入不是它们唯一的保护）。
- **`Idempotency-Key`**：创建会话（`POST /api/conversations`）必须带，同键同参返回原会话（200），首次 201；**创建群邀请链接不带**：明文码只在创建响应里出现一次，重放无法再给出它；重试会多出一条链接，群主和管理员可以撤销，每人每会话最多 10 条有效链接。私信 `POST /api/conversations/dm` 本身幂等（一对人一个会话），新建 201，已有 200。
- **免打扰**是 `mute: {mode: 'off'|'until'|'forever', until?}`，存为 `mute_mode` 加有限的 `muted_until`（04 本来就是这样，D-088）。
- **M3 才有的**：`mentions` 恒为 `[]`（`message_mentions` 表没有建），`attachments` 恒为 `[]`；带 `attachmentIds` 发送返回 422（`reason: 'not_available'`）。

**D-129 系统消息的范围（落实 01 第 4.5 节）**
- 系统消息是真正的消息：`kind='system'`、没有发送者，占用普通的 `seq`，内容放在 `meta.system`（事件类型加涉及的用户 id，不存名字，所以显示的是当前的名字）。
- **群**：加入、退出、被移出、改名、转让群主都记。**频道**：只记改名、被移出、转让群主，**不记加入和退出**——一个活跃的频道里，进出的提示会把真正的对话冲走。**私信**没有系统消息。

**D-130 实时分发用进程内的 Hub，不用 Bun 自带的发布订阅**
- `realtime/hub.ts` 是普通的 Map：主题到连接集合、连接到主题集合。理由：每个连接的订阅会随成员关系变化而增删，需要按主题统计关注者并在授权失效时立刻移除；网关的授权与投影状态本来就在连接对象上；规模目标是 500 个连接，不需要引擎级的广播。Hub 不依赖 Bun，可以单独做单元测试，需要换运行时时不受影响。

**D-131 在线状态放在 Valkey（落实 03 第 5.6 节、01 第 4.7 节）**
- 每人一个 HASH：`c:{连接}` 为 `状态|到期时间`，`f:{连接}` 为当前查看的会话与是否在前台；另有一个全局的到期 ZSET 供清扫使用。写入、续期、移除都是原子的 Lua 脚本，返回「之前、之后」的聚合状态，只在聚合状态变化时才发 `presence`。
- 聚合规则：有任何一个连接是活跃的就 `online`，连接都空闲就 `away`，没有连接就 `offline`（所以开两个标签页、关掉一个，对方看到的仍是在线，L-18）。空闲/活跃由客户端用 `presence.activity` 报告。
- 连接 90 秒不续期视为已死（心跳 25 秒一次）；worker 每 30 秒清扫一遍，对被清掉的人同样发 `offline`；**最后一个连接消失时写 `users.last_seen_at`**（正常关闭或被清扫），`presence` 事件只含 `userId`、`status`、`lastSeenAt`，没有任何「是不是我」之类的字段（L-17）。
- `presence.watch` 整体替换关注集合，立即回 `presence.snapshot`（离线的人带上最后在线时间）。

**D-132 权限边界的几处取舍（落实 01 第 5 节、07 SEC-02）**
- **站点管理员**对自己不是成员的频道和群：可以查看元数据、改设置、移出/禁言/封禁、归档和恢复、撤销任何邀请链接、删除别人的消息（写审计、不含内容）；**不能**读消息、发消息、拉人、建邀请链接、任免管理员、转让。私信和 Agent 会话对非成员（含站点管理员）一律 404。
- **读不到的原因要区分**：频道是公开的，非成员读消息、读成员改动日志返回 403（加入才能读）；群、私信、Agent 会话的非成员一律 404，**且回答与「根本没有这个会话」逐字相同**。
- **按消息 id 的接口同理**：陌生人对一条消息 id 做编辑、撤回、隐藏、删除，对不可见的会话与对不存在的消息给出同样的 404「Message not found」。**这是新写的权限矩阵测试发现的一个真问题**：之前这四个接口对陌生人说「Conversation not found」、对不存在的消息说「Message not found」，等于告诉对方这个 id 属于一个私有会话；已在 `domain/messages.ts` 统一（`enforceView`）。
- **改成员前先看成员列表的权限**：`PATCH /members/:userId` 先检查「能不能看到成员列表」，再回答「这个人不在里面」，所以只有看得到名单的人才能知道某人在不在。
- **私信**：一对人一个（`dm_pairs`）；发起人立刻看到，对方的那一份一开始是隐藏的，第一条消息到达时自动取消隐藏；再次打开已有的私信，会为发起人取消隐藏；私信不计入每人 200 个会话的上限。
- 群主不能直接退出（409 `owner_must_transfer`），除非只剩他一个：那时会话在同一事务里归档，群主仍是它的管理者（04）。

**D-133 个人资料的规则（落实 01 第 4.3 节、L-19、L-24）**
- 显示名不能是保留词（助手的显示名、「系统」等，按 NFKC 和去空白后比较）；用户名与注册时规则相同，**30 天内只能改一次**，放弃的旧用户名保留 30 天（`username_reservations`），别人不能抢，本人可以改回；简介最长 200 个字符。

- 历史消息按账号归属，不按用户名：改名之后别人拿到旧用户名，也撤回不了、删不了原来那个人的消息（L-20）。

**D-134 V-14 的结论：怎样模拟断线（落实 08 第 3 节第 3 条）**
- **实验**（Playwright 1.63，Chromium 1243、WebKit 2359、Firefox 1543 的构建，对着真实的应用栈）：`context.setOffline(true)` 之后——Chromium：已经建立的 WebSocket 不关闭，但它的流量被扣住，ping 的 pong 要等恢复在线才到；新建的 WebSocket 以 1006 失败。WebKit：已建立的连接完全不受影响（离线时 ping 照样得到 pong），**连新建的 WebSocket 也照常打开**。Firefox：已建立的连接不受影响，新建的以 1006 失败。三个引擎的 `fetch` 都会失败。所以 **`setOffline` 在任何一个引擎里都不能断开已经建立的 WebSocket**。
- **采用**：HTTP 用 `context.setOffline`；WebSocket 用 `page.routeWebSocket`（`apps/web/e2e/support/network.ts` 的 `controlNetwork`）：离线时从页面一侧关闭已建立的连接（关闭码 3001）、拒绝所有重连尝试，恢复在线后放行下一次尝试。三个引擎的行为一致；`apps/web/e2e/network.spec.ts` 对真实应用验证了「连接被断开、客户端按退避不停重试、网络恢复后自己重连成功」。它必须在页面打开第一个 WebSocket 之前安装。
- **服务端一侧**：`POST /api/test/realtime/disconnect`（仅 `APP_ENV=test`）从服务端关闭连接，用来测服务器重启、依赖丢失这类由服务端发起的断开；已有实时测试覆盖。
- 限制：`routeWebSocket` 只能用 3000–4999 的关闭码，真实断网时浏览器看到的 1006 发不出来；客户端对这两类码的处理相同（除 4401/4403 外都重连）。

**D-137 网关的订阅状态：每人一份，一次一个读取，集合与序号一起更新（修复复核 R2，细化 D-127、03 第 5.7 节）**
- **问题**：复核把一次成员快照的返回拖到「移出」之后，迟到的旧结果无条件覆盖了订阅集合，同时用 `Math.max` 保留了较新的序号，于是 5 秒兜底发现「序号没有落后」，永远不会纠正：被移出的人继续收到 `message.changed`（只有编号，没有正文）。根因有两个：订阅集合和它所对应的序号是分开更新的；同一个人的多次读取可以并发，结果乱序应用。
- **做法**（`realtime/gateway.ts`）：每个人一条 `Following{conversations, seq, reading, again}`，该人的全部连接共用。读取「单飞」：读取进行中又来了新的提示，只置 `again`，读完立即重读，**所以被采用的读数一定开始于最新提示之后**。`#apply` 在同一个同步步骤里替换集合与序号，并推给这个人的所有连接。读取失败不改动任何东西，由 5 秒兜底补上；读取期间该人的最后一个连接关闭，读数被丢弃，不会交给他的下一个连接。`conversation.removed` 的提示只有 `userChangeSeq` 大于已掌握的序号时才立刻停止订阅（已经过时的移除提示，例如那个人已经重新加入，不会把会话再拿走），无论是否立即停止都会安排一次读取；`user.changed` 不按序号过滤（复核给的 `userChangeSeq:1` 提示也要触发读取）。连接建立时先登记，等到一份**开始于连接打开之后**的读数应用了，才发 `hello`。
- **测试**：`apps/server/test/realtime/subscription-races.test.ts`（8 个）。`test/support/readings.ts` 的 `HeldReadings` 在数据库读取的边界上放屏障，由测试决定哪次读数先、哪次后交回：移出之前取的读数在移出之后才交回、查询乱序、移出后再加入、过时的移除提示、读取失败、人已离开、5 秒兜底在旧读数在途时仍能纠正（核对的是它每 5 秒触发一次，而不是等多久）、请求合并、`hello` 只在新读数之后。「从不听到」一类的断言用顺序哨兵（之后发的一条消息收得到，而被排除的不曾出现），不靠多等一会儿；复核给的原始复现脚本现在 3/3 通过。**变异检查**（`mutate-r2.sh`，改完即还原）：去掉「`again` 之后重读」，4 个测试失败；去掉移除提示的序号判断，1 个失败；去掉「该人已离开则丢弃读数」，1 个失败。

**D-138 幂等重放服从当前授权和历史水位（修复复核 R1，落实 D-035、INV-09、AT-13）**
- **问题**：Bob 在群里发消息，退出后重新加入，水位前移；用原 `clientId` 和原请求体重发，收到 200 和原正文。重放分支只检查当前成员身份，没有检查原消息是否在新的 `visible_from_seq` 之上；`projectMessages` 也只对引用目标做水位判断，不过滤传进来的主消息行。影响是重新入群后取回自己的旧消息，不是读取别人的历史。
- **做法**（`domain/messages.ts`）：（1）重放分支在比对请求指纹之后、投影之前，要求 `existing.seq > member.visibleFromSeq`，否则 404「Message not found」，与读取同一条旧消息的回答逐字相同；（2）`projectMessages` 对传入的主消息行本身也按观察者的水位过滤，任何用别的键（比如 `clientId`）找到一行的调用者，都不能把水位之前的内容交给观察者。同一成员关系内的重试仍然幂等（200 和同一条消息，不论隔多久、中间别人是否发言）；同一个 `clientId` 不会再写第二条（它只对应水位之前的那一条），要发新内容就用新的 `clientId`；异参仍是 409，且不透露那条消息的任何内容。
- **测试**：`apps/server/test/integration/message-replay.test.ts`（8 个）：同一关系内的重试、别的发送者用同一个 clientId 写自己的、退出后重入、被移出后重入、封禁解封再加入、频道重新加入、凭邀请链接回来、异参 409，每一项重放后都核对：回答是 404 且不含原文和原 id，旧消息按 id 读取、列表、changes 里都没有，编辑、撤回、仅自己删除都是 404，数据库里那一行丝毫未动；另有一个直接测 `projectMessages` 的用例。**变异检查**（`mutate-r1.sh`，改完即还原）：两层都去掉，5 个测试失败（其中 4 个是请求层面的重放用例）；只去掉投影的过滤，1 个（直接测投影的）失败；只去掉重放分支自己的判断，没有测试失败，因为投影会给出同样的 404，所以那一层在外部观察不到不同的行为，是第二道防线。

**D-139 总线重连之后立即复核（落实 03 第 5.7 节、AT-02）**

- 总线不在的时候，撤权靠网关自己的 5 秒复核（加 1 秒容差）：`test/fault/at-02.test.ts` 在隔离实例里真的停掉 Valkey，验证被移出的人和被撤销的会话仍在复核时限内结束订阅和连接，总线回来之后没有任何泄露，以及回来之后立即复核而不是等下一个 tick。

**D-141 故障实例的核验与重建（落实 D-085、AT-34）**

**D-143 E2E：先等页面到位再量、再填（WebKit 失败与「找回密码」偶发失败的根因，没有放宽任何断言）**
- **WebKit 侧栏宽度测得 340.000061，断言要求 ≤ 340**：入场动画（`inspector-in`，transform）期间，Chromium 和 WebKit 的 `getBoundingClientRect` 宽度有 ±2⁻¹⁴ 的抖动；按帧探测三个引擎得到这个证据。原用例在动画期间量，WebKit 约 1/8 概率失败。**修复**：`e2e/support/ui.ts` 的 `animationsFinished(locator)`，等元素的全部动画 `finished` 之后再量；断言不变（真正的横向溢出仍会被抓到），没有加容差；修复后同一用例在 WebKit 连续 16 次通过。
- **Chromium 的「找回密码」冒烟用例偶发失败（M2a 第一轮就出现过，当时记为偶发、没找到根因）**：用 Playwright 追踪确认是**用例自己的同步缺陷**。点「忘记密码？」之后，地址栏先变成 `/forgot-password`，而新页面的脚本还在下载，旧登录页仍在屏幕上；登录页也有「邮箱」框，`getByLabel('邮箱').fill()` 填进了**即将被替换的旧表单**，8 毫秒后新页面挂载，把值带走，随后提交的是空表单（出现「请输入完整的邮箱地址」）。追踪里两个输入框的 React `useId` 不同（`_r_2_` 变成 `_r_5_`），网络里只有一次文档加载，证实是客户端路由切换而不是整页重载。**修复**：点击之后先等新页面的标题「找回密码」出现再填。**证明**：临时用例把目标页的脚本拖慢 600 毫秒让竞争必现，旧写法在 Chromium 与 WebKit 都必然失败，新写法都通过（临时用例已删除）；修复后该用例在 Chromium 29 次、WebKit 22 次、Firefox 13 次全部通过（反复运行受管理员登录限流的限制，每批不超过 7 次）。点链接后紧接着填同名字段的写法已全部检查过：另外两处「去登录」之前的页面没有「邮箱」字段，不会竞争。这是路由在新页面就绪前保留旧页面的正常行为，没有改产品代码。

**D-144 时间线的虚拟列表用 virtua 0.52.10，取代 react-virtuoso 4.18.16（V-09 结论；改 03、02、00）**
- **实验**：10,000 条合成消息（固定种子，每次完全相同；1 到 6 行中英文混排；18% 带图片，图片在行挂载 150 到 1050 毫秒后才出现；另有「尺寸已知」一组，图片框先按宽高占位，对应 M3 的附件）。场景：初始停在底部、底部流式回复、连续向上加载 3 页、中间阅读时上方图片加载、翻上去时流式回复与来新消息、在一万条里跳到某条、一万条快速滚动。判据：视口顶端第一条可见消息每帧位移不超过 1.5 px，取**绘制前读数**（在列表自己的观察者之后创建一个 ResizeObserver，在同一帧布局之后、绘制之前读；核实过三个引擎按创建顺序调用回调），也就是用户看到的那一帧。
- **react-virtuoso 4.18.16 不够用**：向上加载历史（聊天里最常见的动作）每次都有一帧错位，只有文字时 44 到 276 px，带图片的行最多 732 px，三个引擎都有；视口上方的行变高时它不补偿，阅读位置被推走 117 到 319 px，跳转目标可能被推出视口（尺寸未知时 seq 3000 最后在 986 px，被推出 800 px 高的视口）。原因是它测量行高的 ResizeObserver 回调默认推迟到下一帧；唯一的开关 `skipAnimationFrameInResizeObserver` 修好了 Chromium 和 WebKit，修不好 Firefox（256/276/72 px），还让 WebKit 每次加载页面都报一次页面异常。它的聊天专用组件 `@virtuoso.dev/message-list` 是商业许可，不考虑；`@tanstack/react-virtual` 没有测。
- **virtua 0.52.10**（npm `latest`，2026-09-29，MIT，无依赖）：向上加载历史三个引擎都是 0 px；上方的行变高除 Firefox 一次 154 px 外都是 0；图片尺寸已知时全部 33 个检查通过（页面 CSP 的基线与开启 Trusted Types 各一遍）；一万条快速滚动同样流畅（帧间隔 p95 17 到 25 ms，没有超过 50 ms 的帧，最差可见覆盖率 100%，DOM 里 15 行）；体积 gzip 5.4 kB（react-virtuoso 20.4 kB）。代价：底部跟随（流式回复、新消息、图片）要约 10 行应用代码；WebKit 每页一次「ResizeObserver loop completed with undelivered notifications.」页面异常（规范定义的通知，被跳过的尺寸变化下一帧照常送达，绘制前读数里没有因此产生的位移；试过的几种接法都只是挪位置，没有一种能避开）。
- **接法**：消息 id 作 key；`shift` 只在前插时为真；挂载时 `scrollToIndex(最后一条, { align: 'end' })`；距底 8 px 以内算「在底部」，在底部时用 ResizeObserver 观察内容高度并重新贴底；离顶 600 px 内加载更早一页。**M3 的图片和附件行必须在字节到达前按已知宽高占位**，否则顶端那一行自己变高时会被多补偿（实测 −151 px），视口里的行变高也会推动跳转目标（355 px）；附件处理完成之前宽高未知的情况，M3 设计时处理。它还是 0.x：锁精确版本，Renovate 的升级必须跑完时间线 E2E 与性能用例才能合并。WebKit 的那句页面异常只在 E2E 夹具里精确放行（只放这一句），M7 接 Sentry 时同样过滤。
- **没有验证**：真机触控板的惯性滚动、macOS Safari 真机、读屏器在虚拟列表下的表现（并入 V-22）。

**D-145 Markdown 渲染管线定稿（V-08 结论，落实 D-047；改 03）**
- **版本**：streamdown 2.7.0（2026-09-30）、shiki 4.5.0（2026-10-01）、`@streamdown/code` 2.0.0、`@streamdown/cjk` 1.0.4（都是 2026-09-30，Apache-2.0，`@streamdown/code` 依赖 `shiki ^4.4.3`，所以只有一份 shiki）。03 里的 2.6.0 与 4.4.3 是写规格时的版本，2026-10-04 核对 npm 的 `latest` 已是上面这些。（**后来**：代码高亮不再用 `@streamdown/code`，改为自己的插件，见 D-168。）
- **配置**（用户消息与 M4 的 Agent 输出共用一个 `SafeMarkdown`）：不允许原始 HTML（`rehypePlugins` 只有 `sanitize`，没有 `rehype-raw`，HTML 节点按文字显示，所以 `<img onerror>`、`<script>`、`<svg onload>`、`<iframe srcdoc>` 都是文字）；数学公式与 Mermaid 不开（streamdown 里唯一的 `dangerouslySetInnerHTML` 在 Mermaid 组件里，不传插件就不会渲染，` ```mermaid ` 当普通代码块高亮）；链接只留绝对的 `http`、`https`、`mailto`，统一 `rel="noopener noreferrer"`，`javascript:`（含大小写混写、实体编码）、`data:`、相对路径、`//` 开头、`file:`、`tel:` 都丢掉链接只留文字，streamdown 默认的「链接安全确认」关闭；Markdown 图片一律改成链接（`img-src` 只允许 self、data、blob，外链图片会被拦并报违规），`data:` 图片丢掉；代码高亮用 shiki 的 JavaScript 正则引擎（不用 WebAssembly，`script-src 'self'` 不允许）加 CSS 变量主题，颜色以 CSS 自定义属性设置，没有 `style=""` 标记，语言包按需加载为独立 chunk；自动识别的链接在汉字、假名、谚文、全角符号处截断（`@streamdown/cjk` 只在全角标点处截断，单用它有 4 个样例不对：汉字紧跟路径或域名、假名与谚文、`www.` 后接汉字，所以加一个自写的 remark 插件）。
- **在 spike 的基础上收紧为 01 第 4.5 节的子集**：允许的节点只有段落、文字、粗体、斜体、删除线、行内代码、代码块、链接、列表、引用、换行，其余（标题、表格、任务列表、脚注、分隔线、定义、引用式链接与图片）按原文文字显示，默认拒绝，新版本的插件引入新节点也不会意外渲染；Shift+Enter 的单个换行显示为换行。
- **结果**：最终 CSP 下 29 个样例全部通过（三个引擎），0 个 CSP 违规、0 个控制台错误、0 个页面异常；31 个代码 token 里 28 个的颜色是 `var(--shiki-*)`、没有十六进制色；11 个请求全部同源；没有加载 WebAssembly；每 16 毫秒追加 7 个字符的流式渲染下表格、代码块、链接正确。
- **体积**：Markdown chunk 793 kB（gzip 253 kB；含 shiki 核心与正则引擎、streamdown 默认插件带进来的 parse5、marked、实体表），懒加载，登录页的构建产物里没有它。
- 正式实现的 E2E 要覆盖：L-11（`<img src=x onerror=…>` 显示为文字、不执行、零违规）、含命名实体（如 `&lt;`）的消息（守住 D-146 的解析插件）、CJK 自动链接截断、`javascript:` 链接被丢掉、代码高亮颜色来自 CSS 变量。

**D-146 页面 CSP 开启 Trusted Types（V-06 并入 V-08 的结论；改 SEC-06）**
- 页面策略在 SEC-06 现有策略末尾追加 `; require-trusted-types-for 'script'; trusted-types 'none'`（不允许创建任何策略）。`apps/web/tools/csp.ts` 是唯一来源，`vite preview` 照发，所以全部 E2E 都在这个策略下运行；`infra/nginx/security-headers.conf` 与它逐字一致，由单元测试比对（进 `bun run check`）。开发服务器（5173）、Storybook、Vitest 不发这个头。
- **依据**：三个引擎都执行（探针页给 `innerHTML` 赋值，三个引擎都抛 `TypeError` 并恰好报告一条 `require-trusted-types-for` 违规）；M2a 的应用（登录、外壳、设置、⌘K、WebSocket）在这个策略下三个引擎零违规。**一个前提**：micromark 解码命名实体用的 `decode-named-character-reference` 1.3.0，在 `browser` 导出条件下取 `index.dom.js`，靠 `element.innerHTML = '&name;'` 解码，会被拦下并让整个 Markdown 渲染崩溃（三个引擎都崩溃，页面空白）；它的默认导出 `index.js` 用 `character-entities` 查表，没有 DOM 写入。构建时用一个 10 行的 Vite `resolveId` 插件把它解析到查表版（Markdown chunk 多 12.9 kB gzip），之后 29/29 个样例零违规。
- 剩下的写入点（streamdown 的 Mermaid、React DOM 对 `dangerouslySetInnerHTML` 的实现）都在我们的配置不会走到的路径上；`apps/web` 的源码、E2E、工具里没有写入点（grep 过，SEC-05 与 `guard` 已经禁止）。以后需要写入点的功能要另立决定、建一个只做一件事的命名策略：M6 的 Service Worker 注册（`navigator.serviceWorker.register` 要求 TrustedScriptURL）、任何 `new Worker(url)`；M7 的 Sentry SDK 也要在这个策略下验证。

**D-147 edge：本地用生产站点配置提供构建产物，API 是独立的测试环境进程，开发值不变（落实 D-045、D-099 的验证要求；改 09、10）**
- 服务端要求非 GET 请求和 WebSocket 握手的 `Origin` 等于 `APP_ORIGIN`（SEC-13），Cookie 是否 Secure、是否带 `__Host-` 前缀由 `APP_ORIGIN` 是否为 https 决定（D-100），Passkey 的 RP ID 是它的主机名。所以让 edge 转发到开发 API（来源不等，所有写入 403）和让 API 接受多个来源（削弱 SEC-13，且 `localhost` 与 `chat.localhost` 的 Passkey 不通用）都不可行。**做法**：edge 有自己的 API 进程，沿用 `scripts/e2e-stack.ts`（测试环境、测试库、真实的 api 与 worker 子进程），用它已有的环境变量覆盖 `E2E_APP_ORIGIN=https://chat.localhost:8443`、`E2E_API_PORT=3104`。spike 就是这样跑通的（`__Host-` Cookie、`wss://`、匿名连接 4401 都实测过）。开发栈（5173/3100、开发库、`events:development`）与 edge 栈（8443/3104、测试库、`events:test`）完全分开，`.env.local` 不动；edge 栈与 `test:e2e`、`test:integration` 一样独占测试库，不能同时运行。
- `bun run edge:up` / `edge:down` 只管网关：构建、组装 webroot、本地 CA 与 `chat.localhost` 叶证书（openssl，只在 `.test-runs/edge/certs/`，权限 600，不导入任何信任库，浏览器测试用 `ignoreHTTPSErrors`）、生成上游配置、`docker compose up -d --wait`、`nginx -t`。`down` 只删 `chatapp-edge` 的容器和网络，不 prune，不按名字前缀删除（D-085 的做法）。镜像锁 `nginx:1.28.3-alpine@sha256:a8b39bd9cf0f83869a2162827a0caf6137ddf759d50a171451b335cecc87d236`（D-045：与服务器同系列、精确版本）；它确实是 1.28 系列的最后一版，但 **1.28 上游已于 2026-04-14 停止安全支持**，两个 2026 年的严重漏洞（CVE-2026-42533 `map` 用正则捕获、CVE-2026-42945 `rewrite` 用未命名捕获）只在 1.30.x、1.31.x 修复；我们的站点配置和镜像自带的配置都没有用 `map`、`rewrite`、`charset`（`nginx -T` 核对过），同一份配置在 nginx 1.30.4 上 `nginx -t` 也通过。**服务器与 edge 何时升 1.30 不是我能替你决定的**（服务器是多站点共用的），交接时作为选择交给你，不编号。（**后来**：用户 2026-10-04 决定改用 1.30，见 D-169。）
- edge 测试套件在本机运行（`bun run test:e2e -- --config=playwright.edge.config.ts`），验证 AT-19（每类 location 与网关自己回的错误响应的安全头）、AT-26/AT-27 的网关部分（超限与异常请求在网关被拒、日志里没有哨兵）、经 edge 的应用与 Passkey；**CI 不跑它**（CI 的 Linux Docker 没有 Docker Desktop 的转发，拓扑与本机和生产都不同），CI 只校验配置（`compose config` 与锁定镜像里的 `nginx -t`）。经 edge 的所有浏览器请求在 API 看来来自同一个地址，套件的注册与登录次数有写死的上限，遇到第一个 429 就整体停止。

**D-148 每个 E2E 的零违规断言覆盖所有上下文，并证明页面确实在策略下运行（加强 D-122）**
- M1b 的探针只装在默认 `page` 夹具上：`newContext()` 建的第二个人、第二台设备没有探针，违规只在测试结束时读 `window.__csp`，中途关闭的页面读不到，夹具也不检查页面是否真的带着策略（预览服务器少发一个头，零违规也会「通过」）。**做法**：每个测试登记它用到的全部上下文（`newContext()` 取不到登记表就抛错），每个上下文装同一套检查：`addInitScript` 探针（违规同时写进控制台通道）、`console`、`weberror`、`response` 监听；文档响应（本站来源、非 `/api/`、状态 2xx 或 404 的导航）的 `content-security-policy` 必须逐字等于 `tools/csp.ts`；测试结束时与 `window.__csp` 取并集再断言为空。
- **按测试的放行**：`allowConsole(pattern, reason, engines?)` 只对调用它的测试、只在列出的引擎上生效，且必须至少匹配过一次，否则测试失败，所以放行不会悄悄留下；全局白名单不变。WebKit 的 `ResizeObserver loop completed with undelivered notifications.` 是唯一的页面异常放行，精确匹配并把次数写进测试注解（D-144）。Trusted Types 金丝雀（三个引擎里给 `innerHTML` 赋值抛 `TypeError` 并恰好一条违规）显式认领这条预期中的违规，认领不到就失败。放弃的方案：策略里加 `report-to`（让 E2E 的策略与生产不再逐字相同）、用 CDP 收集（只有 Chromium 有）。

**D-149 「滚动流畅」与收发延迟的量法与阈值（落实 M2b 验收第 2、3 条）**
- 夹具：E2E 启动时（API 启动之前）用 domain 的函数建一个一万条消息的群「性能 10k」（固定种子，逐字可重现：1 到 6 行中英文混排，10% 列表、5% 代码块、10% 链接、3% 回复、1% 长消息；发送者成段交替、时间跨 30 天、偶有超过 1 小时的间隔）；两条确定的规则：seq 10,000 回复 seq 3,000，seq 9,901 到 10,000 的发送者只有 `perf_a` 与 `perf_c`（`perf_b` 的已读设为 9,900，打开后的未读分隔位置因此确定）。探针由测试代码注入，应用里没有测量钩子（唯一的例外是时间线根元素上一个只读的 `data-loaded-count`）。
- 阈值（现在定下；以后要改须新增决定，不能为了通过而放宽，同 D-086）：**T1 内存中快速滚动**：测量期间没有加载请求；帧间隔 p50 ≤ 17.5 ms、p95 ≤ 25 ms；没有 ≥ 100 ms 的长动画帧，≥ 50 ms 的不超过帧数的 1%；每帧视口覆盖率 ≥ 0.9。**T2 一路加载到最早**：每一次向上加载与裁剪的锚点位移 ≤ 1.5 px（至少 95 次加载）；没有 ≥ 200 ms 的长动画帧；任何时刻 `[data-seq]` ≤ 150、元素 ≤ 8,000、窗口 ≤ 2,000 条；零控制台错误。**T3 跳转与回到最新**：引用跳转 1.8 秒内位移 ≤ 1.5 px，回到最新后离底 ≤ 2 px。**T4 打开到未读**：「以下为新消息」在视口内、紧挨 seq 9,901，未读徽标在读到底之前一直是 100。**收发延迟**：A、B 两个上下文在同一个浏览器里，40 个样本，p95 < 200 ms（含 HTTP、事务、派发、Valkey、网关、客户端补拉与渲染，不含 B 页面的绘制合成，最多差一帧）。
- 与渲染速度有关的断言（帧间隔、长动画帧、覆盖率、延迟）只在本机断言，CI 里照样测量并把数字写进附件和作业摘要（共享 runner 的 CPU 不受控）；确定性的断言（锚点位移、DOM 与窗口上限、T3/T4、零错误）在任何环境都断言。每个 T 是独立的串行用例，T2 超时 10 分钟。

**D-150 客户端一致性落在 TanStack Query 上的方式（落实 05 第 4.5 节、D-056、D-082；改 03 第 11 节）**
- **Query 只当存储和订阅机制，不是同步协议**。协议状态（observed、synced、在途、重试）在 `apps/web/src/lib/sync/engine.ts`，与 React 无关、可单元测试；Query 里的数据只经 `merge.ts` 的纯函数写入，规则：Message 按 `changeSeq` 更大才替换，墓碑记进 `gone` 防止更早发出、更晚到达的页把它带回来；会话共享资料按 `metadataVersion`、本人关系按 `viewerVersion`、计数按 `lastChangeSeq`、预览按复合版本（两个分量都不小且至少一个更大才替换，不可比就隐藏预览并重取）、用户按 `profileVersion`、`me` 按 `meVersion`（`null` 与身份变化一律替换，同一身份才比版本）；未读数不存储，渲染时现算。没变的对象原样返回。
- **键带账号命名空间**（D-070）：`['u', userId, authEpoch, …]`，时间线的键再带 `membershipId`。受同步管理的键（会话索引、用户字典、时间线窗口）`staleTime`、`gcTime` 都是无穷大、不自动重取、**从不失效**（失效会整对象替换，违反 D-082），淘汰由引擎显式 `removeQueries`；普通键（成员分页、封禁、邀请、发现页、已归档）按提示失效重取。
- **observed 与 synced 分离**：observed 只由提示、对账和写操作的回答抬高；synced 只由补发抬高（每页之后 `max(synced, scannedThrough)`，最后一页之后 `max(synced, through)`）；首次载入时 synced 取**发请求之前**已知的 `lastChangeSeq`（先取水位、后取页，否则会漏）。补发：`GET /changes?after=synced&limit=100` 之后只用游标翻页；同一会话一次一个，全局最多 2 个，目标 50 毫秒批处理（前沿加尾沿）；`resetRequired` 时丢弃旧窗口、按 baseline 重建，待发项保留（有 `clientId`，重试幂等）。对账：前台每 24 到 30 秒（`30 s × (0.8 + 0.2 × random)`，上限 30 秒，加一次补发仍在 35 秒内，满足 AT-01；对称的 ±20% 会到 36 秒），收到 `hello`、回到前台、`online` 时立即做，`GET /sync/heads` 之后只对落后的会话排队，不凭缺席删除。
- **请求边界检查**：每个请求发起时捕获账号、`authEpoch`、`restoreEpoch`、本地重置世代和会话的 `membershipId`、会话世代；回答回来、合并之前任何一个变了就静默丢弃。会话世代在重置、离开、重新加入、遗忘时加一，并取消在途请求。
- **遗忘一个会话的唯一入口** `forgetConversation`，只在四种情况下触发：自己 `leave` 成功；更新的移除墓碑；个人日志重置的快照里没有它；对当前成员关系的内容请求回答 404 `NOT_FOUND` 或 403 `FORBIDDEN` 且原因是 `not_member`。别的 403（`requires_admin`、`silenced`、`WINDOW_EXPIRED` 等）只影响那一次操作。成员关系 id 变了（重新加入）时，旧关系下的全部键在同一个同步步骤里删除。`conversation.removed` 提示本身只促使对账，不直接删除（05 第 4.5 节）。
- **在本机改密码换了登录世代**（只改 `authEpoch`、不改 `meVersion`）：`mergeMe` 把它当作身份变化接受，引擎执行 `switchScope`：停止、删旧世代前缀下的键、清旧范围的本地存储、世代加一、用新范围重新首载，用户不被踢出（D-121 的延伸）。
- **后台同步的请求预算**（避免活跃会话打满账号共用的 `api.user` 每分钟 600 次）：引擎发起的所有请求共用一个令牌桶（每秒 4 次、突发 20 次）；窗口补发与无窗口会话的重取各自相隔至少 2 秒，落后的会话达到 10 个就改用一次列表请求；已读 `POST` 同会话单飞、两次开始相隔至少 1 秒、尾沿带最新的 seq；个人补发相隔至少 500 毫秒；任何请求得到 429 或 503 后，后台同步暂停到 `Retry-After`；用户发起的请求不排在后面。

**D-151 时间线窗口模型**
- 每个会话（每个 `membershipId`）一个连续窗口，最多 2,000 条，LRU 保留最近打开的 8 个会话的窗口（当前会话不淘汰；被淘汰的会话以后按「首次载入」处理）。窗口「贴着最新」或「脱离最新」（跳转、打开到很早的未读、向上翻超过 2,000 条之后）；脱离时新消息不追加、只计数。页大小：首页 50，之后向上、向下每页 100。超过上限的裁剪放在**下一次提交**里（先加载、后裁剪，因为 virtua 的 `shift` 只该在改动开头的那次提交里为真）。跳转用 `aroundSeq`，回答里没有目标（不可见或已隐藏）就提示「这条消息无法显示」、窗口不变；自己发送时脱离最新的先回到最新。

**D-152 已读推进与未读分隔**
- 已读只在三个都能精确判断的条件同时成立并持续 400 毫秒后推进：页面可见、窗口贴着最新、列表在底部（`offset + viewportSize ≥ scrollSize − 8`，挂载与每次数据或尺寸变化之后在 layout effect 里重算，内容不足一屏时不会有滚动事件）；推进到窗口里最新一条**服务器消息**的 seq（待发项不算），只增不减，客户端先记 `pendingRead`，徽标立刻归零；往上翻着看历史不推进（01 第 4.7 节）。**未读分隔**定位在「锚点 seq」上而不是行索引，它是那条消息上方的装饰、不是列表项：打开会话时取当时的 `me.lastReadSeq`，装饰在第一条 `seq > 锚点` 且不是自己发的消息上；会话一直打开时锚点不动（推进已读不会让分隔消失），页面从后台回到前台且期间有未读时换成此刻的 `lastReadSeq`。打开时有未读：第一条未读在最新一页里就停在分隔处，否则用 `aroundSeq = lastReadSeq + 1` 载入脱离最新的窗口再停在分隔处。

**D-153 时间线的键盘、读屏与焦点（落实 AT-21、02 第 7 节）**
- 容器是 `role="feed"`，每条消息是 `role="article"`，名称含发送者与时间，时间分隔、未读分隔、分组都是视觉装饰（`aria-hidden`）；feed 里只放消息、零高度的幽灵项和没有角色的起点项。**「载入更早消息」按钮放在 feed 之外**（时间线区域顶部，`aria-controls`、`aria-busy`）：axe 的 `aria-required-children` 只允许 feed 里有 article，放在里面一定报违规，放在列表第 0 项还会让 virtua 的前插错配交界处的尺寸缓存。
- **漫游 tabindex**：只有一个「当前行」可聚焦，按**消息 id** 记录，不按索引。焦点在 feed 里时当前行就是焦点所在的那条；焦点不在 feed 里时当前行跟着视口走（打开、跳转、回到最新之后和每次滚动结束，取顶边落在视口内的第一条 article），所以用 Tab 进入时间线不会把视口拉到最新一条，已读也不会因此被推进。virtua 的 `keepMounted` 保住当前行和含焦点的行，滚出视口也不会被卸载；移除当前行（仅自己删除、墓碑、裁剪、重置）时当前行改为相邻的一条，焦点在被移除的行里就同一次提交里移到新的当前行，绝不落到 `<body>`。程序移动焦点一律 `focus({ preventScroll: true })`，滚动只由 virtua 做。
- 新消息的播报走时间线**外部**的视觉隐藏 `aria-live="polite"` 区域（一秒内合并，只播报当前会话、不播报自己的）。**读屏模式**：外观里的设备级开关（和 D-117 的其他外观偏好一样只存本机），打开后同一个窗口模型但不虚拟化，一次显示最多 100 条，上下各有「载入更早／更新消息」按钮；`aria-posinset` 用稳定编号（`seq − visibleFromSeq`），隐藏和删除让编号有空缺是已知取舍。单字母快捷键一律不用（会和读屏的浏览模式冲突）。

**D-154 输入栏、乐观发送与消息操作**
- **Enter** 发送，Shift+Enter 换行；组字期间、`keyCode === 229`、以及组字刚结束 40 毫秒内的 Enter 不发送（覆盖 Safari 先发 `compositionend` 再发确认用 Enter 的顺序；D 阶段原型已用 CDP 和合成事件验证过这套规则，D-050）。↑ 在输入框为空、没有选区、不在组字时编辑自己最近一条 24 小时内可编辑的消息。草稿按会话只存内存（M6 才持久化）。
- **乐观发送**：点发送时生成 `clientId`，建待发项并立即显示「发送中」（气泡去饱和，不改文字不透明度，02 第 5 节）；同一会话的待发项**按顺序**逐个 `POST`；失败显示红色感叹号，可「重试」（同一个 `clientId`，幂等）或「删除」；消息 DTO 里没有 `clientId`，不做按正文的猜测匹配，补发先于 `POST` 回答带来这条消息时两者最多同时出现一个往返的时间。
- **编辑和撤回不做乐观更新**（改 03 第 11 节：它原写「编辑、撤回也乐观更新」）：它们都有服务端判定的条件（`expectedChangeSeq`、时限），回答很快，失败时回滚比等待更容易让人误解；只有发送是乐观的。撤回时限由客户端用 `hello`/`pong` 的 `serverTime` 校正后的时钟判断（不加 5 秒宽限，L-07），超时就不出现撤回项；菜单开着时过了时限，点击后服务端回 403 `WINDOW_EXPIRED`，提示「已超过撤回时限」。权限永远以服务端为准，界面只据此隐藏按钮。

**D-156 页面结构与范围**
- 四个路由：`/c/:id` 会话页、`/channels` 频道发现页、`/archived` 已归档页、`/join#<码>` 群邀请链接页。`/join` 放在 `_public`（要先读 URL 片段再判断登录状态；码读入内存后立即用 `history.replaceState` 抹掉，D-120 的做法）；未登录时把 `{ code, savedAt }` 存进 `sessionStorage`（只在本标签页，15 分钟失效，读后即删，会话结束与离开登录页时也删，码始终不进 URL 的路径和查询），登录后取回。「打开」要走 `accept`，不是只导航。工具栏是页面可写的「插槽」；资料在账号页编辑；通知级别的界面留到 M6（那时才有效果）；附件、emoji、@助手按钮在各自里程碑出现前不显示（沿用 D-091「不提前提供没有后端能力的控件」）。新增的设备级设置（时间线读屏模式、侧栏分组的折叠状态）写进 01 第 4.11 节的隐私说明，M1b 起就存在却没写进去的侧栏宽度一并补上。页面标题：会话页载入后用会话名（私信用对方的显示名），载入前用中性的「会话」；**私有会话的 404 与不存在的会话标题相同**（「找不到这个会话」，场景 5 的一致包括标题）。

**D-157 详情面板（Inspector）镜像服务端的权限规则，界面只隐藏会被拒绝的操作**
- `apps/web/src/features/inspector/permissions.ts` 是 `domain/authorize.ts` 里 `decide()` 在客户端的镜像（纯函数，角色×状态的组合有单元测试）：成员菜单只列出当前角色真能做的事（群主：设/撤管理员、转让、移出、封禁、禁言；管理员：只对普通成员移出、封禁、禁言；站点管理员比管理员高一级但不能任免）。服务端仍是唯一的裁决，操作被拒（比如角色刚被改）时按原因用文案说明（`errors.ts`：`VERSION_CONFLICT` 说「刚刚有变化，已刷新」并重读；归档后的 `CONFLICT`、`FORBIDDEN`、`NOT_FOUND` 各有专门的说法）。
- 站点管理员对自己不在其中的频道或群：工具栏照样有「成员与详情」；面板里有成员及其菜单、会话设置、封禁名单、归档；没有「添加成员」「创建链接」「我的设置」「退出」；会话页只显示资料、成员数和一句说明，没有输入栏，群也没有「加入」按钮（评审 #26，01 第 5 节「站点管理员不是成员则不能发消息、不能拉人」）。
- 添加成员的结果逐人说明（已是成员、已被封禁、账号不可用、成员已满），不会静默丢人；邀请链接的明文只在创建后的对话框里出现一次（D-128），列表里只有谁创建、何时失效、用了几次，用完次数的链接不再列出；退出：群主还有别人时按钮停用并说明，只剩群主时退出等于归档，确认框里写明；设置面板里的名称冲突（频道重名）显示在字段旁边。

**D-158 时间线的定位、读屏分页、新消息朗读与信息流键盘（补充 D-151 到 D-153）**
- 打开会话时停在「以下为新消息」那一行、跳到引用、回到最新，都用 `scrollToIndex`（必要时带 `offset`）；**不用** `getItemOffset` 算出偏移再 `scrollTo`：虚拟列表里没画过的行只有估算高度，按估算算出的偏移在行被量过之后会漂走（用一万条消息的夹具发现的：打开后分隔线不在视口里）。「回到最新」要等新窗口真正画出来再滚（窗口的替换发生在回答之后的另一次提交里，先滚的是旧列表）；离得远时直接跳，不用平滑滚动。
- 读屏分页模式（外观设置里的开关，只存本机，D-117）：把 virtua 的 `bufferSize` 设成很大的值，让已载入的消息全部在页面里；不再随滚动自动载入，改成「载入更早消息」「载入更新的消息」两个常驻按钮（都在 feed 之外，评审 #7），载入之后用 `role=status` 说一句载入了几条。
- 新消息朗读：只播当前打开的会话、别人发的非系统消息，窗口不贴着最新时不播；1.2 秒没有新的或最长 4 秒合成一句（一条读原文，最多 140 字；多条读「N 条新消息，最后一条来自…」）；`announce.ts` 是纯函数，有单元测试。
- 信息流的键盘：焦点在消息行上时 ↑↓ 移动当前行（到已载入的边缘先载入下一页）、Home/End、PageUp/PageDown，Esc 回输入栏；行内的按钮保留自己的键。每个 article 有 `aria-posinset`，总数未知（任一头还没到底）时 `aria-setsize` 是 -1。

**D-161 性能测量在有图形硬件的 Chromium 里做，阈值不变（补充 D-149）**
- **发现**：无头 Chromium 在没有 GPU 的环境里用软件合成（SwiftShader/llvmpipe），工具栏和输入栏两层 `backdrop-filter` 玻璃叠在滚动的列表上，一帧要 50 毫秒（实测 p50 50 ms，两层都关掉是 16.7 ms；缩小模糊半径、去掉饱和度、提升层都没有用，代价在「有这一层」而不在半径）。这是测量环境的问题，不是页面的：同一台机器上改用显卡（WSL 里经 Mesa 的 d3d12 驱动：`GALLIUM_DRIVER=d3d12`、`LD_LIBRARY_PATH=/usr/lib/wsl/lib`、`--use-angle=gl --use-gl=angle --ignore-gpu-blocklist --enable-gpu-rasterization`，WebGL 渲染器报 `D3D12 (Intel UHD Graphics)`），一万条消息的会话里以 2,500 px/s 滚 3 秒，179 帧，p50 16.7 ms、p95 16.7 ms，没有长动画帧。
- **做法**：性能场景（T1 到 T4、延迟）带 `@perf` 标记，只在 `perf` 这个 Playwright 项目里运行（Chromium，有 `/dev/dxg` 时用上面的参数启动），其他项目排除它们。**阈值一个字不改**；帧间隔、覆盖率、长动画帧只在「本机且合成确实用了图形硬件」时断言（探针里读 WebGL 渲染器名，含 SwiftShader/llvmpipe/software 就当软件合成），其余情况照样测量并附在报告里，确定性的断言（锚点位移、DOM 与窗口上限、T3、T4、零错误）在任何环境都断言。放弃的方案：给页面加「滚动时关掉玻璃」的降级（软件合成下才有的问题，不该改所有人的外观）；把阈值放宽到软件合成也能过（违反 D-149 的「不能为了通过而放宽」）。

**D-162 性能测量的两个细节：先热身再量，常见代码语言在空闲时预载（补充 D-149、D-161）**
- 在有显卡合成的运行里，一万条消息的会话以 2,500 px/s 滚 3 秒：冷启动的那一次测量有 1 到 2 帧超过 50 毫秒（有时一帧到 100 毫秒，主线程没有脚本和渲染，是显卡第一次光栅化新内容的停顿），先滚 0.8 秒热身之后再量，179 帧全部在 16.7 到 16.8 毫秒，没有一帧超过 17 毫秒（三次）。所以 T1 的协议是**先热身 0.8 秒、停 0.3 秒、再量 3 秒**；阈值不变，量的是稳态的滚动，不是页面第一次动起来的那一帧。
- 一条消息里的代码块第一次滚进视口时，Shiki 才去加载这门语言的语法（动态导入加编译，约 60 毫秒的脚本）。Markdown 的代码块在渲染器的块载入之后，用空闲时间一次一门地预载常用语言（ts、tsx、js、jsx、json、bash、sql、python、html、css、yaml、diff，`components/markdown/lazy.ts`），这样滚动时不会为了语法停一帧（评审 #20）；其他语言仍按需载入。
- **后来（D-168）**：代码高亮换成预编译语法的自己的插件，预热只取并登记语法、不再分词；上面「分一个空格」的说法不再适用，冷启动的成本问题由 D-168 解决。

**D-163 窗口上限的说法与时间线的每次变更要便宜（补充 D-149、D-151）**
- D-149 写的「任何时刻窗口 ≤ 2,000 条」与 D-151 的「向上载入的那次提交里只加、裁剪放在之后的提交（约 40 毫秒后）」互相矛盾：虚拟列表只在那次提交里被告知「前面加了行」，同一次提交里同时裁掉另一头会让它的位置补偿出错。取舍：**裁剪之后窗口 ≤ 2,000 条，载入与裁剪之间的那一次提交最多再多一页（≤ 2,100）**；T2 两个都断言（`maxSettled ≤ 2,000`，`maxMessages ≤ 2,100`）。D-149 的其余阈值不变。
- T2 暴露了一个真问题：窗口里有两千条消息时，每次变更（载入一页、来一条新消息）都要重新排一遍行（`buildItems`），它为每一对相邻消息各问一次「是不是不同的一天」，而每次询问都新建一个 `Intl.DateTimeFormat` 来验证时区、再格式化，两千多条要 135 毫秒，一页载入就造成 200 毫秒以上的长帧。改为记住「这个时区是否可用」和「某个时刻在某个时区是第几天」（`lib/time-format.ts`，最多 2 万项，满了清空），同样的计算降到 1.4 毫秒；新出现的时刻仍按需计算。

**D-164 Markdown 块载入失败要能重试；没人写过消息的会话，列表不是 feed（补充 D-145、D-153）**
- 旧的载入函数把第一次失败的 `import()` 记住了：空闲预载的那一刻网络刚好断一下，之后每次请求拿到的都是同一个失败，所有要显示消息正文的屏幕就停在「载入中」，直到刷新页面。改为：**失败不记住，下一次请求重新取**；等着它的屏幕（`useMarkdownReady`）每 2 秒再取一次，浏览器离线时不取，等 `online` 事件；空闲预载在离线时不开始，语法预热遇到离线就停下（之后显示的代码块自己加载语法）。预热遇到失败（断网；在预热中途离开页面，WebKit 报「请求被取消」、Firefox 报一个对象）就当没做过，也不往控制台写：原来的代码插件会把每次失败写进控制台，还把失败的高亮器缓存到会话结束，之后这门语言的代码块一直不高亮（现在的插件失败不被记住，见 D-168）。预热也改成一次一门、等上一门到了再排下一个空闲时段。`components/markdown/lazy.test.ts` 有五个测试（载入一次、失败后重取、等待中的屏幕重试并在成功后停止、离线时不请求并在恢复后请求、预热逐门进行且离线时停止）。
- 时间线容器原来无条件是 `role="feed"`，而 feed 必须含 article；没有一条消息的会话（刚建的频道、对方还没说话的私信）里 axe 判 `aria-required-children`（严重）违规，是 E2E 新用例「没人写过的会话」发现的。改为**有消息时是 `feed`，没有时是带名称的 `group`**，第一条消息到来时角色随之切换；其余（D-153 的键盘、D-152 的未读线）不变。

**D-165 E2E 夹具的几处修正（补充 D-148、D-160）**
- **Playwright 自己塞进页面的内联样式不算页面的违规**：WebKit 和 Firefox 在截图时（每个测试结束时，以及测试自己关闭每个上下文时）往页面里塞一个内联 `<style>`，页面的策略会拦下它并报一条 `style-src-elem` 违规，WebKit 还会在控制台再写一份「Refused to apply a stylesheet…」。夹具原来在上下文拆除之后才检查，这一条被当成页面的违规，WebKit 的无关用例因此全部失败（Chromium 不受影响）。**做法**：检查夹具依赖默认上下文，所以先于它被拆除（检查结束了才截图）；测试自己关闭的上下文（第二个人、第二台设备）在关闭时也会被截图，所以探针丢掉「`style-src-elem`、`inline`、**没有源文件**」这一种事件（应用自己造出来的样式一定来自应用的文件或文档，有来源），WebKit 控制台里同一件事的文字副本也放过；真正的拒绝仍然会被策略事件抓到，那一条是严格检查的。
- **断网期间浏览器对失败请求的报告是测试造成的**：`controlNetwork`（V-14）切断网络之后，浏览器把每个失败的请求记成控制台错误（Chromium 的 `net::ERR_INTERNET_DISCONNECTED`、WebKit 的 `WebKit encountered an internal error`，Firefox 在页面重连被拒时写的「Firefox can't establish a connection to the server at ws://…」）。登录后应用在空闲时载入 Markdown 渲染器和代码语法，所以断网的时刻随时可能落在它们中间。夹具只在**该上下文断网期间（含恢复后 1 秒）、文本匹配这几种「加载失败」时**放行；页面自己写的错误、CSP 违规、页面异常照旧失败。放弃的方案：断网前等页面把文件加载完（WebKit 没有 `requestIdleCallback`，预载用 2 秒的定时器，在断网之后才开始，等不到）。
- **E2E 里发消息要等过组字宽限**：Firefox 把 Playwright 的 `fill` 报成一次完成的输入法组字，紧跟着的 `Enter` 落在 `enter-key.ts` 的 40 毫秒宽限里，被当成确认候选词的那一下，只换行不发送（D-154 的 Safari 规则）。`sendFromComposer` 在 `fill` 之后等过这个窗口，同真人的节奏。
- **成员行的选择器限定在成员列表里**：封禁名单的每一行也是 `.member`，也写着被封的人的名字；原来的选择器在封禁成功、名单先于「成员消失」被断言之前加载出来时会匹配到它，测试成了看时间的（场景 10 在 Chromium 里五次失败三次）。`memberRow` 现在只找 `aria-label` 为「成员列表」的那一个列表。
- **T2 的探针在步进之后才选「读者的那一行」**：探针先把列表放到离加载区 800 px 的地方，再步进到 500 px（进入加载区），并在步进之前选好锚点行。列表会在量过实际高度之后自己动（估计高度变成实测高度），所以步进前选的那一行有时在步进之后离开视口一屏，不再被画出来，提交时找不到它，`compared`（比较过多少次）只有 81 而不是 90 以上。单独跑 T2 时从未读线开始、整套性能用例跑时 T4 已经把 `perf_b` 读到底、T2 从底部开始，所以只有整套才失败。产品没有问题（`maxShift` 一直是 0）。现在步进和选锚点在同一个任务里（此时还没有渲染，也没有发出请求），选的是步进之后视口顶部的第一行；整套性能用例 `compared` 为 117。
- **管理员的接口会话按「一次运行」保存**：Playwright 在每个失败的测试之后换一个新的工作进程，缓存在进程里的管理员会话随之丢失，重新登录很快撞上同账号的登录限流（8 次 / 10 分钟，返回 429），一个失败就变成几十个。会话改存在这次运行的文件里（`test-results/.administrator-session-<runner 进程号>.json`，同一次运行的所有工作进程共用，下一次运行开始时该目录被清空）。

**D-166 键盘跳转之后焦点不能落到 `<body>`；窄窗口的抽屉在选了地方之后要关上（补充 D-153、D-157；AT-21）**
- **问题**：AT-21 要求「焦点不被虚拟列表吞掉」。新的键盘用例（在一万条的会话里 ↑ 三十次、PageUp、滚轮拉走一屏又一屏、End、Home、Esc）发现了三处：(1) 长距离跳转之后，刚被画出来的目标行在量过尺寸之前被 virtua 设成 `visibility: hidden`，对隐藏元素调用 `focus()` 不报错也不生效，而旧代码调用一次就认为做完了；(2) `focusMessage` 一开始就把「当前行」改成目标，原来有焦点的那一行不再被 `keepMounted` 保留，列表一滚走它就被卸载，焦点掉到 `<body>`；(3) 按键连发时每次按键都从「仍有焦点的那一行」出发，一帧里按几下只走一步（WebKit 上三十次 ↑ 只走了二十三步）。
- **做法**：落地以 `document.activeElement === 目标` 为准，每帧重试，最长 2 秒（长跳转到已载入范围的顶部时，上一页要先读一次再提交，行要等那之后才稳定），不再数帧；时间线记下含焦点的行（根节点上的 `focusin`/`focusout`），它和当前行一起放进 `keepMounted`，所以在目标落地之前焦点始终有地方待；「去向」（`heading`）是焦点正在去的那条消息，连发的按键从去向出发，只有最后一个目标拿到焦点。用例在 Chromium 与 WebKit 上通过（`e2e/accessibility.spec.ts`）。
- **窄窗口的抽屉**（低于 768 px，列表是盖在页面上的抽屉）：之前只有 Esc 和点遮罩能关，选了会话之后抽屉还盖着它——M1b 没有会话，所以没人发现；320 px 的用例（登录、选会话、发消息、看详情，页面不横向溢出）发现了它。现在在抽屉里点任何链接（包括已经打开的那个会话，路径不变）就关，路径变了（⌘K 选中等）也关；设置和对话框只改地址的查询串，不关。

**D-167 「正在输入」要给还没开过口的人起名字；网关的两处补正（补充 D-147、D-072）**
- 没有开过口、也没有人打开过成员列表的人，页面的人物字典里没有他：用 API 建一个已经带着他的群，不会有「某某加入了」的系统行把他带进来。这时他一开始输入，输入栏上方写的是「某位成员 正在输入…」，而不是他的名字——是经过网关的 E2E（边缘套件）发现的，直连的场景 2 里 B 先开过口所以看不出来。**做法**：收到 `typing` 的 `start`、而字典里没有这个人时，向 `GET /api/users/{id}` 要一次资料（`app/realtime.ts` 的 `learnOf`，同一个人在途中不重复；失败 30 秒后才再问），到了就写进字典，那一行随即换成名字；`engine.knowsUser` 有单元测试。E2E：`scenario-2-chat.spec.ts` 的「没开口的人正在输入也有名字」，Chromium 和 WebKit 跑（Firefox 只跑冒烟）。
- **网关就绪要等整条链**：边缘套件原来用 `127.0.0.1:3104` 的 `readyz` 判断 API 起来了，但容器是经 Docker Desktop 到宿主机再转进 WSL 的，宿主机发现新监听端口要晚一点，第一批请求会拿到 502。现在 Playwright 的就绪检查直接问 `https://chat.localhost:8443/api/readyz`（网关、转发、API 全通才算）。
- **server 块也带 HSTS**：见 10 第 5 节，网关套件发现请求行解析不了时（`GET /%zz`）的 400 没有 HSTS，因为 Nginx 在选定 location 之前就回了；server 块里 include 一次，其余 location 因为有自己的 `add_header` 不继承，所以没有重复。

**D-168 代码高亮：自己的插件、预编译的语法、一个高亮器（取代 D-145 里的 `@streamdown/code`，补充 D-162）**
- **测量**（同一份代码、同一台机器，只算每种语言第一次分词）：标准的 JavaScript 正则引擎在 V8（Chrome、Node）里 TypeScript 153 毫秒、Bash 43、SQL 58、JSON 2；在 JavaScriptCore（Safari 的引擎，用 Bun 测）里 TypeScript **633 毫秒**，而且第二次还要 85。原因是 Shiki 第一次遇到某条语法规则时才把它的 Oniguruma 正则转成 JavaScript 正则。Playwright 的 WebKit 里打开一个会话，首屏之后主线程停 1.2 秒；性能用例里（V8）表现为 T2 偶尔出现 ≥ 200 毫秒的长帧：主线程剖析是 `DIV#feed.onscroll` 里的 `codeToTokens → tokenizeLine2 → findNextMatchSync / #execCore`，夹具里的代码块只有一两行，所以是冷启动，不是长度。D-162 的预热只加载语法、分词的是一个空格，碰不到它；预热时分一小段真实代码（试过）只是把这个停顿挪到打开会话之后，WebKit 里 1.2 秒的停顿照样在，还让依赖时序的 E2E 用例（被移出的提示）失败。
- **做法**：`@shikijs/langs-precompiled@4.5.0`（与 shiki 同版本、npm 最新稳定版；同样的语法，正则已经转好）加 Shiki 的 `createJavaScriptRawEngine`，同样的示例首次分词 V8 里 TypeScript 7.8 毫秒、Bash 1.4、JSON 0.8、SQL 24，JavaScriptCore 里 TypeScript 26 毫秒（快 24 倍）。`@streamdown/code` 把引擎写死，所以自己写了代码高亮插件（`components/markdown/code-plugin.ts`，接口就是 Streamdown 的 `CodeHighlighterPlugin`），去掉 `@streamdown/code` 依赖，加 `@shikijs/langs-precompiled` 4.5.0。**保持原插件的做法**：按（语言、主题、代码）缓存结果，缓存按代价和个数有上限；还在写的代码块（`isIncomplete`）的结果不缓存，它的分词接着上一次的最后一个完整行和语法状态往下做，流式输出只算新增的行（M4 的 Agent 输出会用到；单元测试核对「每个前缀逐段写出来」与「整段一次高亮」逐 token 相同）；语法还没取回来时回答 `null`、之后用回调给结果；不支持的语言按纯文本。**不同之处**：整个页面只有一个高亮器（原插件每种语言建一个，Shiki 在第 10 个实例时往控制台警告「应当用单例」，预热 12 门语言就会碰上）；语法已加载时同步给出结果（不先画一遍纯文本）；加载失败不被记住（下次再取）；只提供 `code-plugin.ts` 里列出的 50 种常见语言和 34 个别名（`ts`、`bash`、`yml`、`c++` 等，其他按纯文本），每种语言是一个单独的文件，用到时才取；构建里不再带 Shiki 的全部 300 多个语法块。预热（`lazy.ts`，D-162、D-164）现在只取并登记语法，不再分词。
- 代价：这是一份要自己维护的、约 330 行的插件；语言清单要增减时改 `code-plugin.ts` 的两张表（单元测试核对别名和未知语言）。
- 仍然没解决：WebKit 里首次打开会话时 Markdown 块的执行（unified、remark、rehype 加实体表，约 1 MB 的脚本）本身还会让主线程停 600 毫秒左右，纯文本的会话也一样，与代码高亮无关；这段时间界面显示的是载入状态。

**D-169 网关的 Nginx 改用 1.30 系列（用户 2026-10-04 的决定，取代 D-045 与 D-147 里的 1.28；服务器 M8 再升）**
- **决定**：本地网关（`infra/compose.edge.yml`，M2b 的网关套件和 M7 的彩排用它）和 CI 里 `nginx -t` 用的镜像从 `nginx:1.28.3-alpine` 换成 `nginx:1.30.5-alpine@sha256:0985e772fb9f729e6fa0980da05fca5d9c468e870eed43071545afa9d2e27d94`：1.30 系列当前的最新版（2026-09-26），精确版本加索引摘要（amd64 与 arm64 都在里面，所以服务器上也能用同一个摘要）。原因是 1.28 上游已于 2026-04-14 停止安全支持，两个 2026 年的严重漏洞（CVE-2026-42533、CVE-2026-42945）只在 1.30.x、1.31.x 修复。
- **验证**：镜像里 `nginx -t` 通过（`bun scripts/edge.ts configtest`）；本地网关套件 25 个用例在 1.30.5 上全部通过（`bun run test:edge`），容器里 `nginx -v` 为 `nginx/1.30.5`；`scripts/edge-config.test.ts` 8 个通过，它现在要求镜像是「1.30 系列的精确版本加 64 位摘要」。站点配置一个字没改。
- **没有改的**：**服务器上共用的那个 Nginx 还是 1.28**（多站点共用，Orbit 也在上面），M8 部署时才升到 1.30：到时先查服务器的包源能装到哪个 1.30.x，升之前后各检查一次 Orbit 与 ChatApp 的站点，不动 Orbit 的站点文件；在那之前站点文件必须在 1.28 上也安全，所以仍不用正则 `map`、`rewrite`（未命名捕获）、`charset`（`edge-config.test.ts` 核对）。1.30 的小版本更新（1.30.x）：装了 Renovate（`renovate.json` 已按摘要锁定 docker 镜像，App 还没装）之后由它提醒，没装就在每次依赖复查时看一眼；更新时同一次改 `compose.edge.yml` 的标签和摘要，再跑 `test:edge`。
