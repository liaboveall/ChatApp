## 产品与范围

**D-001 重写，不修补**
旧版的问题是结构性的：迁移链断裂、数据模型导致越权、前端 JS 需要全部重写、技术栈落后两个大版本。在旧代码上修补，成本会高于重写。

**D-002 技术选型只看"最新、最好"（用户）**
不考虑用户是否熟悉，也不参考其他项目的技术栈。版本以 registry 上的最新稳定版为准，不用 beta 或 RC，例外会单独注明。

**D-010 邀请制注册（用户）**
- 注册必须持有邀请码。站点管理员可以无限邀请；普通成员有 5 个"成功邀请"名额，可以调整。
- 群邀请链接只对已注册用户有效，因此不能被当作注册的后门。
- 既然只有受邀者能注册，就不需要人机验证。

**D-016 桌面优先（用户）**
- 以 ≥ 1280px 为主，最低支持 1024px；手机和平板布局放到 v1.1。
- 桌面端的 PWA 仍然要做：可以安装成独立窗口，并使用 Window Controls Overlay。

**D-017 Apple Liquid Glass 风格（用户）**
- 以 2026 年 WWDC 修正后的版本为准，即可读性优先。
- 玻璃效果只用于导航层，内容层保持实底；提供四档透明度。
- 不打包 SF 字体，不使用 SF Symbols，也不使用任何 Apple 商标。原因是授权只允许在 Apple 平台上使用。

**D-018 本地优先，上线放在最后（用户）**
- M1 到 M7 都在本地开发和验收；M7 在本地用生产配置做一次 HTTPS 彩排，降低最后上线的风险。

**D-020 消息规则**
- 撤回：2 分钟内，与微信的习惯一致。
- 编辑：24 小时内，不保留历史版本。
- 超出撤回时限后，只能"仅对自己删除"。
- 群主或会话管理员、站点管理员可以删除任何消息，并写入审计日志。

**D-021 附件**
> 2026-10-01补充：单位与基础设施硬限以D-078为准（MiB/GiB）；后台只能在硬限内收紧，隔离实施见D-081。下列保留历史表述。
- 单个文件 100 MB，图片 20 MB，每人总空间 5 GB，均可在后台调整。
- 视频不做转码，因为服务器只有 2 个 CPU 核心。
- HEIC 格式、视频封面放到 v1.1。
- ↪ **D-041** 补充：视频重新封装以去除位置等元数据（仍然不转码）。

**D-022 AI 预算默认值**
> 2026-10-01修正：D-087保留预算初值，取代“足够日常使用”的容量判断；D-062管预占，06第8.1节管任务容量和实验预留。
- 每人每天 50 万 token；全站每月 20 美元，用到 80% 时提醒，100% 时暂停。
- 按 DeepSeek 的价格，这些额度足够日常使用；均可在后台调整。
- ↪ **D-034**、**D-049** 补充：额度和预算只针对站点 key 的运行；"每天"和"每月"按 `Asia/Shanghai` 计算。

**D-026 频道里成员加入、离开不产生系统消息**
频道人多，这类消息会刷屏；成员变化只体现在成员列表里。群组和私信里照常产生。

**D-027 站点管理员不能读取私有会话的内容**
- 站点管理员可以对会话做管理操作，但读不到自己不在其中的群组、私信、Agent 会话的消息。
- 唯一的例外是处理举报时，可以看到被举报的消息及前后各 5 条，并且要写入审计日志。

## 架构与技术

**D-003 全栈 TypeScript；后端用 Bun 1.4 + Hono 4**
- 选择理由：
  - 前后端共享 zod 契约，类型和运行时校验都统一；
  - Bun 自带高性能的 WebSocket 发布订阅、S3 客户端和测试工具；
  - Hono 基于 Web 标准，万一需要，可以换回 Node 24 LTS 运行。
- 放弃的方案：
  - Django 6 + Channels 4：两种语言，实时能力偏弱；
  - Elixir/Phoenix：实时能力最强，但生态小，也无法和前端共享类型；
  - Go、Rust：性能不是这个项目的瓶颈；
  - Elysia：只能跑在 Bun 上。
- ↪ "可以换回 Node"只在一定范围内成立，Bun 专有 API 的边界见 **D-055**。

**D-004 前端用 React 19.3 单页应用 + Vite 8**
- 选择理由：
  - 应用需要登录才能使用，用不到服务端渲染；
  - React 的组件生态最全（Base UI、react-virtuoso、Streamdown 等）；
  - React Compiler 1.0 可以自动处理大部分性能优化。
- 放弃的方案：
  - Next.js 16：对 WebSocket 支持不好，服务端渲染用不上；
  - TanStack Start：用不上服务端渲染；
  - Vue 3.6、Solid 2：还在 RC 阶段；
  - Svelte 5：可以用，但生态不如 React。

**D-005 实时模型：写操作走 HTTP，WebSocket 只推送；用 seq / change_seq 补发；自己实现 WebSocket 层**
- 放弃的方案：
  - Socket.IO：协议较重；
  - Centrifugo：为超大规模设计，对我们来说只是多维护一个服务；
  - Zero 1.9、Electric 这类同步引擎：聊天消息基本只追加，"序号 + 事件"已经够用；而"正在输入"、AI 流式输出这类瞬时事件，照样需要另开通道。

**D-006 PostgreSQL 18.6 + pgvector 0.8.6**
- PostgreSQL 19 目前还是 beta4，不用。
- 18 版原生支持 `uuidv7()`；pgvector 提供语义搜索和 Agent 记忆需要的向量能力。

**D-007 Valkey 9.1 + BullMQ 6**
- 用途：事件总线、在线状态、限流、任务队列。
- 放弃的方案：
  - Redis 8：Valkey 是 BSD 许可的社区版本，功能相当；
  - pg-boss：既然已经有 Valkey，BullMQ 更成熟，功能也更全。

**D-008 对象存储用 Garage 2.4（自托管 S3）**
- 选择理由：占用资源很小，支持 arm64；对外是 S3 接口，以后可以换成 R2 或 S3；下载统一经过应用鉴权。
- 放弃的方案：
  - 直接存本地磁盘：以后不方便迁移；
  - MinIO 社区版：已进入维护模式；
  - RustFS：9 月中旬才发布 1.0，还太新。

**D-009 认证用 Better Auth 1.7**
- 支持邮箱密码（必须验证邮箱）和 Passkey。
- 不做第三方登录：在邀请制下意义不大。
- 两步验证放到 v1.1。

**D-012 ORM 用 Drizzle**
- 选择理由：贴近 SQL，适合序号分配、未读数、部分索引、pgvector 这类场景。
- 放弃的方案：Prisma 7，可以用，但对 SQL 的控制力不如 Drizzle。
- 版本：Drizzle 1.0 目前是 RC4。M1 开工时如果 1.0 已经正式发布，就用 1.0；否则先用 0.45.x，并计划在 1.0 正式发布后升级。

**D-024 组件底层用 Base UI 1.8（Radix 作为备选）**
Base UI 提供无障碍的交互原语（菜单、弹窗、焦点管理等）；视觉部分按 02 整体重做。组件的组织方式参考 shadcn/ui。

**D-025 不使用 outbox 表**
> 2026-10-01：以下为历史记录；相关实现条款由 D-056 取代或补充。
事件在事务提交之后发布；万一发布失败，客户端会通过 `change_seq` 补发兜底，因此不会丢数据。
- ↪ **D-043** 补充：客户端按会话检测 `changeSeq` 跳号。否则发布失败而连接没断时，客户端没有理由去补发，上面的兜底并不成立。

**D-032 清理 git 历史中的用户上传文件（用户确认，2026-09-30；执行了 D-019 中待确认的那一步）**
- **删除范围**：所有历史中的 `media/chat_files/`、`media/room_icons/`，以及 `media/profile_pics/` 下除 `default.jpg` 以外的文件，共 96 个路径、约 41 MB。

- **做法**：在 `--no-local` 的镜像克隆里执行 `git filter-repo --invert-paths`（通过 `uvx` 运行）。推送前逐项核对：

## 规划审查修订（2026-09-30，会话 2）

> 来自对 00–13 的全面审查。标"用户"的四条由用户拍板；其余由 Claude 按用户授权决定（原话："其他的要优化完善的地方你自己决定"）。

**D-033 内存预算放宽（用户）**
- 只要求不超过服务器的总内存。ChatApp 合计上限约 6 GB：api 1 GB、worker 2 GB、postgres 2 GB、valkey 512 MB、garage 512 MB（见 10 第 3 节），其余留给已有站点和系统。

**D-034 站点 key 的 Agent 运行内容可以由站点管理员查看；鼓励用户自带 key（用户）**
- 区分两种 key：
  - **站点 key**：站点提供的 DeepSeek key；
  - **自带 key**：用户在设置里填写的自己的 DeepSeek key（M5a）。
- 使用站点 key 的运行：完整内容保留 30 天（后台可调），站点管理员可以在后台查看，每次查看都写审计日志。完整内容包括请求、读取到的消息、工具参数和结果、模型输出。
- 使用自带 key 的运行：管理员只能看到用量、状态、耗时等元数据。
- 界面鼓励使用自带 key，但文案只讲好处：不占每日额度，全站预算用完时照常可用。文案里不提管理员能看到内容（用户要求）。
- 隐私说明（01 第 4.11 节）如实写明管理员能看到什么。这是 Claude 的补充：原规格对用户承诺"管理员不能读取私有内容"，如果不更新说明，就与实际行为不符。
- 补充 D-027：管理员能看到私有内容的例外从一个变为两个。

**D-035 新成员看不到加入前的历史（用户）**
> 2026-10-01：以下为历史记录；相关实现条款由 D-057、D-060（保留用户的历史不可见目标，替换实现） 取代或补充。
- **适用范围**：频道和群组。退出或被移出后再加入，按新成员处理。
- **实现**：`conversation_members.visible_from_seq` 记下加入时会话的 `last_seq`，成员只能看到 `seq` 比它大的消息。已读位置也从这里开始，未读数不会一加入就显示 99+。
- **所有读取路径用同一个可见性判断**：消息列表、补发、搜索、Agent 工具、语义搜索、附件下载、引用摘要。
- **广播不能泄露**：如果被更新的消息早于最近一次有人加入（`seq ≤ conversations.last_join_seq`），只广播不含内容的 `message.changed`，客户端再按自己的权限补拉。Agent 的流式输出同理。

**D-036 "重新生成"替换原回复（用户）**
> 2026-10-01：以下为历史记录；相关实现条款由 D-068（保留原位替换目标） 取代或补充。
- 在原位置替换同一条消息，旧内容不保留；只有发起这次运行的人可以操作。
- Agent 会话和面板里，只能重新生成最近一条回复；群组和频道里，24 小时内可以重新生成。执行过需要审批的工具的运行，不能重新生成。
- 取代 05 中"基于同样的输入重新运行一次"的模糊描述。

**D-037 副作用工具恰好执行一次（取代 INV-10 的原做法）**
- **原做法的问题**：原做法是"先写入步骤，重试时发现步骤已存在就跳过"。如果 worker 在"写完步骤、还没执行"时崩溃，已经批准的操作就永远不会执行，而且会补写一个虚构的结果。
- **新做法**：副作用操作和一条 `agent_effects (run_id, step_index)` 记录在同一个事务里提交。重试时先查这张表：有记录就直接返回之前的结果，没有才执行。
- **状态存放**：续跑需要的完整模型消息存进 `agent_run_states`；`agent_steps.payload` 只存供展示的截断版本（≤ 32 KB），避免截断破坏续跑时重建的历史。

**D-040 邀请名额原子占用；未验证的账号怎么处理**
> 2026-10-01：以下为历史记录；相关实现条款由 D-059 取代或补充。
- **注册时的占用**：先原子地占用名额——邀请码的 `use_count` 条件加 1，邀请人的 `users.invites_used` 也条件加 1，并写入一条 `pending` 使用记录（10 分钟内没有确认就自动释放）。账号创建成功后，这条记录改为 `confirmed`。

**D-041 附件按用途授权；视频去除位置信息**

**D-042 会话级封禁；邀请链接随创建者一起失效**
- **封禁**：被"移出并封禁"的人，不能通过频道发现、群邀请链接或被别人拉入的方式重新加入，直到被解除封禁。

**D-043 补强实时一致性（补充 D-005、D-025）**
> 2026-10-01：以下为历史记录；相关实现条款由 D-056 取代或补充。
- **跳号检测**：客户端按会话检测 `changeSeq` 是否跳号，缺号 1 秒后仍未补上，就调用 `/changes`。这样"事件发布失败、连接却没断"的情况也能自愈。
- **`/changes` 的补充**：接口同时返回这段时间里我隐藏的消息。如果缺口超过 1000 条变更，接口返回 `resetRequired`，客户端丢弃这个会话的缓存，重新加载。
- **焦点上报**：客户端新增 `focus` 消息，上报当前在看的会话以及页面是否在前台。正在看的会话不推送。
- **在线状态**：按连接分别记录活跃状态再汇总；worker 每 30 秒清理一次过期的连接，并发布离线状态；客户端发出 `presence.watch` 后，服务端立即回一份当前状态；用户的最后一个连接断开时，写入 `users.last_seen_at`。
- **客户端的连带更新**：收到某条消息的更新时，同时更新引用它的回复和会话列表里的预览。

**D-044 数据库是唯一的事实来源；Valkey 的使用规范**
> 2026-10-01：以下为历史记录；相关实现条款由 D-056、D-061、D-071 取代或补充。
- **频道名**：Valkey 的 pub/sub 不区分 db 编号，所以事件频道名要带上环境：`events:{APP_ENV}`。
- **任务保留与告警**：BullMQ 统一设置任务保留期限：已完成的保留 1 天或 1000 条，失败的保留 7 天。Valkey 内存用到上限的 80% 时告警。
- **对账任务**：定时消息、提醒、审批过期、卡住的 run，都以数据库为准。`reconcile` 任务每分钟把到期的项重新放入队列，并用实体 id 作为任务 id 去重。因此 Valkey 不需要备份。
- **登录会话**：以 Postgres 为准，Valkey 丢了数据不会让用户掉线。
- **客户端库**：应用里所有 Valkey 访问统一用 ioredis（BullMQ 本来就依赖它）。

**D-045 网关、安全响应头与健康检查**

- **健康检查**：路径改为 `/api/healthz`、`/api/readyz`，避免被前端的回退规则拦走。
- **客户端 IP**：只信任本机反向代理（`TRUSTED_PROXIES`）写入的客户端 IP 头，限流按真实 IP 计算。
- **邀请码不进日志**：不出现在服务器会记录的地方。检查接口改为 POST；注册链接和群邀请链接把码放在 URL 的 `#` 后面。

**D-051 补强 Agent 的安全与行为**
> 2026-10-01：以下为历史记录；相关实现条款由 D-060、D-061、D-068 取代或补充。
- **面板和 ⌘K 的读取范围**：默认只读当前会话，用户在界面上明确切换到"我的全部会话"后才放宽。原因是面板既读不可信的群聊内容，又能接触私密数据；一旦被注入，可能把私信写进草稿或链接。
- **记忆的写入**：只有本轮用户原话里有明确的记忆意图（"记住""别忘了"等）时，才向模型提供 `remember` 工具；否则写入记忆需要审批。这是为了防止记忆被投毒。
- **等待审批时的消息**：当前消息先收尾，标为"等待某某批准"；继续运行时再新建一条消息。这样群里不会挂着一个长达 24 小时的"输出中"气泡。
- **机器人的身份**：机器人不是任何会话的成员，不出现在成员列表里。Agent 的回复由专门的 domain 函数写入，前提是调用者此刻仍能在该会话发言。Agent 消息中的 @提及不产生通知。
- **流式输出**：每 50–100 毫秒合并发送一次增量。每秒写库时，同时记下已写入部分对应的增量序号（`streamIndex`），中途打开会话的客户端可以接着往下拼。
- **评测**：
  - 安全类用例检查结果：没有泄露数据，也没有未经审批的副作用。必须 100% 通过。
  - "模型是否尝试了越权操作"单独统计。
  - 每周定时跑一次评测，及时发现 `deepseek-flash` 升级带来的变化。

## 独立复审后的实施规划（2026-10-01）

以下决定落实审查 F01–F24；表示设计已修订，不表示实现或故障测试已通过。

**D-056 持久工作意图与完整同步水位（取代 D-025、D-043 的可靠性交付方案，补充 D-044）**
- 业务变更、同步日志和需要可靠执行的工作意图在一个 Postgres 事务提交；增加 `work_items`，承担小型 outbox 和任务台账职责。dispatcher 至少一次派发，消费者依靠业务唯一键和条件更新去重。
- Valkey Pub/Sub 只是实时提示，BullMQ 只是执行运输层。独立的 Postgres 扫描循环恢复未完成任务，不能把恢复循环本身只放在可能丢失的队列中。
- 用只含实体标识的 `conversation_changes` / `user_changes` 日志和有固定上界的游标补齐；客户端区分 observed 与 synced 水位。前台每 30 秒对账，尾事件丢失也能发现。正常依赖下目标 35 秒内收敛；依赖故障时显示未同步，不能宣称已送达。
- 放弃只靠跳号和 after-commit 入队：它们不能恢复最后一个丢失事件或根本没创建的任务。协议见 03、05。

**D-057 内容按接收者投影，撤权以数据库为准（取代 D-035 的广播技巧、D-038 的五分钟兜底）**
> 后续D-079区分session与持久委托；D-082补实体版本与关系墓碑，其他权限原则仍有效。
- 消息创建、编辑和删除统一广播不含正文的变更提示，再按 HTTP 当前权限读取；引用、预览、附件列表也逐个做可见性投影。移除 `last_join_seq` 作为授权依据。
- 写入与成员变化按 03 的锁顺序串行化；WS 的个人内容和 Agent 增量在每次实际派发批次重新查会话、成员和运行版本，不靠缓存中的订阅名单授权。
- 注销事件可靠投递，并每 5 秒复核连接；授权查询失败即停止敏感派发。撤权提交后开始的授权读取必须失败；提交前已授权的在途响应或已下载内容无法收回，不承诺消除网络在途窗口。

**D-058 认证端点默认拒绝，管理员不具备代登能力（补充 D-027、D-034，取代 D-039 的黑名单收口）**
- `/api/auth/*` 不是无条件透传：仅放行 05 列明的登录、验证、本人会话和 Passkey 能力；其余默认 404。插件升级后的新路由默认关闭。
- 不启用 admin 插件的 HTTP 管理能力；禁止代登、替他人设置密码或邮箱、原生硬删除与无邀请创建账号。后台和 CLI 经应用 domain 执行，扩展字段一律禁止客户端赋值。
- 管理员限制是应用角色边界，不是对掌握主机、数据库和加密密钥的运维者提供端到端隔离。[Better Auth 管理插件](https://better-auth.com/docs/plugins/admin)能力不能直接等同于本站角色权限。

**D-059 注册是可恢复的激活状态机（取代 D-040 的 pending 超时直接释放）**
- 注册占用带稳定 `registration_id`，账号在第一次插入时原子写入同一标识并保持未激活。优先使用共享事务；adapter 不支持时使用 04 的可恢复流程，不能只在 after hook 关联账号。
- 邮箱验证与邀请确认都完成后才能激活；清理、人工验证、邀请撤销使用同一把注册锁。超时必须先查明账号是否存在，禁止仅按 pending 时间退名额。
- V-13 必须证明“账号创建时关联标识”可实现；若做不到，M1a 先实现定制 adapter/注册服务，注册入口不得以已完成交付。

**D-060 Agent 上下文有来源与范围世代（补充 D-014、D-035、D-051）**
- 面板切换读取范围即开启新上下文世代，不沿用另一范围的模型历史、摘要或工具结果。恢复与每次模型调用前检查全部来源；来源被撤权、编辑或撤回时终止旧 run，重新发起时重建。
- 共享输出只读所有当前接收者共同可见的当前会话消息，水位为成员 `visible_from_seq` 的最大值。成员世代变化时停止旧 run 的后续生成和发布，必要时从新水位重新请求。用户主动粘贴转述的内容属于新消息，不声称系统能防止人工转述。
- 无来源标记的旧摘要不允许直接恢复。个人长期记忆也不得注入共享输出。

**D-061 Agent 持久状态、执行租约和续跑编号（补充 D-037、D-044、D-051）**
- 审批回应、状态转为 queued、`resume_seq` 增加及工作意图必须同事务提交；每段输出以 `(run_id, resume_seq)` 唯一。BullMQ jobId 使用 work id 和投递序号，不复用已保留的 runId job。[BullMQ 任务标识规则](https://docs.bullmq.io/guide/jobs/job-ids)是运输层限制，不是业务去重依据。
- `lease_epoch` 防止旧 worker 提交；取消先写 Postgres，Valkey 仅用于唤醒。工具执行事务复核 epoch、取消、权限和审批参数哈希。
- “恰好一次”仅指同库事务内的业务效果；邮件、Web Push、模型供应商调用不能承诺外部恰好一次，未知结果按各自重试策略处理。

**D-062 调用前原子预占预算（补充 D-022、D-049）**
- 每次模型调用按保守输入估算、最大输出和思考 token、当前价格版本预占用户日额度与站点月费用；不足则不发起调用。统计缓存不能用于授权花费。
- 唯一 attempt id 记录 reserve → started → settled/unknown/released；usage 只结算一次。网络结果未知或收费后崩溃不得自动退占用或盲重试；保守记满上限并人工/供应商对账。
- 周期归属在预占时冻结，审批续跑新调用按新周期。该控制保证应用按配置计价的准入上限，不保证供应商账单绝无价格变动或外部重复计费。

**D-063 完整副本清单与删除时限（取代 D-048 的立即物理删除表述，补充 D-052）**
> 后续D-084补成功确认前的异地删除意图；下面的立即清空指最终在线删除事务完成，待异地确认时返回202而非成功。
- 撤回事务立即清空在线正文、提及与向量，并使附件不可访问；对象物理删除目标 1 小时、最长 24 小时，失败告警重试。备份最多 28 天，逾期备份未清理必须告警，不能继续宣传已物理清除。
- Agent 状态、步骤、审批参数、效果结果、派生摘要均进入 04 的保留清单。效果账本只留去重所需 id、哈希和结果码。删除私有 Agent 会话同时清除其运行内容；注销时取消未完成运行和未来任务。
- 普通消息撤回可能仍在既有 Agent 运行副本中保留到创建后 30 天；这些副本不能再作模型上下文。外部已送达通知、供应商副本、用户另存文件不可远程召回，隐私说明如实区分。

**D-064 上传预占、对象账本与媒体资源上限（补充 D-021、D-041）**
- 先持久化上传身份、临时对象 key 和配额预占，再接收流；无 Content-Length 时预占该类型上限。对象写入、处理、绑定、删除都有可恢复状态及代次。
- 用户配额按处理后的主文件计费，衍生文件计入全站容量；输出变大必须再原子预占，失败则删除且不公开。墓碑和删除任务防止旧处理任务复活对象。
- 图片像素、动画帧、时长、解码内存和超时有硬限；媒体子进程无网络，默认并发 1，和向量工作共享内存闸门。具体默认值见 01、03。

**D-065 Web Push 从 M6 起执行 SSRF 与接收权限检查（取代 SEC-23 的延期假设）**
- 注册和发送时均校验端点：HTTPS、受支持服务商域名清单、公共 DNS 地址、连接目标固定、无重定向、超时和出口防火墙；服务商清单由 V-10 的真实订阅证据确定，不能先允许任意 URL。
- endpoint 与用户、session、安装实例绑定，禁止无证明跨账号换绑。发送前重查成员、可见性、session、消息状态和通知偏好；通知正文临发送再生成。
- 中国网络可达性是实测事项，不承诺某浏览器必定可达。Sentry 转发只使用服务端固定目的地与项目 id。

**D-066 幂等键绑定操作与请求（补充 D-005）**
- Postgres 的 `idempotency_records` 唯一键包含 actor、operation、target、key，存规范化请求哈希与资源 id；相同键不同请求返回 409，重放前重新鉴权。
- 一般创建键保留 24 小时；消息 `(sender_id, client_id)` 在消息生命周期内唯一，跨会话复用也返回冲突；离线队列 24 小时后不自动重发。编辑用 expectedChangeSeq，已完成的撤回/取消可幂等返回。

**D-067 向量和摘要有内容版本（补充 D-015）**
- 任务携带 content_version、模型版本和维度，写回时确认消息仍有效且版本匹配；检索联表重查授权、删除状态及版本。模型迁移在新索引构建、评测完成后切换，不混用维度。
- 旧任务不能重建已撤回内容，摘要也需来源版本；本地向量性能按真实 ARM 测量，不由桌面耗时折算。

**D-068 重新生成不重做效果（补充 D-036）**
- 仅允许终态且未执行任何业务效果、无待审批的 run；包括提醒、记忆等无需审批的效果。重新校验当前权限和上下文后原位替换，保留稳定的目标消息 id。
- 原回复不作为消息历史保留；旧 run 副本仍按 30 天规则处理。输出达到 20000 Unicode 字符时停止并记录 length 截断，不因 token 预算大于字符上限而写库失败。

**D-069 跨表约束及生产 bootstrap（补充 D-052）**
- 群主与成员 owner 必须一致；转让、最后成员退出、归档恢复有明确事务与约束。附件有效绑定、Agent 内容清理和外键策略见 04。
- `db:bootstrap` 只创建机器人、系统保留名、配置默认值，可在生产幂等执行；`db:seed` 仅创建开发演示数据。不以开发 seed 代替生产初始化。

**D-070 离线数据按账号与会话世代隔离（补充 D-038）**
- Query、IndexedDB、草稿、队列、推送与 SW 消息均带 userId 和登录世代；注销先本地封锁并通知全部标签页，SW 只缓存公共外壳，敏感 HTTP 响应 no-store。
- 重连先验证当前身份、成员世代和幂等键，才发送 24 小时内纯文本队列。首次离线冷启动只显示外壳；已验证的活动标签页可以继续看已载入内容。不能宣称能立即清掉失联设备已下载的数据。

**D-071 一致备份、恢复隔离与目标（取代 D-044 的恢复后直接外发，补充 D-048）**
> 后续D-076/079/084补凭证与委托失效、独立删除journal。缺删除证据不能仅经人工确认解锁；RPO不放宽已确认删除重放要求。
- 不可变对象 key；备份先建立物理删除屏障，再取得数据库一致快照和附件清单，按清单校验对象，全部成功并异地落盘才算成功。失败备份不能替代上一份有效备份。
- 目标 RPO ≤ 24 小时、RTO ≤ 4 小时，以实际演练为准；每 12 小时执行，上一份异地备份快照年龄不能超过 24 小时，否则告警并记目标违约。
- 恢复先禁止模型、邮件、推送和定时外发，清会话/验证令牌、增加恢复世代，核对可能重复执行的任务后人工解锁。物理备份无法判断灾难前已发出的外部效果。

**D-072 健康、网关和旧前端升级（修正 D-045）**
- Docker restart 策略只处理退出，不会因 unhealthy 自动重启。应用内部死锁由独立 watchdog 有限重启；共享依赖故障只告警，不循环重启全部服务。
- HSTS 独立片段加 always，显式覆盖所有 HTTPS location 及错误响应；静态 CSP 与 API 头仍按职责划分。Nginx 1.28 不依赖新版本继承选项。
- 哈希资源保留至少 7 天且至少最近 3 版；API/WS 与上一版客户端兼容，过期客户端提示刷新，不能静默丢草稿。

**D-073 全站容量和背压（补充 D-033、D-052）**
> 后续D-078统一附件单位，D-081将原后台2GiB分为1536MiB worker与512MiB独立media，D-087补AI容量估算；不沿用同worker内解码的实现假设。
- 5 GB 是个人上限，不是给 1000 人预留 5 TB。上线前填写实际可用存储预算，设置预占闸门和磁盘水位；共享宿主机其他站点也计入余量。
- 目标数据集与混合负载、慢连接、重连风暴见 08。媒体、向量、Agent 的并发受同一 worker 2 GB 总预算约束；超限优先暂停向量和新 AI/上传，保留聊天和删除。

**D-074 可访问性是桌面版要求（补充 D-016、D-017）**

## 第二次独立复审后的规划完善（2026-10-01）

用户授权“全面优化完善项目规划”。以下 D-076–D-092 落实 [15 的 R01–R12 和五项一致性问题](15-planning-rereview-2026-10-01.md)，优先于它们明确补充或取代的旧条款。这里只完成设计；AT-25–AT-37、V-18–V-21 仍待实现验证。

**D-076 认证凭证绑定注册实例，服务端一次性消费（补充 D-058、D-059、D-071）**
- 邮箱验证和密码重置使用应用控制的随机 256-bit opaque token，数据库只存哈希及受限邮件投递密文；绑定 user_id、registration_id（普通注册必填）、用途、邮箱摘要、auth_epoch、restore_epoch、有效期和 consumed_at。不得用邮箱查找后来重建的替代账号。
- 默认有效期均为 1 小时；重发使同用户同用途的旧凭证失效。消费、验证事实、邀请确认检查及激活在同一事务中完成；密码重置的密码更新、消费、撤销也必须原子，禁止原生 JWT 回调旁路。
- 链接使用 /verify-email#token=… 或 /reset-password#token=…；页面读取后立即清 fragment，只在内存保留，用户确认后 POST 受控端点。GET 不消费、不激活、不登录，避免邮件预取扫描消费链接。人工验证仍受注册锁及审计约束。
- V-13 必须证明锁定版适配可行；不支持就做受控认证适配，不把默认库行为当作一次性、注册绑定或恢复失效的证据。AT-25 覆盖同邮箱重建、重发、重复、撤销竞态和旧快照。

**D-077 日志只记录白名单字段和规范化路由（补充 D-046、D-072）**
- 应用、Nginx、错误收集统一禁止原始 URL/query/Referer、Cookie、请求体和认证头；路径里的凭证同样不能记录。访问日志只记 route 类别、method、状态、耗时、服务端 requestId 和经信任链验证的 IP。
- 网关未知路由只写 unknown；不能回退到 $request/$request_uri/$uri。错误日志无法安全剥离请求行时，该站点使用丢弃原文错误输出的配置，以脱敏状态指标、上游健康和 requestId 诊断；不得影响其他站点日志。
- Sentry 在事件及 breadcrumb 发送前执行允许字段重建，拒绝 envelope 指定目的地；认证页使用 no-referrer。AT-26 用假哨兵同时验证成功、4xx、413、超时、上游失败、重定向和监控转发。

**D-078 请求按用途预算，先限流读取再解析（补充 D-064、D-072）**
- 普通 JSON 原始 UTF-8 请求体最多 128 KiB；monitoring envelope 最多 256 KiB；单文件流最多 100 MiB 且不能超过 reservation。全版附件大小统一按 MiB/GiB 计算，界面明确单位。
- 网关和应用均在解析前执行字节限额；不信任 Content-Length，无长度流也累计，异常 framing 拒绝。拒绝请求 Content-Encoding 压缩，避免解压放大。普通请求总读取 15 秒、空闲 5 秒；上传总 120 秒、空闲 15 秒。端点可以更严，不能全局放宽。
- 未读完的大请求不反射输入；默认 413、415 或 408，关闭/取消上游读取。M1a 校准最大合法中文正文、Passkey 和审批参数；不够时只调整经证据批准的端点。AT-27 覆盖直连 API 与代理两条路径。

**D-079 请求身份与持久委托分离（补充 D-057、D-061）**
- domain 接受服务端构造的 SessionPrincipal、DelegatedPrincipal 或限定维护动作的 SystemPrincipal，拒绝裸 userId 作为执行凭证。后台 run/未来任务使用持久 delegation，记录来源设备 origin、账号 auth_epoch、restore_epoch、目的、目标、参数哈希、到期和撤销状态；执行时仍检查当前成员/禁言/归档/来源。
- 普通退出、自然 session 过期不撤销已授权任务；明确撤销设备则撤销该 origin 的全部未完成委托。注销其他设备只影响其他 origin；安全性“注销全部设备”、改密、重置、封禁、注销和恢复撤销全部委托。改密可以保留当前登录会话，但也撤销全部旧委托；解封不复活任务。
- run 委托最长 25 小时，审批不延长；批准的定时消息/个人提醒有独立子委托，最长预约 365 天，到点超过 24 小时未执行即 failed。取消父 run 不撤销已提交的未来任务，用户可在任务列表单独取消；删除相关 Agent 会话/注销则全部取消。
- 权限检查在事务锁内；撤销先提交则旧 worker 不得提交新效果，已经发出的模型请求仍结算 usage。完整真值表见 03，AT-28。

**D-080 私有 BYOK 内容的来源限制随派生数据传递（补充 D-034、D-060）**
- 私有 Agent 会话/面板中的 BYOK 请求、输出、附件与派生记忆/摘要标记 byok_private；站点 key 的自动上下文和全部工具查询均排除该类别。复制、摘要、向量命中和恢复不能丢失标签；旧数据缺标签时拒绝作为站点输入。
- key_source 在创建 run 时固定，来源或 scope 切换都新建 context_epoch。改用站点额度是新建空白请求，不重放 BYOK prompt、图片、工具结果或摘要；用户可以主动重新输入。私有记忆默认保留原类别，设置页手动新增默认 byok_private，可逐条明确允许站点助手使用。
- 此保护不改变共享消息的权限：群里主动 @Agent 的消息及群内回复、完整预览并批准的代发内容，是用户明确发布的普通消息；有权用户后续可用站点助手读取，可能进入站点运行审计。只释放发布的内容，不释放原 run、私有推理/工具结果；隐私页说明此边界，鼓励 BYOK 的文案仍只讲好处。
- AT-29 同时验证私有内容不随 key 切换泄露、工具全范围检索不绕过，以及明确发布内容按普通权限可用。

**D-081 固定媒体执行容器，隔离网络和业务凭据（落实 D-064，修正 D-041 的共进程假设）**
- M3 创建独立 media 镜像/容器：network_mode=none、非 root、read_only、cap_drop=ALL、no-new-privileges、默认 seccomp、pids_limit=64、memory/swap 总上限 512 MiB；可写 tmpfs 总 256 MiB，临时文件计入内存上限。不挂载 Docker socket、应用 env、数据库或对象存储卷。
- worker 负责授权、S3 与账本；通过仅两者可访问的 Unix socket 传受限文件字节和固定操作枚举，禁止任意命令、URL、宿主机路径。media 不持有 S3/DB/模型凭据。单并发、单任务 60 秒，终止整个子进程组并清理；协议和输出限额由 worker 独立检查。
- worker 限 1536 MiB，media 限 512 MiB，合计保持原后台 2 GiB 预算；向量 ≤1 GiB 且受余量闸门约束。V-18/AT-30 在真实 Linux/ARM 上验证 IPC、隔离、超时、OOM、资源占用；失败时阻止媒体上线，不退回有凭据的 worker 解码。

**D-082 实体版本与同步游标各司其职（补充 D-056、D-066）**

## M1a 实施决定与实验结论（2026-10-01）

> 以下是 M1a 实施中的决定，均有可重复运行的测试或命令作证据（见 PROGRESS 的 M1a 交接记录）。它们补充或修正对应的旧条款，不改变用户已定的产品方向。

**D-094 认证入口由受控处理器实现，SDK 只转发 Passkey（补充 D-058、D-076，V-13 结论）**
- `/api/auth/*` 前面是精确的 method + path 允许清单（`packages/contracts/src/auth-endpoints.ts`）。注册、登录、退出、改密、邮箱验证与密码重置共 8 个入口由应用自己的处理器实现：先做请求预算、Origin、限流和 zod strict 校验，再经 domain 事务写入；登录用 `auth.api.signInEmail` 完成口令校验与建会话，响应体去掉令牌。只有 7 个 Passkey 路由在严格校验后转发给 SDK。SDK 注册的其余 28 个 (方法, 路径)，包括 `get-session`、`list-sessions`、`revoke-*`、`update-user`、GET 的 `verify-email` 和 `reset-password/:token`，一律 404。
- 原因：① 原生 `get-session`/`list-sessions` 的响应带 `session.token`，等于把 HttpOnly 令牌（以及其他设备的令牌）交给脚本；② SDK 的 `after` 钩子在事务提交之后才执行、拿不到事务句柄，无法在首次 INSERT 关联注册，也无法原子消费凭证；③ 原生验证/重置是 GET 链接加 JWT，预取就会消费，也不能绑定注册实例和 restore_epoch。
- 证据：`test/security/auth-matrix.test.ts` 用匿名、成员、管理员三种身份请求 SDK 注册的全部 39 个 (方法, 路径)，除允许清单外全是 404 且数据库无变化；`test/contract/auth-sdk-endpoints.snapshot.json` 固定 SDK 端点清单，升级后出现新路由会让测试失败；路由变体（大小写、尾斜杠、`%` 编码、双斜杠、`;`、错误方法）全部 404。
- 设备管理改为 `/api/me/devices` 一组接口（列表、撤销单台、注销其他、安全注销全部），以 origin 作设备，不暴露令牌。
- 放弃：透传 SDK 加 after hook 关联注册；启用 admin 插件。

**D-095 不启用 username 插件（补充 D-039）**
- username 由受控注册写入并带 CHECK（`^[a-z0-9_]{3,20}$`），保留名走 contracts 的保留名单和 `username_reservations`；在 SDK 里只声明为 `required: true, input: false` 的用户附加字段。声明还有一个作用：Better Auth 1.7.7 带运行时 Drizzle schema 检查，会拒绝“存在 SDK 从不写入的 NOT NULL 列”，这个检查在升级时也是保险。`display_username` 列不建。
- 原因：插件的增量只有用户名登录（05 已禁止）和 `is-username-available`；它的校验钩子与受控创建重复。

**D-096 注册在一个事务里完成，中间状态保留为可恢复行（落实 D-059，V-13 结论）**
- `registerAccount` 在单个事务中按“邀请人 → 邀请码”的锁序占位（条件更新 `use_count` 与 `invites_used`），写入 registration，账号第一次 INSERT 就带 `registration_id` 并保持 pending，随后建立双向关联、转 confirmed，创建验证凭证和 email work_item，写幂等记录和审计。口令哈希在取锁前计算，并且总会计算，已有邮箱与新邮箱耗时一致。已有邮箱返回与成功相同的通用响应，不占名额；用户名冲突返回 409。`reserved`/`account_created` 状态与对账器（`reconcileRegistrations`）仍保留，用来恢复多步创建。
- 证据（AT-05）：在 registration / accounts / auth_challenges / work_items / audit_logs 各自的 INSERT 上用触发器注入失败，整体回滚、名额不变，同一请求在故障消除后仍可成功；同一单次码 6 个并发恰好 1 人成功；额度 2 的成员 5 个并发恰好 2 人；两个码抢同一邮箱只建 1 个账号、只占 1 个名额；对账器的释放与退额度只发生一次。
- 放弃：延迟外键的多步流程（共享事务做得到时不需要）；after hook。

**D-097 数据库拥有者账号与应用账号分离（落实 04 约定）**
- 新增 `DATABASE_OWNER_URL(_TEST)`；`DATABASE_URL(_TEST)` 是无特权的 `chatapp_app`。迁移、bootstrap、CLI、测试清表用拥有者；`db:migrate` 迁移后幂等创建并授权应用账号（默认权限覆盖以后新增的表）。API 与 worker 启动自检：未 bootstrap 就拒绝启动，生产里账号有特权也拒绝。`bun run setup` 会把旧布局一次性转成新布局并补齐模板新增的键。
- 证据：集成测试用应用账号连接，并断言它不能建表、改表、truncate、建角色、读迁移记录。

**D-098 限流用自有 Valkey 限流器，失败即关闭（落实 SEC-11；修正 03/07 里“Better Auth 限流计数存 Valkey”的说法）**
- 固定窗口，INCR 与 PEXPIRE 在同一个 Lua 脚本里；键含环境；主体是 IPv6 按 /64 分组后的 IP，或账号邮箱的 HMAC 摘要。Valkey 不可用时返回 503 + Retry-After，不放行。不使用 Better Auth 内置限流，也不使用 `secondaryStorage`（它会让会话读取走缓存，违背“每次请求查当前会话”）。
- 匿名“请求”类端点（验证重发、找回）至少耗时 300 ms，已有账号与未知邮箱的响应时间相同。

**D-099 `users.account_source` 与 INV-18 的 CHECK**
- `account_source ∈ {registration, cli, bootstrap}`。CHECK：active 必须 email_verified；只有 registration 来源的账号带 registration_id，并且从第一次 INSERT 起就带。CLI/bootstrap 是 INV-18 里“受审计的例外”，创建时写审计行。

**D-100 会话与 Cookie 的实现结论（V-04、V-05、V-13）**
- UUID（V-04）：`advanced.database.generateId` 注入 UUIDv7 后，SDK 创建的行（会话、passkey 挑战）用 uuid 主键工作正常；Drizzle 适配器要求 `usePlural`，并可用 `transaction: true` 让整个原生流程共享一个事务。
- Cookie（V-05）：SDK 默认会生成 `__Secure-` 前缀。要得到 `__Host-`，必须 `useSecureCookies: false`，自己给出名字 `__Host-chatapp.session_token` 并显式设置 `secure`、`path=/`、不设 Domain。https 下实测通过；http 开发环境使用无前缀名。M7 在真实 Nginx 下再复核。
- 会话令牌在库里是明文，Cookie 值是 `令牌.签名`；因此备份加密与数据库访问限制是硬性要求（04 已写）。
- 会话带 `auth_epoch` 与 `authorization_origin_id`（SDK 的 additionalFields，`input: false`）：`session.create.before` 钩子在建会话时同时做账号状态闸门并创建 origin；每次请求再由 `resolveSessionPrincipal` 复核账号状态、epoch、origin 与 restore_epoch，写入路径在事务里用 `lockAndRevalidate`（先锁用户行）再次复核。

**D-101 请求预算、路径规范化与日志的实现（落实 D-077、D-078）**
- 请求预算中间件在任何解析之前读取并计数：不信 Content-Length，总时限 15 s、空闲 5 s，超限 413，压缩 415，Content-Type 只认 UTF-8 JSON，Content-Length 与 Transfer-Encoding 同时出现 400，非法 UTF-8 或 JSON 422。读完后把文本预填进 Hono 的 `bodyCache`，校验器与处理器不再碰原始流（有测试固定这一行为）。Bun 的 `maxRequestBodySize` 暂设 1 MiB；M3 上传需要为该路由放宽，并保持流式计数。
- 路径守卫：路径含 `%`、`//` 或反斜杠一律 404；点段在 URL 解析时已被规范化，所有层看到同一个 URL，不存在解析差异。
- 日志：pino 只接受白名单字段；路由记匹配到的模式，通配则记 `unknown`；Drizzle 包装的错误消息里带 SQL 和参数值，所以错误只记类名、SQLSTATE、约束名和栈帧。AT-26 的哨兵测试覆盖成功、4xx、413、415、422、429 与 500。

**D-102 WebSocket 网关：先接受升级再按码关闭，持久撤权加 5 秒复核（落实 05 第 4 节）**
- Origin、限流和会话在升级前判定，随后接受升级并以 4403/4401/4429/1013 关闭（浏览器看不到被拒升级的 HTTP 状态）。连接绑定 sessionId、originId 与 authEpoch。撤销（退出、设备、改密、重置）在同一事务里写 `realtime` work_item，worker 的 dispatcher 发布到 `events:{env}`，网关立即复核（真实进程走查中退出后 58 ms 关闭，集成测试要求 < 2 s）；hint 丢失时每 5 秒批量复核（实测 ≤ 6 s），复核查询失败即 1013 关闭。帧 64 KiB、每 10 秒 200 条、每用户 10 连接、25 秒心跳、60 秒无响应 4408、256 KiB 发送缓冲。
- 未做：topic 订阅与 Hub（M2），presence/typing（M2b）。

**D-103 隔离故障环境的实现（落实 D-085，AT-34）**
- `compose.test.yml` 每次运行一个独立 compose 项目（`chatapp-test-<runId>`），随机密码，每次运行选定后固定的随机回环端口（必须固定：容器重启后 Docker 会重新分配随机端口）；清单 `.test-runs/<runId>/manifest.json` 权限 600、不入库。注入前逐项验证：`APP_ENV=test`、project 与 run-id 标签、完整容器 id、卷与网络标签、只绑 127.0.0.1 且不含开发端口、库名 `chatapp_test`、在三个服务里读回的随机实例标记；动作只经 `act()`，每次重新核对标签；清理只对该项目执行 `compose down -v`，核验失败就什么也不删，也不使用 prune。
- 证据：`bun run test:fault`（11 项）。开发服务带哨兵，对测试实例 kill Postgres、FLUSHALL Valkey、重启，开发容器的 id 与 StartedAt、哨兵都不变；伪造目标（APP_ENV、开发容器 id、开发端口、错误项目或 run-id、库名、实例标记、开发卷、清单权限与位置）全部被拒且无副作用；对列出开发卷的伪造清单做清理被拒。
- 已观察到：Docker Desktop 重启后测试容器处于 Exited，清理仍必须成功，所以拆除时允许已停止的容器（只放宽端口检查，标签、id、卷、网络检查不放宽）。
- 已观察到（2026-10-02）：有一次，Docker Desktop 把 Garage 单文件绑定挂载的 `Source` 报成它的内部路径 `/run/desktop/mnt/host/wsl/docker-desktop-bind-mounts/...`，自检按设计拒绝，半起的实例按项目名拆除，没有残留；同一环境里 `docker run`/`compose` 的探针都报告原始路径，几分钟后重跑 11 项全部通过，原因未查明。结论：不放宽“绑定挂载必须在本次运行目录内”这一检查（它防的是对错误容器做破坏性操作，误拒绝的代价只是重跑），只在拒绝信息里提示重跑。

**D-106 gitleaks：测试夹具白名单（2026-10-02）**
- 首次远端 `security` 运行里，gitleaks 8.24.3 对 7 个新提交报了 13 处 `generic-api-key`，全部在测试文件里，只涉及三个字面值：假密码 `tomato-umbrella-47-lantern`（9 处）、测试应用用的占位 secret（3 处）和占位加密密钥（1 处）；是变量名里的 `password`/`SECRET` 触发了通用规则。核对结果：这三个值都不是任何环境的真实值（与 `.env.local` 里密钥类取值逐个比对，一个都不相同），只出现在测试代码里。
- 处理：仓库根目录新增 `.gitleaks.toml`，保留全部默认规则（`useDefault`），只对这三个**精确字面值**做白名单，不按路径放行，所以真实密钥误写进测试文件仍会被发现。历史提交里的这些行没法用行内注释放行，所以用配置；语法按 CI 实际使用的 8.24.3 写（`[allowlist]`）。
- `security` 工作流加了 `workflow_dispatch`：push 与 pull_request 只扫描各自的提交，手动触发和每周定时才扫描整个历史，用它来验证这份配置。
- 约定：测试需要新的“像密钥”的字面值时，优先在运行时生成；必须写死时加行内 `gitleaks:allow` 并写明用途，不要放宽这份白名单。
