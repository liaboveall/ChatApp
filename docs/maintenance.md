## 2026-11-13：生产网关改为公开访问

收到邀请码的人都无法打开站点。原因是生产 Nginx 仍按封闭部署时的 IP 允许清单拒绝其他来源，请求还没到达应用、看不到注册页，就被直接返回 403。应用容器一直健康，本人在允许清单之外的网络上同样看到 403。维护者决定改为公开访问，注册仍需邀请码和邮箱验证。

- `production.ts edge DIR --public` 生成 `allow all;`。`--public` 只能单独使用，不能与地址混用；IP/CIDR 清单的校验（拒绝 `/0`、拒绝注入）和默认的 `deny all;` 不变。
- `configtest` 只接受这两种策略，并在结果中给出 `accessPolicy`。单元测试覆盖默认封闭、拒绝宽泛或混用参数、精确的清单输出，以及切换到公开再恢复封闭。
- 生产已按同样的字节安装 `allow all;`；`chatapp-production` 站点文件只有 access include 的注释一行变化，与仓库保持一致。原文件已备份在服务器 root 目录。以允许清单之外的来源访问，`/`、`/api/readyz` 和 `/privacy` 均返回 200，`/ws` 不带 Upgrade 时返回 426。
- 本地 `bun run check` 通过：后端 / 脚本 703 项，前端 750 项。改动只涉及部署工具、文档和 Nginx 注释，没有运行浏览器组件回归和 M3 媒体链，由 CI 执行。

旧版部署轮次的 postflight 断言封闭策略，并要求清单外来源返回 403；下一轮部署须先改为按实际策略核验。应用镜像和数据库没有变化。

## 2026-11-14：后端性能与结构整理

前端重构之后对后端做的一轮整理。先分区审读 `apps/server` 与 `packages/db`，只改经核实的问题；行为修复先写会失败的测试再改。改动提交在 `feat/liquid-glass-redesign`（基于 `a46ac73`，该分支此前没有改过任何后端文件），随界面重构一起经 PR 合并到 `main`。

**请求与鉴权**

- 会话守卫对一个请求只执行一次。Hono 的 `/api/x/*` 也匹配 `/api/x`，各路由模块又分别登记，导致 `GET /api/me`、`/api/conversations`、`/api/notifications`、`/api/users`、`/api/reminders`、`/api/scheduled-messages` 鉴权两次，`/api/me/memories` 三次；每次多一轮 session 查询，并重复计入每人限流（记忆写入的专属限额也被计两次）。守卫现在发现 principal 已建立就放行，各模块只登记一个路径模式。
- 写事务里对 origin 与 session 的复核由两条语句并为一条；每请求与每连接的会话校验只取用到的列，不再读整行用户资料或 session 令牌。
- 限流脚本注册为命令（EVALSHA），多项限流一次往返完成。

**消息与同步**

- 发送：新消息不再回读自身并清空不存在的向量；提及写入由三条语句减为一条查询加一条插入；成员行的已读位置或取消隐藏与版本号在同一条语句写入；私信对端只读一次；没有提及时不查助手账号。
- 读取：非加锁的权限加载为一条语句；会话详情一次查询；sync heads 单条语句、不开事务；变更流和消息详情把“对我隐藏”并入消息查询；消息分页多取一行，省去一到两次探测。

**后台任务与实时**

- dispatcher：扫描期间到达的唤醒不再丢失；领满一批立即续扫；worker 的消费者完成任务后唤醒它；realtime 提示批量标记完成。队列与消费者挂上 `error` / `failed` 监听，错误经允许字段日志输出；停止时各消费者并行关闭。
- 一条消息的推送任务为全部收件人批量写入；“全部标为已读”由每条两条语句改为总共三条。
- 网关：客户端在握手读取期间自行断开时不再被登记为在线；presence 续期一次发出并防重入；Agent 文本增量的授权按批读取全部在线成员的成员关系。

**缺陷修复（各有回归测试）**

- 新举报的通知始终显示为“来源不可见”，现按规格对管理员给出 `reportId`；不再是管理员的人看不到也不计数。
- Agent 用量：自带密钥的未知结果调用被从站点额度的预占中扣减，数值变负，前端按契约解析失败。
- 因成员变化被取消的运行保留“等待审批”标记，既不能审批也不能重新生成。
- 准备提醒或定时消息时用的是固定的 100，而不是站点设置的任务上限。
- 存储清理中一个附件因其他删除未结算而被拒绝时，整轮中止，到期对象不删除、容量不释放。
- 预算提醒会发给被封禁或未验证的管理员；管理员筛选条件统一为一处。

**结构**

- 路由共用的请求体、成功响应与幂等键读取集中在 `http/routes/helpers.ts`；`config/domain.ts` 统一生成交给 domain 的配置（此前三个入口把含认证 SDK 密钥的整个 `auth` 对象传入）；附件预览种类的 SQL 片段、通知偏好换算、邀请码哈希各归一处。

## 2026-11-14：删除受理卡住，后台派发停摆约半小时

上线当晚（以下为 UTC+8）维护者报告三件事：一条带长代码行的消息撑出了聊天区；两人几乎同时 @助手 的三条消息只有最后一条得到回复；之后撤回、删除一直不生效。后两件是同一个故障。

**经过（服务器记录）**

| 时间 | 发生了什么 |
| --- | --- |
| 20:00:56–20:01:29 | 两次上传被取消，产生两项待受理的附件删除 |
| 20:02:15 起 | worker 的删除受理每约 35 秒失败一次（`ERR_POSTGRES_IDLE_TIMEOUT`）；20:04:10 起 dispatcher、对账、附件清理在同一秒一起失败 |
| 20:03:50、20:04:01 | 两条 @助手：到 20:04:40 才被领取，模型调用进行中，于 20:05:16 随连接被关而失败（`MODEL_REQUEST_FAILED`）；20:04:40 的第三条 4 秒内完成，恰好落在两次失败之间 |
| 20:12:56 | 撤回一条消息，停在待受理；它的通知任务尚未派发，随消息一起被冻结 |
| 20:13:16–20:24:49 | dispatcher 每次领取都因这一行报 23514，实时提示、推送、助手任务全部不动 |
| 20:17:42、20:24:49、20:31:45 | 三项删除先后受理并应用，之后恢复正常；20:16:32 的 @助手 在 20:25:41 才开始，并在 20:26:16 同样失败 |

**原因**（都在这次上线之前就存在；上一次有删除操作是 11-09）

1. 受理一次删除要沿异地 journal 的哈希链把自保留下限以来的全部记录读一遍，而且读两遍。链上已有 2828 条，逐条串行读取要几分钟。
2. 受理期间用一个事务持有 advisory lock。数据库客户端会关闭 30 秒没有流量的连接，事务内也一样：锁随连接丢失，而受理还在继续；5 秒后下一轮又开始，多轮受理同时改写链头，互相作废。第一项删除因此花了 16 分钟。
3. 每个维护任务也各用一个这样的事务，worker 的连接池只有 6 个连接，恰好能被它们占满。此时排在后面的语句被挂到空闲连接上，连接被关时一起失败，包括正在流式输出的助手请求。
4. 删除待受理期间，目标及其工作项被数据库冻结。领取语句里只要有一行被拒，整条语句失败，所以一个被冻结的通知任务挡住了全部后台派发。

当天上线的改动没有引入以上任何一条，但有一处同类弱点：实时提示改为批量标记完成后，一行被拒同样会让整批失败。

**修复**

- 持锁事务在等待外部 I/O 期间发心跳（`keepAlive`），锁和连接保持到工作结束；worker 连接池由 6 改为 12。
- journal 的长跨度读取改为并行取回后逐条校验，同一次受理的第二遍只读新增部分；校验规则不变。
- 领取与过期回收跳过被冻结的工作项；批量完成被拒时逐条完成。
- 消息列不再被不换行的内容撑宽；@提及改为玻璃珠样式；代码块重新打磨，消息里 Markdown 的样式不再受渲染库自带类名的影响（[设计规范](02-design-system.md) 第 5 节，经过见第 8 节同日的三条记录）。

**验证**：后端新增 10 项测试——客户端空闲超时与心跳 3 项（在真实 PostgreSQL 上：等待超过空闲超时的持锁事务会丢掉连接和锁；有心跳时锁保持到工作结束；心跳随工作结束而停，工作抛错时也一样），长链读取 4 项，冻结工作项 3 项；冻结与读取相关的用例在旧实现上确认失败。前端：消息布局的浏览器用例 1 项，对比度检查新增 2 组、覆盖 9 种强调色的深浅主题，@提及的像素行对齐 20 项，Markdown 样式独立性 8 项。本地用真实模型重放了当晚的操作：两个账号同一时刻 @助手 三条，三条都在约 1 秒内答完，随后撤回、删除各约 30 毫秒。本地没有开启异地 journal，所以这只说明并发的助手请求本身没有问题；受理耗时在生产上的实际值要等修复上线后的第一次删除才有。重放时还确认了一个容易被当成故障的既定行为：助手回答期间，会话里被它用作来源的消息一旦被撤回、编辑或删除，进行中的请求立即以 `CONTEXT_CHANGED` 结束（[Agent 规格](06-agent.md) 的来源清单），界面显示“请求未完成”。

**仍然成立的限制**：受理一次删除仍要读完整条链，只是从几分钟降到几秒，并随 35 天窗口内的删除数量线性增长。让它与历史长度无关需要在进程内保留已校验的链（见上一节“留待决定”的第一条），那会推迟发现旧记录丢失的时间，属于 D-084 的取舍，没有在这次修复里做。
