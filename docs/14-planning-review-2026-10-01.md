**总体判断**

| 维度 | 判断 | 理由 |
|---|---|---|
| 产品方向 | 可以保留 | 邀请制、桌面优先、中文优先、可审批的 Agent，有明确边界 |
| 技术栈 | 没有推倒重选的依据 | 单体 API 加 worker、Postgres 为事实来源，适合所写规模；主要风险来自组合机制 |
| 数据与权限 | 需要先补关键协议 | 原始消息权限有定义，广播、引用、模型历史和管理插件还没有完整闭环 |
| 实时与异步可靠性 | 当前保证不足 | 跳号检测不能发现尾部丢事件，提交后派生任务和权限事件没有可靠交付 |
| Agent | 不能仅凭账本认定可恢复 | 审批续跑、取消、并发执行、上下文沿用和预算预占仍需定义 |
| 测试与上线 | 框架清楚，证据尚未建立 | 真实依赖、浏览器测试、恢复演练值得保留，但测试故障点和通过条件不够完整 |
| 设计 | 方向可用，令牌仍需修正 | 已测得默认消息气泡对比度不足；桌面缩放需求不能随手机布局一起推迟 |
| 交付安排 | 可作为功能分解，尚非工期计划 | 缺少估算、关键风险实验前置、失败退路和可量化的试用成功标准 |

值得保留的设计包括：身份来自服务端会话；统一 domain 与授权；HTTP 写入和 WebSocket 推送分工；`seq` 与 `change_seq` 分离；副作用与效果账本同事务；真实基础设施测试；旧缺陷映射；生产彩排、ARM 冒烟及备份恢复演练。不需要为了修正下面的问题引入微服务或更换全部组件。

**高优先级问题**

**F01 P1 事务提交后的事件和任务没有完整可靠交付机制**

依据：03 第 28–30、179–212、319–330 行；12 的 D-025、D-043、D-044。

反例：客户端已同步到 10；消息 11 已提交，但发布失败；之后没人发消息，连接和页面前台状态一直不变。客户端没有收到 12，便不会检测到跳号，也没有重连或回到前台来触发对账。消息在数据库中存在，接收者仍可无限期看不到。

另一个窗口在消息提交与创建 Agent run、通知任务之间。进程在这里退出，数据库甚至没有 run 可供 reconcile 恢复。当前对账清单也没有覆盖丢失的媒体处理、邮件发送、通知派生和向量更新任务。“Valkey 的东西都能重建”因此尚未由设计保证。[Valkey 官方文档](https://valkey.io/topics/pubsub/)明确说明 Pub/Sub 不持久化，订阅者错过后不会补送。

建议将需要保证执行的事件或工作意图与业务变更同事务持久化，使用小型 outbox 或等价的持久工作表，再由 dispatcher 重试和消费者去重。实时提示另加有上限的周期对账，明确最大可接受滞后。若继续不用 outbox，必须逐类写出恢复扫描依据和执行去重规则，不能只靠客户端补消息。

验收：提交后立即杀 API；单独丢最后一个事件；Valkey 断开后恢复；清空隔离测试实例的队列后，媒体、邮件、通知和 Agent 均能按规定恢复。最晚阶段：M1a 设计机制，M2a 落实消息，后续队列沿用。

**F02 P1 权限撤销依赖可能丢失的事件，泄露窗口没有所声称的上界**

依据：03 第 281–311 行；05 第 179–182 行；07 SEC-03。

成员移出后依靠 `user:*` 事件退订。该事件一旦丢失，登录会话本身仍有效，五分钟的 session 复核也不会发现成员关系已删除，被移出者可能继续接收群消息。03 接受的是“毫秒级”窗口，当前机制却可能把它扩大到连接结束。会话注销事件丢失时，也只能由五分钟复核兜底，与“几秒内断开”不同。

建议为授权变化引入可核对的版本和可靠通知；网关失去事件总线同步状态时停止敏感推送或断开重建订阅。区分登录凭证有效期、成员关系版本和内容可见边界。客户端收到 remove 后自愿清缓存不能成为服务端授权保障。

HTTP 写入也应定义授权检查与业务事务之间的并发规则：03 的发送流程先鉴权再进入事务，如果期间发生踢人、禁言或归档，就需要在受锁保护的事务中复核，避免授权结果已经失效仍提交消息。

验收：仅丢弃退群、踢人、封禁和注销事件，保持 WebSocket 在线，测量最后一次能收到受限内容的时间；按确定的上限断言。最晚阶段：M1a、M2a。

**F03 P1 按会话广播同一份消息内容不能覆盖加入竞态和引用权限**

依据：03 第 194、270–279、305–307 行；04 INV-09、INV-12；05 第 64–83、220–234 行。

两个独立反例：一是消息 11 提交后暂停发布，新成员加入并取得 `visible_from_seq=11`，随后才发布完整的 `message.created`。新成员已经订阅，会收到自己不应看到的消息 11。二是新成员加入后，老成员发送消息 12，引用旧消息 5。消息 12 可见，但同一广播 DTO 中面向老成员生成的 `replyTo.excerpt` 对新成员不可见。

现有保护只对“被更新消息本身的 seq”做判断，不能解决以上情况。Agent 增量还明确允许加入后再发送最多一秒，与严格的历史不可见承诺直接冲突。

建议广播不含个性化摘要的变更提示，再按权限拉取；或由网关按成员版本及可见水位过滤每个接收者，并单独投影引用。创建、编辑、流式、会话预览都要适用。安全边界必须在发送时成立，不能只在生成 payload 时成立。

验收：用可控屏障安排“提交消息—加入成员—发布消息”；新消息引用旧消息；流式过程中加入；退出后重新加入。检查原始 WS 帧，而不只是 UI 是否隐藏。最晚阶段：M2a，M4 扩展流式。

**F04 P1 Better Auth 管理插件的原生权限没有收口**

依据：11 第 96–99 行启用 admin 插件；05 第 92 行挂载 `ALL /api/auth/*`；12 D-039；01 第 317–319 行。

已有收口针对注册、普通 `update-user`、用户名登录和账号删除，但未覆盖 admin 插件。[官方文档](https://better-auth.com/docs/plugins/admin)列有代用户登录、设置用户密码、修改用户、创建用户和硬删除用户等能力。若按默认权限挂载，站点管理员可以取得普通用户身份，再通过“本人接口”读取私聊或自带 key 的运行详情；也可能绕过自己的账号注销、邀请、审计规则。

建议给原生认证端点制定明确允许清单；禁用 impersonation、任意设置他人密码或邮箱、原生硬删除等不符合产品规则的能力。扩展字段如 role、is_bot、限额、验证状态必须禁止普通请求赋值。管理员受限的承诺应明确指应用角色权限，不应被解释为对控制服务器和数据库的运维者提供密码学隔离。

验收：直接请求原生端点，覆盖普通用户、站点管理员、机器人和已注销账号；不能只测试后台页面有没有按钮。最晚阶段：M1a。

**F05 P1 邀请占用和账号创建之间存在未定义的跨事务故障窗口**

依据：04 第 79–98 行；12 D-040；11 第 100–120 行。

先创建 pending 占用，再由认证库创建账号，成功后才填 `user_id` 并 confirmed。账号已经提交、确认占用之前进程退出时，pending 仍没有账号关联；清理器释放名额后，账号却可能仍然存在并完成邮箱验证。同一邀请码便可能继续被使用。当前并发计数测试不能覆盖这个窗口。

建议优先验证认证 adapter 能否共享事务；不能共享时，设计可恢复的注册状态机，用稳定 registration id 关联占用和账号，未最终确认的账号不得激活。释放前必须能判断是否存在已创建账号；邮件验证、撤销未验证注册、七天清理也要通过条件更新或锁串行化。

验收：分别在占用、账号提交、关联确认前后崩溃；验证与撤销并发；重试注册。最后账号、邀请码次数、邀请人名额必须一致。最晚阶段：M1a 的 V-13。

**F06 P1 Agent 的读取范围尚未覆盖历史上下文和输出接收者**

依据：06 第 31–43、198–221 行；04 第 129、314–325、360–362 行；01 第 152–156 行。

确定的设计缺口：同一个面板对话可从“我的全部会话”切回“只看当前会话”，但历史、摘要和已保存工具结果可能已经含有其他私聊。仅限制本次可用工具不会让模型忘掉这些内容。审批续跑期间退群或重新加入，直接加载旧 `agent_run_states.messages` 也可能带回当前已无权新读的消息。

另一个必须明确的产品边界：老成员在群里让 Agent 总结自己的旧历史，新成员虽然不能读原始消息，却能看到新生成的总结。若“历史不可见”也保护内容来源，就必须限制共享输出的输入范围；若只禁止直接访问旧消息，则要明确承认老成员主动让助手转述的行为。现在文档没有作此区分。

建议为上下文记录来源和权限范围，缩小 scope 时建立新的上下文或重建经过过滤的历史；恢复前重新校验来源。共享输出若要保护旧历史，可限制为全部接收者共同可见的消息，并处理运行中新增成员的情况。

验收：先全范围读取私聊再缩小范围；暂停后退群、重入、封禁；老成员总结历史时新成员加入。最晚阶段：M4，M5 扩展恢复和摘要。

**F07 P1 Agent 审批续跑和取消尚不是一个完整的持久状态机**

依据：06 第 101–153 行；04 第 294–333 行；03 第 323–333 行。

审批后“放入新任务”没有规定 run 必须在哪个事务转回可恢复状态。若仍是 awaiting_approval、审批已经 approved、入队前崩溃，现有 reconcile 只恢复 queued 和超时 running，可能永远不续跑。原任务完成后保留一天，而对账使用 runId 作为 jobId；若续跑也复用它，会被已完成但仍保留的任务挡住。[BullMQ 文档](https://docs.bullmq.io/guide/jobs/job-ids)说明相同 jobId 的任务仍存在时不会重新添加。

取消只写 Valkey，与数据库唯一事实来源冲突；run/step/state/approval 的原子提交边界、同一 run 的独占执行、旧 worker 恢复后是否还能写入，以及每次审批续跑新建输出消息的唯一标识，都未定义。已有 `agent_effects` 能保护同事务业务效果，不能单独解决这些状态问题。

建议持久化 execution generation、续跑序号、取消请求和执行租约版本；状态迁移用条件更新。任务 id 区分每次合法续跑，业务效果 id 在重试时保持稳定；旧执行者不得覆盖新状态。效果提交前再次检查运行状态和权限。

验收：审批提交后入队前崩溃；原 job 仍保留时批准；取消后 Valkey 重启；两个 worker 竞争同一 run；审批续跑创建新回复后立刻崩溃。最晚阶段：M4 设计状态机，M5a 完整落实。

**F08 P1 预算是事后检查，尚不能兑现硬上限**

依据：06 第 102–108、223–238 行；04 第 352–354 行。

四个并发 run 都可以在余额尚未耗尽时通过检查，各自调用模型后才记账；任一调用的成本可能超过剩余预算。月度统计还允许缓存一分钟。模型已完成收费、usage 尚未持久化时崩溃，重试可能再次收费并漏记第一次。等待审批跨越业务日或月份时，也没有明确归属规则。

建议明确预算是软阈值还是硬控制。如果坚持上限，就在调用前原子预占输入和最大输出费用，调用后结算并释放差额；记账以调用尝试为唯一标识。无法确认结果的外部调用保守占用并对账，不能承诺供应商绝不计费或精确恰好一次。明确重试、思考 token、跨日及取消后的费用归属。

验收：余额仅够一次调用时四路并发；usage 写入前崩溃；月底暂停次月批准；取消时仍收到供应商 usage。最晚阶段：M4。

**F09 P1 删除和保留期没有覆盖所有内容副本**

依据：01 第 191、195、286–297 行；03 第 218–221、327 行；04 第 327–348、360–362、401–416 行。

“附件文件立即清除”与“标记 deleting、后台每小时清理”不同。逻辑上立即拒绝访问可以实现，但物理删除需要有单独时限和失败重试。30 天内容清理只列出了 run_states 与 steps.payload，没有覆盖可能带正文的 `agent_effects.result`、审批 args/edited_args、定时消息正文和滚动摘要。若继续保留这些字段，清空两张表不等于运行内容已删除。

建议逐一列出原始内容、运行副本、派生摘要、通知 payload、对象文件、客户端缓存和备份的生命周期。效果账本优先只保留去重必需的最小结果；敏感内容按规定脱敏或清空。注销时同步处理活动 run、审批、提醒和定时消息，防止注销后继续执行。说明中区分立即不可读、后台物理删除和备份轮换。

验收：构造含同一标识正文的所有副本，执行撤回、删除 Agent 会话、注销和到期清理，分别检查读取权限、数据库字段和对象是否还存在。最晚阶段：M3 建机制，M4–M7 扩展。

**F10 P1 上传在配额 数据库和对象存储之间缺少恢复机制及处理资源上限**

依据：03 第 225–238 行；04 第 236–260 行；07 SEC-07；10 第 37 行。

流程先预占配额、写 S3、再创建附件记录。中途断流或崩溃，可能留下已占配额却无附件记录，或 S3 已有对象却无行可清理。图片重编码、视频重新封装后大小可能变化，但配额按上传大小占用，`size_bytes`、处理后 sha256 和释放基准没有统一。数据库事务不能原子回滚已经发生的对象写入。

此外，压缩文件大小并不限制解码后像素数、GIF 帧数、处理时长和内存。两个 media 并发与本地向量模型共享 2 GB worker，更容易被合法格式的极端文件耗尽资源。

建议先持久化 upload reservation 和临时对象身份，再接收数据；完成、失败和超时都能幂等结算。区分原始字节、处理后字节和计费字节，定期对账。限制像素、帧数、媒体时长、解码内存及运行时间，使用受限的媒体子进程并限制其网络访问。

验收：无 Content-Length、截断上传、每个阶段崩溃、重复重试、输出变大、超高像素和长动画；配额最终准确且 API 仍能服务。最晚阶段：M3。

**F11 P1 浏览器推送已引入服务端访问用户提供地址的入口**

依据：05 第 163 行；04 第 276–282 行；03 第 325 行；07 SEC-23。

SEC-23 认为服务端抓取用户 URL 是 v1.1 才出现的风险，但 M6 接受推送订阅 endpoint，并由服务端请求它。[web-push 官方接口](https://github.com/web-push-libs/web-push)使用订阅中的 endpoint 发送通知。规划没有规定端点来源、协议、DNS 解析结果、内网地址和重定向防护，因此 SSRF 防线不能延后。

建议推送注册和发送都限制为经验证的浏览器推送服务，校验 HTTPS、解析后的地址及目标变化，设置超时和出口限制。Sentry 转发也固定服务端目的地，不能接受任意转发地址。发送时重新检查成员关系、消息状态、session 和通知偏好；排队时合法不等于发送时合法。明确通知已经送达外部推送服务后无法保证撤回。

验收：内网和回环 endpoint、DNS 变化、订阅换绑、排队后退群或撤回消息、注销设备后任务重试。最晚阶段：M6，M7 扩展监控转发。

**需要新增的故障验收清单**

1. 数据提交后、事件发布前 API 退出；仅最后一条消息的事件丢失。
2. 退订事件丢失；Valkey 订阅连接重连，但用户 WebSocket 未重连。
3. 发消息提交后加入新成员；新消息引用入群前消息；Agent 流式中加入。
4. 直接调用认证插件的管理、代登、改密码、删除和扩展字段接口。
5. 注册在占用、创建、确认三个阶段退出；验证和撤销同一注册并发。
6. 审批已写库但未入队；原 job 仍保留时续跑；同一 run 两个执行者。
7. 取消后重启队列；退群后恢复 Agent；scope 缩小但历史已含私聊。
8. 最后一笔预算并发竞争；模型收费后记账前崩溃。
9. 上传断流、孤儿对象、配额回收；撤回后旧媒体或向量任务才完成。
10. 用户 A 退出后用户 B 在同一浏览器登录，检查草稿、附件缓存、离线队列和推送。
11. 数据库快照与对象备份期间并发删除；恢复旧备份后避免重发定时任务。
12. 旧库升级、旧前端仍打开、慢 WebSocket、重连风暴、图片处理和向量索引同时运行。

以上先用确定性测试验证系统边界，再用真实模型评测任务质量。测试必须针对实现执行；本次最小逻辑模型只是证明文档中的机制存在反例。

**建议采用的完成标准**
