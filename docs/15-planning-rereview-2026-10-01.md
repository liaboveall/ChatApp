**R01 邮箱验证令牌需要绑定注册实例**

依据：[04 数据模型](04-data-model.md) 第 83–101 行允许撤销未验证账号并释放邮箱；[05 接口](05-api-and-realtime.md) 第 105–116 行要求单次短期验证令牌；[10 部署](10-deployment.md) 第 136–140 行要求恢复时失效验证凭证。

我核对了规划所选 [Better Auth 1.7.6 的邮箱验证源码](https://github.com/better-auth/better-auth/blob/v1.7.6/packages/better-auth/src/api/routes/email-verification.ts)。默认令牌是携带邮箱的签名 JWT，验证时再按邮箱查找用户；这个默认路径没有绑定 ChatApp 的 `registration_id`，也不依靠 `verifications` 行消费这枚令牌。

由此构造的反例是：账号 A 注册并收到验证邮件；邀请人撤销 A；同一邮箱注册账号 B；用户随后点击 A 的旧链接。若直接沿用默认回调，链接会找到 B。只检查 B 的邀请已确认、给当前 registration 加锁，不能证明链接属于 B。如果 B 的密码由另一人设置，还会产生账号安全风险。这是基于上游源码的设计反例，尚未在 ChatApp 中运行。

建议定义受控验证凭证，绑定 `user_id`、`registration_id`、用途、有效期、一次性标识及恢复世代；验证、消费与激活在同一受锁保护的流程中完成。可以包装原生端点或定制适配器，不能假定补一个 after hook 或清空 `verifications` 就已满足撤销要求。

验收应新增：旧链接遇到同邮箱重新注册必须失败；重复消费只产生一个结果；撤销和验证并发；恢复旧快照后旧验证凭证失效。将这些加入 V-13、AT-05、AT-18 的具体用例。

**R02 禁止记录令牌需要覆盖网关的完整请求地址**

依据：[07 安全](07-security.md) SEC-19 禁止日志写令牌和正文；[10 部署](10-deployment.md) 第 91 行只说明邀请码放在 fragment，因此不会进入访问日志。

这个说明不能覆盖邮箱验证、密码重置以及 `GET /api/search/messages?query=...`。Better Auth 的验证链接带 token；[Nginx 默认 combined 日志格式](https://nginx.org/en/docs/http/ngx_http_log_module.html)记录完整请求行和 Referer。如果按目前的部署要点直接启用默认访问日志，认证令牌或搜索文本仍可能落盘，应用层 pino 的字段过滤不会清除另一份网关日志。

建议明确认证和搜索路由的日志模板：记录规范化路由、状态和 requestId，过滤查询参数及路径中的令牌；敏感页面控制 Referer。应用错误、网关错误、Sentry request URL 和重定向链一起检查。不能只移除 query，因为部分认证流程可能把令牌放在 path。

验收使用人工哨兵字符串走验证、重置、搜索的成功与失败路径，再检查全部日志和模拟 Sentry 上报；哨兵不得出现。不要使用真实用户凭证做日志探针。

**R03 普通 JSON 的限制必须发生在解析之前**

依据：[05 接口](05-api-and-realtime.md) 第 9–18 行规定 Content-Type 和 zod 校验；[10 部署](10-deployment.md) 第 82–86 行把整个 `/api/` 的上限设为 `110m`；API 容器只有 1 GB 内存。

文件允许 100 MB，不意味着登录、设置、邀请和消息 JSON 都应接收这个数量级的请求体。正文最多 5000 字是解析后的业务限制；并发大 JSON 在触发 zod 拒绝之前就可能消耗大量内存。现行文档没有定义普通 JSON 的字节上限、解析前执行顺序及无 Content-Length 时的处理。

建议给 JSON、上传内容和 monitoring 分别设置预算；普通 JSON 可先以 64–256 KiB 为候选，经真实最大合法请求校准。限制应在网关和应用读取流时执行，不能仅信任 Content-Length。[Hono body-limit 文档](https://hono.dev/docs/middleware/builtin/body-limit)提供了流式计数的实现入口。

验收覆盖超大 JSON、无长度请求、声明长度异常以及并发慢请求；应该尽早返回 413，正常小请求仍能服务。上传继续使用独立预占与流式路径。

**R04 后台执行需要独立于 HTTP 的授权身份模型**

依据：[03 架构](03-architecture.md) 第 181–183 行规定业务写入锁定并复核 session；[04 数据模型](04-data-model.md) 的 `agent_runs`、`agent_approvals`、`scheduled_messages` 主要持久化 user_id，没有明确的发起 session 或授权委托；[01 产品](01-product-spec.md) 的登录 session 为 30 天，定时任务最长可预约 365 天。

这里有一个必须明确的选择：后台任务若每次要求原 session 有效，用户退出或 session 到期后，合法的长期定时任务就无法执行；若仅凭持久化 user_id 执行，又不符合所有业务写入都检查 session 的统一表述。设备被盗后撤销该设备，已排队 run、已批准操作和未来定时任务分别怎么办，也没有真值表。

建议把身份分成当前 HTTP session 和持久授权委托。委托至少记录本人身份、批准的目标与参数、来源凭证、权限世代、有效期及撤销状态；执行仍检查当前账号、成员、禁言和归档。明确普通退出、指定设备撤销、改密、找回密码、封禁和注销各自影响哪些任务。

这不是断言“退出后执行一定是漏洞”：已批准的提醒可以有独立生命周期，但必须明确授权依据。验收要同时证明正常退出后合法任务仍按约定工作，以及安全撤销能够阻止约定应撤销的后续效果。

**R05 自带 key 的隐私边界不能只看当前 run 的字段**

依据：[06 Agent](06-agent.md) 第 15、40–45、180–181、300–312 行；[01 产品](01-product-spec.md) 第 294–295 行；[04 数据模型](04-data-model.md) `agent_runs.key_source`。

当前方案按 run 的 key_source 控制管理员读权限，但同一 Agent 对话会继承历史，专用 Agent 会话还能读取所有可访问会话。可能出现：先用自带 key 生成私有内容，再改成站点额度继续同一对话；旧回答、工具结果或摘要进入新的 site run 后，管理员通过新 run 读到它们。仅禁止访问旧 user run 的详情接口，不能阻止这个路径。

这属于尚未决定的内容继承规则，不是已证实的越权实现。如果产品允许用户把旧内容重新交给站点 key，隐私说明和切换行为需要准确表达这个例外；如果希望默认保留两类运行的隔离，切换隐私类别就应开启新上下文段，检索、摘要和工具结果的传递来源也必须遵守边界，只有明确选入的内容才迁移。不能仅清空对话历史，却允许搜索工具重新取回同一份内容。

保留 D-034 的既定方向：站点 key 的本次运行可审计、自带 key 的原运行受限。需要补的是两者之间的内容流转规则。验收覆盖 user→site→user、显式重试、长期摘要、记忆与跨 Agent 会话检索，而不只检查管理接口的 key_source 过滤。

**R06 媒体隔离还缺少实施机制**

依据：[03 架构](03-architecture.md) 第 211 行要求媒体子进程无网络、512 MiB、60 秒、256 MiB 临时目录；[10 部署](10-deployment.md) 第 36–37 行让 API 和 worker 共用带 ffmpeg 的镜像，媒体位于需要访问数据库、S3 和模型服务的 worker 中。

要求本身合理，但“另起子进程”“非 root”并不会自动建立独立网络、内存或凭证边界。尚未选定如何限制子进程的网络、环境变量、文件系统和内存，也没有说明超限时如何只终止该任务。单独给整个 worker 限制 2 GB，不能证明媒体只用 512 MiB，也不能证明它无法读取 worker 的凭证。

建议在 M3 前完成一个实际沙箱实验，明确受限执行器或独立媒体容器的选择、输入输出交换方式、最小环境变量、只读文件系统、临时目录和进程组清理。容器方案的网络隔离可参考 [Docker none 网络](https://docs.docker.com/engine/network/drivers/none/)，但必须同时解决存储访问和资源边界，不能给联网的整个 worker 简单断网。

验收在 Linux/ARM 目标形态中使用恶意测试进程尝试联网、读取哨兵凭证、超额分配内存、派生子进程和写满临时盘；主 worker 的租约续期、清理和聊天派发应继续工作。Windows 本地应使用同等隔离路径，或明确哪些证据必须由容器提供。

**R07 非消息实体的版本契约不完整**

依据：[05 接口](05-api-and-realtime.md) 第 18 行要求设置携带 version，第 57–68 行的 `Me`、`Conversation`、`Member` 没有对应的完整版本，第 265–267 行允许读取比固定日志上界更新的当前实体。

消息有 changeSeq 和 streamRevision，run 有 stateVersion；会话设置、个人通知偏好、用户资料和可恢复移除墓碑尚未明确等价规则。membershipId 只区分退出重入，消息 lastChangeSeq 也不能表示单纯的通知设置变更。旧 GET 响应晚于新设置响应到达时，客户端缺少可直接比较的实体版本；仅有“该页扫描到哪里”的 through 不能总是替代实体版本。

建议定义会话元数据版本、个人成员设置版本、用户资料版本以及移除操作的版本；普通 GET、PATCH 和同步投影使用同一契约。也可以采用经过证明的串行读取策略，但要写清跨端变更与并发响应的合并规则，不能留给前端临时猜测。

验收故意调换响应顺序，覆盖改名、免打扰、角色变更、归档后恢复和已读推进；旧响应不能覆盖新状态或重新删除已恢复的列表项。

**R08 代发不应自动代表用户已经阅读**

依据：[03 架构](03-architecture.md) 第 182 行在通用发送事务中推进发送者已读；[06 Agent](06-agent.md) 第 73–74 行规定助手以用户身份立即或定时发送；[01 产品](01-product-spec.md) 第 249–253 行把未读定义为 last_seq 减 last_read_seq。

反例：用户已读到 50，会话已有 100 条，尚有 50 条未读；后台定时发送第 101 条。如果复用规定的通用发送流程，last_read_seq 会变成 101，未读降为 0，而用户没有打开会话。单调更新和事务一致性都无法纠正这个产品语义错误。

建议由服务端可信的执行来源决定是否推进已读。后台代发/定时发送默认不推进人的已读；本人交互发送或明确阅读动作才按产品规则推进。不要接受客户端任意声明的 sender 类型来绕过权限。

验收让用户离线、后台执行代发，同时检查其他设备的未读和“总结未读”结果。该反例已按规划公式计算，但不是应用运行时测试。

**R09 灾难后用于恢复删除状态的记录来源仍未落实**

依据：[10 部署](10-deployment.md) 第 124–142 行。

最新方案已经正确规定：恢复时先隔离，拿不到后续删除证据就保持相关内容不可公开。这解决了默认盲目恢复的风险，但没有说明这些后续墓碑和注销记录保存在什么独立位置。

反例：00:00 备份，01:00 用户删除消息，02:00 原主机及数据库丢失。旧快照没有 01:00 的删除记录；如果墓碑也只存在原库，就无法判定旧快照中的哪些内容应继续隐藏。保守隔离是安全退路，但依靠人工逐项确认可能无法满足 RTO ≤4 小时。

建议选择独立、可恢复且受控的删除/注销日志及其顺序和保留策略，或明确缺少该证据时的可用性降级范围和验收目标。若异地记录异步写入，必须说明尚未复制的窗口，不能重新承诺零遗漏。演练要包含原主机彻底不可用的情况，不能偷偷从仍存活的源数据库取回墓碑来证明灾难恢复成功。

**R10 故障测试需要真正独立的基础设施**

依据：[08 测试](08-testing.md) 第 44–52 行；[09 本地开发](09-local-dev.md) 的端口与 Compose；当前 [开发 Compose](../infra/compose.dev.yml)。

普通集成测试使用同一 PostgreSQL 实例的 chatapp_test、同一 Valkey 实例的 db 1 和单独 Garage bucket，这可以隔离很多数据操作。它不能隔离容器退出、Valkey 全局内存压力、磁盘满、服务重启、网络中断和实例级配置变更。规划同时要求这些故障只在测试服务发生，但尚未定义独立服务的启动入口与拓扑。

建议在首次故障测试前提供独立 Compose 项目，使用独立容器、卷、网络、端口和凭据；普通集成测试可继续使用便捷环境。故障入口除 APP_ENV 和名称校验外，还应核验实际目标实例，防止把开发服务误当成可销毁的实验对象。

验收在开发服务仍运行且保留哨兵数据时中断测试实例；开发服务必须持续可用，数据保持不变。本轮没有实施任何破坏性测试。

**R11 检索质量验收缺少可复核的指标**

依据：[06 Agent](06-agent.md) 第 227–231 行要求“30 个以上中文查询，检索质量达标”，第 285 行用关键词或另一个模型评价总结覆盖率；[11 路线图](11-roadmap.md) 第 388 行仅写语义搜索通过质量检查。

性能与内存阈值已经量化，检索质量仍缺少固定语料、标注方式、K 值、指标和通过线。记忆的相似度阈值也没有校准方法。两个实现者可能对同一结果分别给出通过和失败，测试只使用演示数据还容易高估效果。

建议建立中文任务集及独立留出集，覆盖短词、人名、时间、否定、无结果、长消息和无权限来源。关键词检索作为基线，再定义 Recall@K 或 nDCG@K 等指标及最小改善要求；检索返回无权数据仍必须为零。总结使用人工标注的必含事实与禁止编造事实，模型打分只作辅助。阈值可在一次明确的校准实验后冻结，不必现在虚构一个通过比例。

验收保存语料版本、模型及量化配置、硬件、端到端延迟和分项结果；换模型或提示词时复用同一留出集复测。30 条可以用于第一轮冒烟，不能自动视为全面质量证据。

**R12 预算控制和可服务人数需要分开估算**

依据：[12 决策](12-decisions.md) D-022 写每人每日 50 万 token、全站每月 20 美元足够日常使用；[06 Agent](06-agent.md) 已有正确的两级预算预占；[01 产品](01-product-spec.md) 设计容量为 1000 个注册用户。

20 美元是站点愿意付出的上限，50 万 token 是个人使用上限，两者都不能证明多少人能稳定使用助手。需要把活跃 AI 用户、每日任务量、每任务调用次数、上下文大小、缓存命中、重试和 eval 成本连起来。

以下只是容量场景，不是用量预测：100 人每天各用 5 次，每月 30 天；每次仅一个模型调用，8000 个未缓存输入 token 加 1000 个输出 token；按当前 [DeepSeek Flash 官方峰时价格](https://api-docs.deepseek.com/quick_start/pricing/)每百万输入 0.3 美元、输出 1.2 美元计算，每次 0.0036 美元，月计约 54 美元。缓存和非峰时可降低费用，多步工具循环则可能增加费用。20 美元只覆盖约 5555 个这种单调用样本。

建议在真实试用前定义预计覆盖人数、站点额度的分配方式和预算耗尽后的体验；用真实任务记录校准，不直接调整用户既定预算。预算预占能保护费用，但不能替代可用性目标。
